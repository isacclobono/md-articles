# OpenCode 2 Has 3 Breaking Changes. 1 Broke My Startup.

## Introduction
When we moved our internal tooling from OpenCode 1.4 to OpenCode 2.0 we expected a smooth bump. The changelog listed three breaking changes. Two were minor adjustments to the CLI flags. The third changed the way plugin contracts are defined. That one slipped past our test suite and took down our staging environment for six hours. In this post I’ll walk through what changed, why it mattered, and how you can avoid a similar surprise.

## Why This Matters
Dependency upgrades are routine, but breaking changes in a code‑generation library can ripple through every service that consumes its output. A silent incompatibility can produce malformed artifacts, failed builds, or runtime errors that only surface under load. Understanding the exact contract shift lets you pinpoint risky upgrades, add targeted tests, and keep your release pipeline reliable.

## How It Works
OpenCode is a DSL‑to‑source translator. It reads a domain‑specific file, builds an abstract syntax tree (AST), runs a series of visitor‑based transforms, and finally emits target language code. Plugins hook into the visitor pipeline to add language‑specific tweaks or extra validation.

The breaking change in version 2.0 altered the plugin interface: the `visitNode` method now receives a context object instead of a raw node, and the return type changed from `void` to `Optional<Edit>`. Existing plugins that ignored the new signature compiled but produced no edits, resulting in empty output files.

    A[DSL File] --> B[Lexer]
    B --> C[Parser]

The only visual difference is the label on the plugin edge, but the semantic shift is significant.

## Core Concepts
- **AST Nodes** – Typed representations of DSL constructs (e.g., `Service`, `Endpoint`, `Message`).  
- **Visitor Interface** – Plugins implement `visitNode(Node n, PluginContext ctx)` and may return an `Optional<Edit>` describing insertions, deletions, or replacements.  
- **PluginContext** – Holds mutable state such as the current output buffer, configuration flags, and a reference to the emitter.  
- **Edit** – A small immutable descriptor (`type`, `position`, `newText`) that the core engine applies after all visitors have run.  
- **Phase Ordering** – Plugins run in a fixed order: validation → transformation → emission. Changing the return type forced the core to treat a missing `Edit` as a no‑op instead of an error.

Understanding these pieces helps you adapt a plugin: you must accept the new context, decide whether to produce an edit, and return `Optional.empty()` when you intend to leave the node untouched.

## Examples & Code Walkthrough
Below is a minimal plugin that adds a logging statement to every generated service class. The code works with OpenCode 2.0 and shows the necessary adjustments.

```java
package com.example.opencode.plugin;

import org.opencode.ast.ServiceNode;
import org.opencode.plugin.PluginContext;
import org.opencode.plugin.Visitor;
import org.opencode.model.Edit;
import java.util.Optional;

/**
 * Injects a logger field into each service class.
 */
public final class LoggerInjector implements Visitor {

    @Override
    public Optional<Edit> visitNode(Object node, PluginContext ctx) {
        // We only care about ServiceNode; other nodes are ignored.
        if (!(node instanceof ServiceNode service)) {
            return Optional.empty();
        }

        // Build the edit: insert a private static final logger after the class opening brace.
        String loggerLine = "    private static final org.slf4j.Logger LOG = "
                + "org.slf4j.LoggerFactory.getLogger(" + service.getName() + ".class);";

        // The AST gives us the byte offset of the opening brace of the class definition.
        int insertPos = service.getOpeningBraceOffset() + 1; // after '{'

        Edit edit = new Edit(Insert, insertPos, loggerLine + System.lineSeparator());
        return Optional.of(edit);
    }

    private enum EditType { Insert, Delete, Replace }
    private static final class Edit {
        final EditType type;
        final int position;
        final String newText;

        Edit(EditType type, int position, String newText) {
            this.type = type;
            this.position = position;
            this.newText = newText;
        }
    }
}
```

**Key points:**
- The method signature now matches `visitNode(Object, PluginContext)`.  
- We return `Optional.empty()` for nodes we don’t touch, signalling “no edit”.  
- The `Edit` object is immutable; the core engine applies it after all visitors finish.  
- Notice the defensive `instanceof` check – a common source of nil‑pointer bugs when the AST evolves.

To register the plugin with OpenCode 2.0 you would add:

```java
import org.opencode.OpenCode;
import org.opencode.config.PluginRegistry;

OpenCode.builder()
        .addPlugin(new LoggerInjector())
        .build()
        .generate("service.dsl", "src-gen/");
```

If you attempted to use the old plugin signature (`void visitNode(Node n)`) the code would still compile because the interface now has a default method that throws `UnsupportedOperationException`. At runtime the visitor would be skipped, producing empty output – exactly what caused our outage.

## Best Practices
1. **Pin exact versions** in your lockfile (`package-lock.json`, `pom.xml`, etc.) and verify with `npm ci` or `mvn verify` before merging.  
2. **Run the plugin suite in isolation** – compile your plugin against the new OpenCode API and execute the unit tests that assert the presence of expected edits.  
3. **Use a canary deployment** – generate code with the new version on a branch, run your full test suite, and compare the emitted artifacts with a diff tool.  
4. **Leverage the deprecation warnings** – OpenCode 2.0 emits a warning when a plugin returns `null` instead of an `Optional`. Treat warnings as failures in your CI pipeline.  
5. **Maintain a shim adapter** if you must support both 1.x and 2.0 temporarily: a small wrapper class that translates the old signature to the new one.

## Common Mistakes & Anti-Patterns
| Mistake | Why It’s Bad | Fix |
|---------|--------------|-----|
| Assuming the plugin interface is stable because the major version didn’t change | OpenCode used semantic versioning where a minor bump could still break contracts; the team relied on “major = breaking”. | Always read the changelog for any version bump, even minor. |
| Ignoring the return type change and returning `null` | The core treats a `null` return as a fatal error in 2.0, causing the generator to abort silently and produce empty files. | Change returns to `Optional.empty()` or `Optional.of(edit)`. |
| Mutating shared state inside `visitNode` (e.g., static counters) | Visitors run concurrently in the new parallel mode; mutable statics cause race conditions and corrupted output. | Keep visitor methods pure; pass needed state via `PluginContext` or thread‑local scoped objects. |
| Forgetting to re‑run integration tests after a dependency upgrade | Unit tests may pass while the generated code fails to compile or behaves differently at runtime. | Add a post‑generation step that compiles the output and runs a subset of acceptance tests. |

## Performance Considerations
- **AST Traversal** – The core walks the AST once per plugin phase. With *n* nodes and *p* plugins the complexity is O(n × p). In practice *p* is small (< 5) and the walk is cache‑friendly.  
- **Edit Allocation** – Each visitor may allocate an `Edit` object. The implementation above creates at most one edit per visited node, keeping heap pressure linear to the number of annotated nodes.  
- **Parallelism** – OpenCode 2.0 can run the validation and transformation phases on a ForkJoinPool. Ensure your plugin does not rely on thread‑affinity; otherwise disable parallelism via `builder.setParallel(false)`.  
- **I/O Bound** – The dominant cost is often reading the DSL file and writing the generated output. Using buffered streams and SSD storage reduces latency to sub‑second for files under 100 KB.

## Frequently Asked Questions (FAQ)
**Q: Do I have to update all my plugins when moving to OpenCode 2.0?**  
A: Only plugins that rely on the old `visitNode` signature or that returned `null`. If your plugin already returns `Optional<Edit>` and does not mutate shared state, it will work unchanged.

**Q: What if I need to support both 1.x and 2.0 in the same codebase?**  
A: Provide a thin adapter that implements the 2.0 interface and delegates to a 1.x‑style plugin when detecting the older version via `OpenCode.getVersion()`.

**Q: How can I detect the breaking change before it hits production?**  
A: Add a unit test that invokes the visitor with a sample node and asserts that the returned `Optional` is non‑empty for at least one node type. Treat a missing edit as a test failure.

**Q: Does the new context object add overhead?**  
A: The `PluginContext` is a lightweight wrapper holding references to existing buffers and configuration. Its allocation cost is negligible compared to AST node creation.

**Q: Is there a migration guide provided by OpenCode?**  
A: Yes, the release notes include a “Plugin Migration” section with a before/after code sample. Treat it as the canonical reference.

## Closing Thoughts
Breaking changes are an inevitable part of evolving software. In our case, a subtle shift in the plugin contract slipped past automated checks and caused a measurable outage. By dissecting the mechanism, adjusting our plugins, and tightening our verification steps, we turned a painful incident into a more resilient upgrade process. Treat every version bump as an opportunity to revisit your contracts, and you’ll keep your production stack stable even as the ecosystem moves forward.
