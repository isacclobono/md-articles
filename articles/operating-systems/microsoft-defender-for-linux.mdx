# Microsoft Defender for Linux

## Introduction

Most security teams I work with treat Linux servers as second-class citizens in their EDR strategy. Windows endpoints get a full-featured agent, while Linux hosts are left with a collection of open-source scanners, custom audit rules, and hope. The architectural problem is straightforward: you have a heterogeneous fleet, but your security telemetry is fragmented. Microsoft Defender for Linux attempts to close that gap by bringing the same Defender for Endpoint sensor and cloud backend to RHEL, Ubuntu, SUSE, and other enterprise distributions.

It is not a rebranded Windows port. The Linux agent runs as a native system service with a kernel-level sensor for real-time protection, a user-mode scanner for on-demand jobs, and a command-line tool (`mdatpctl`) for local management. The goal is a single console for detections across Windows and Linux, but achieving that in production requires understanding where the agent fits in your stack and where it can get in the way.

## Why This Matters

Linux servers run your databases, your Kubernetes nodes, and your CI/CD runners. They are also high-value targets for cryptominers, ransomware, and lateral movement after an initial compromise in a web application. When a vulnerability like Log4j or a supply-chain backdoor hits, you need to know which Linux hosts are affected and whether any malicious binaries have executed. Without a unified agent, that means logging into dozens of boxes and running ad-hoc scans.

Defender for Linux solves a specific production pain point: alert fatigue from disjointed tooling. If your Windows fleet sends telemetry to Microsoft Defender but your Linux fleet sends logs to a separate SIEM with no correlation, an attacker hopping from a compromised workstation to a Linux database server becomes invisible at the boundary. A single agent and a single API surface reduce the mean time to detection, but only if you deploy it without destabilizing the hosts it is supposed to protect.

## How It Works

The agent architecture splits responsibilities between a privileged kernel component and an unprivileged user-mode service. The kernel sensor registers for file-system and process events. When a binary is executed or a file is written, the event is forwarded to the user-mode service, which checks it against local signatures and, when necessary, submits metadata to the Defender cloud for deeper analysis. On-demand scans are triggered through `mdatpctl` and traverse directories using the local engine.
