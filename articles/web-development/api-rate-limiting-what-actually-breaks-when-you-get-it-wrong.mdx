# API Rate Limiting: What Actually Breaks When You Get It Wrong

## Introduction
A few years ago our team watched a critical service degrade from 200 ms latency to over 5 seconds after a minor traffic spike. The root cause wasn’t a bug in the business logic; it was a misconfigured rate limiter that started returning 429 responses to every request. Clients, unaware of the back‑off semantics, immediately retried, turning a protective throttle into a retry storm that overwhelmed downstream databases. The incident taught us that rate limiting is not just a “nice‑to‑have” header; it is a distributed system primitive that can amplify failures when implemented incorrectly.

## Why This Matters
Modern APIs are consumed by a mix of internal services, third‑party partners, and end‑user applications. Without effective throttling, a single misbehaving client can cause resource exhaustion, cascading failures, or unfair resource consumption. Conversely, an overly aggressive limiter can block legitimate traffic, degrade user experience, and trigger costly support tickets. Understanding the failure modes helps architects design limiters that protect the system while remaining observable and operable.

## How It Works
At its core, a rate limiter answers a simple question: *has this caller exceeded their allowed request quota within a given time window?* The answer must be computed quickly, consistently across multiple service instances, and with minimal coordination overhead.

A common production‑grade approach combines a **sliding window counter** stored in a fast, atomic data store (e.g., Redis) with a thin middleware layer that decides whether to let a request through or return **429 Too Many Requests**. The sliding window smooths the burstiness inherent in fixed‑window counters while avoiding the memory overhead of keeping a full request log.

**Step‑by‑step flow**

1. **Ingress** – The load balancer forwards the incoming HTTP request to the rate‑limit middleware.
2. **Key Extraction** – The middleware derives a limiter key (e.g., `API_KEY:IP:ENDPOINT`) from headers, JWT claims, or connection attributes.
3. **Atomic Check** – A Lua script runs inside Redis to:
   * Remove timestamps older than the window (`ZREMRANGEBYSCORE`),
   * Count remaining entries (`ZCARD`),
   * If under the limit, add the current timestamp (`ZADD` with `EXPIRE`),
   * Return the new count and the reset time.
4. **Decision** – If the returned count ≤ limit, the request proceeds to the backend; otherwise, middleware writes a `429` response, includes `Retry-After` (derived from the oldest timestamp in the window), and adds metrics (`rate_limit_blocked_total`).
5. **Observability** – Every check increments a histogram (`rate_limit_latency_seconds`) and a counter (`rate_limit_allowed_total` or `rate_limit_blocked_total`). These metrics drive alerts and autoscaling policies.

## Core Concepts
- **Sliding Window Counter** – Stores request timestamps in a sorted set; provides a smooth rate approximation without the “spike at window edge” problem of fixed windows.
- **Atomicity** – The Lua script guarantees that the read‑modify‑write sequence happens without race conditions, even under high concurrency.
- **Key Granularity** – Choosing the right dimensions (API key, IP, endpoint, tenant) determines how fairly limits are applied. Too coarse enables abuse; too fine creates hot keys in Redis.
- **Signaling** – Standard headers (`X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, `Retry-After`) let clients adapt their behavior.
- **Failure Modes** – If the store becomes unavailable, a common pattern is to **fail open** (let traffic through) or **fail closed** (block traffic) based on business risk tolerance. The choice must be explicit and observable.

## Examples & Code Walkthrough
Below are two production‑style snippets: a Go middleware that implements the sliding window with Redis Lua, and a TypeScript client that honors `Retry-After` with jittered exponential backoff.

### Go Middleware (Gin framework)
```go
package ratelimit

import (
	"context"
	"strconv"
	"time"

	"github.com/gin-gonic/gin"
	"github.com/go-redis/redis/v8"
)

// Config holds the limiter parameters.
type Config struct {
	Redis      *redis.Client
	Limit      int           // max requests
	Window     time.Duration // sliding window size
	KeyFunc    func(*gin.Context) string
	FailOpen   bool          // true = allow on Redis error
}

// Middleware returns a Gin handler that enforces the rate limit.
func Middleware(cfg Config) gin.HandlerFunc {
	lua := redis.NewScript(`
		-- KEYS[1] = storage key
		-- ARGV[1] = now (unix ms)
		-- ARGV[2] = window size (ms)
		-- ARGV[3] = limit
		local now = tonumber(ARGV[1])
		local window = tonumber(ARGV[2])
		local limit = tonumber(ARGV[3])

		-- Remove outdated entries
		redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, now-window)

		-- Count current entries
		local current = redis.call('ZCARD', KEYS[1])

		if current >= limit {
			-- Find oldest entry to compute reset time
			local oldest = redis.call('ZRANGE', KEYS[1], 0, 0, 'WITHSCORES')
			local reset = 0
			if #oldest == 2 {
				reset = math.max(0, oldest[2]+window-now)
			}
			return {0, reset}
		}

		-- Add current request
		redis.call('ZADD', KEYS[1], now, now)
		redis.call('EXPIRE', KEYS[1], math.ceil(window/1000))

		return {current + 1, 0}
	`)

	return func(c *gin.Context) {
		key := cfg.KeyFunc(c)
		if key == "" {
			c.AbortWithStatusJSON(400, gin.H{"error": "invalid key"})
			return
		}

		nowMs := time.Now().UnixNano() / int64(time.Millisecond)
		windowMs := int64(cfg.Window / time.Millisecond)

		var result []int64
		var err error
		if cfg.Redis != nil {
			result, err = lua.Run(context.Background(), cfg.Redis, []string{key}, nowMs, windowMs, int64(cfg.Limit)).Result()
		} else {
			err = cfg.Redis // nil client error
		}

		if err != nil {
			if cfg.FailOpen {
				c.Next()
				return
			}
			c.AbortWithStatusJSON(502, gin.H{"error": "rate limiter unavailable"})
			return
		}

		allowed := result[0]
		resetMs := result[1]

		c.Header("X-RateLimit-Limit", strconv.Itoa(cfg.Limit))
		c.Header("X-RateLimit-Remaining", strconv.FormatInt(allowed, 10))
		if resetMs > 0 {
			resetSec := time.Duration(resetMs) * time.Millisecond
			c.Header("X-RateLimit-Reset", strconv.FormatInt(time.Now().Add(resetSec).Unix(), 10))
			c.Header("Retry-After", strconv.FormatInt(int64(resetSec/time.Second), 10))
		}

		if allowed > int64(cfg.Limit) {
			c.Next()
			return
		}

		c.AbortWithStatusJSON(429, gin.H{
			"error":   "rate limit exceeded",
			"retry_after": resetMs / 1000,
		})
	}
}
```

**Explanation**
- The Lua script performs the sliding‑window logic atomically inside Redis, eliminating race conditions.
- On Redis failure we either fail open (configurable) or return a 502 to avoid silently dropping traffic.
- Headers follow the RFC‑style conventions; `Retry-After` is derived from the oldest timestamp in the window when a denial occurs.

### TypeScript Client with Jittered Backoff
```ts
import axios from 'axios';

interface RateLimitError extends Error {
  status: number;
  retryAfter?: number; // seconds
}

/**
 * Perform a GET request with automatic retry on 429.
 * Uses exponential backoff with full jitter to avoid thundering herd.
 */
async function fetchWithBackoff<T>(url: string, maxAttempts = 5): Promise<T> {
  let attempt = 0;
  while (true) {
    try {
      const resp = await axios.get<T>(url);
      return resp.data;
    } catch (err) {
      const e = err as RateLimitError;
      if (!e.response || e.response.status !== 429) {
        throw err; // non‑rate‑limit error, propagate
      }

      attempt++;
      if (attempt > maxAttempts) {
        throw new Error(`Max retries exceeded for ${url}`);
      }

      // Honor Retry-After header if present, otherwise use base delay
      const headerRetry = e.response.headers['retry-after'];
      const baseDelaySec = headerRetry ? parseInt(headerRetry, 10) : Math.min(2 ** attempt, 30);
      // Full jitter: random delay between 0 and baseDelaySec
      const delayMs = Math.random() * baseDelaySec * 1000;

      // Optional: respect Retry-After as a minimum delay
      const minDelayMs = (headerRetry ? parseInt(headerRetry, 10) : 0) * 1000;
      const finalDelayMs = Math.max(delayMs, minDelayMs);

      await new Promise(res => setTimeout(res, finalDelayMs));
    }
  }
}

// Usage
fetchWithBackoff<{data: string}>('https://api.example.com/resource')
  .then(console.log)
  .catch(console.err);
```

**Explanation**
- On a 429 response we read `Retry-After` (seconds) from the header; if missing we fall back to an exponential base.
- Full jitter (`Math.random() * base`) spreads retries uniformly over the interval, preventing synchronized retry storms.
- The loop caps attempts to avoid infinite retries on persistent limit violations.

## Best Practices
- **Choose the right algorithm** – Sliding window with a Redis sorted set offers a good trade‑off between accuracy and memory for most APIs. Token bucket works well for burst‑ tolerant workloads.
- **Make the limiter stateless at the service layer** – Keep all state in a fast, shared store; this enables horizontal scaling of API instances.
- **Use atomic scripts** – Lua (Redis) or transactions (etcd, Consul) prevent race conditions that would otherwise allow bursts beyond the limit.
- **Expose clear headers** – `X-RateLimit-Limit`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`, and `Retry-After` empower clients to self‑throttle.
- **Fail safely** – Decide early whether your system fails open or closed when the store is unreachable, and log the decision.
- **Instrument relentlessly** – Track allowed/blocked counts, latency of the check, and Redis error rates. Alert on sudden spikes in blocked requests.
- **Apply hierarchical limits** – Global IP limits, per‑API‑key limits, and per‑endpoint limits can be combined to defend against both volumetric and targeted abuse.
- **Educate consumers** – Provide documentation that explains the meaning of the headers and recommends back‑off strategies.
