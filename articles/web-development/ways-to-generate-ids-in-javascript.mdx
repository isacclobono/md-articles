# Ways to Generate IDs in JavaScript

## Introduction
When a UI component mounts, a fetch request is dispatched, or a record is stored in a database, a unique identifier is required. That identifier can be a React key, a URL slug, a session token, or a primary‑key value. The choice of generation strategy influences collision probability, performance, bundle size, and security. This article walks through the spectrum of ID generation techniques—from deterministic counters to cryptographically‑secure random bytes—and shows how to pick the right one for a given problem.

## Why This Matters
In production, a bad ID generator can cause silent data corruption. A collision in a cache key leads to stale UI, a clash in a URL slug breaks SEO, and a predictable token opens a session‑hijacking vector. Engineers must understand the trade‑offs between entropy, speed, and maintainability. The wrong approach adds latency to request handling, bloats the bundle with unnecessary dependencies, or introduces subtle bugs that surface only under load.

## How It Works
Choosing an ID generator is essentially a decision tree based on three axes: required entropy, performance budget, and formatting constraints. Below is a visual representation of the flow. The diagram highlights the primary branches and the typical code paths that lead to a usable identifier.

```mermaid
flowchart TD
    A[Start] --> B{Entropy needed?}
    B -->|High (crypto‑grade)| C[Use crypto.getRandomValues]
    B -->|Low (fast, non‑secure)| D[Use Math.random + timestamp]
    C --> E[Generate 128‑bit random array]
    D --> F[Combine Date.now with random suffix]
    E --> G[Encode to hex/base64]
    F --> G
    G --> H[Return formatted ID]
```

**Step‑by‑step breakdown**

1. **Assess entropy requirement** – If the ID is exposed to untrusted actors (authentication tokens, CSRF tokens, public URLs), a cryptographically‑secure source is mandatory.  
2. **Select source** – `crypto.getRandomValues` yields 32 bytes of true entropy per call. `Math.random` and `Date.now` are fast but predictable.  
3. **Shape the output** – For human‑readable IDs we typically encode the raw bytes (hex, base‑64, or base‑62). For machine‑only keys we may keep the raw binary representation.  
4. **Validate uniqueness** – Deterministic methods (timestamp + counter) rely on monotonicity; random methods rely on statistical rarity. The article later quantifies collision risk.

## Core Concepts
- **Uniqueness** – Guarantees that two entities never share the same identifier within the scope of use.  
- **Collision resistance** – Measured by the probability that two independently generated IDs collide (Birthday paradox).  
- **Entropy** – Number of unpredictable bits. A 128‑bit random value offers ~3.4 × 10³⁸ possibilities; a 32‑bit timestamp only ~4 billion.  
- **Readability** – IDs that are short and URL‑safe improve UX and SEO.  
- **Length vs. payload** – Short IDs reduce network overhead but may require larger entropy to keep collision probability low.

## Examples & Code Walkthrough
Below are production‑ready utility functions. Each includes defensive checks, clear naming, and inline comments.

### 1. Pseudo‑Random ID (`Math.random` + timestamp)
```js
/**
 * Generates a short, non‑cryptographic ID.
 * Format: yyyyMMddHHmmssSSS + 5 random chars (A‑Z0‑9).
 */
function makeFastId() {
    const ts = Date.now().toString(36); // base‑36 reduces length
    const rnd = Math.random().toString(36).slice(2, 7); // 5 chars
    return `${ts}${rnd}`.toUpperCase();
}
```
*Use case*: UI keys where predictability is acceptable.

### 2. Timestamp + Counter (`Date.now` + monotonic counter)
```js
let counter = 0;
/**
 * Generates a sortable, low‑entropy ID.
 * Format: epochMS (base‑36) + 3‑digit counter.
 */
function makeSortableId() {
    const epoch = Date.now().toString(36);
    // ensure counter does not overflow
    if (counter >= 999) counter = 0;
    const seq = (++counter).toString(36).padStart(3, '0');
    return `${epoch}${seq}`;
}
```
*Use case*: Incremental primary keys in a single‑process service.

### 3. Cryptographically Secure ID (`crypto.getRandomValues`)
```js
/**
 * Returns a URL‑safe base‑64 ID with 128 bits of entropy.
 */
function makeSecureId() {
    if (!crypto?.getRandomValues) {
        throw new Error('crypto.getRandomValues not available');
    }
    const arr = new Uint8Array(16); // 128 bits
    crypto.getRandomValues(arr);
    // encode to base‑64, strip padding for URL friendliness
    return btoa(String.fromCharCode(...arr))
        .replace(/\+/g, 'u')
        .replace(/\//g, 'v')
        .replace(/=/g, '');
}
```
*Use case*: Authentication tokens, session IDs.

### 4. Custom UUID‑v4 (random)
```js
/**
 * Implements RFC‑4122 version‑4 UUID.
 * Pattern: xxxxxxxx-xxxx-4xxx-yxxx-xxxxxxxxxxxx where y ∈ {8,9,a,b}
 */
function makeUuidV4() {
    const r = (n) => {
        const arr = new Uint8Array(n);
        crypto.getRandomValues(arr);
        return Array.from(arr, (b) => b.toString(16).padStart(2, '0')).join('');
    };
    const timeLow = r(4);
    const timeMid = r(2);
    const timeHiAndVersion = r(2);
    const clockSeqHi = r(1);
    const clockSeqLow = r(1);
    const node = r(6);
    // set version to 4 (random)
    const versionByte = parseInt(timeHiAndVersion[2], 16) & 0x0f;
    const versionHex = (versionByte | 0x40).toString(16);
    timeHiAndVersion = timeHiAndVersion.slice(0, 2) + versionHex + timeHiAndVersion.slice(3);
    // set variant to RFC‑4122 (bits 1,0 = 10)
    const variantByte = parseInt(clockSeqHi, 16) & 0x3f;
    const variantHex = (variantByte | 0x80).toString(16);
    clockSeqHi = variantHex + clockSeqLow;
    return `${timeLow}-${timeMid}-${timeHiAndVersion}-${clockSeqHi}-${node}`;
}
```
*Use case*: Inter‑service identifiers where a standard format is expected.

### 5. NanoID‑style generator (tiny, alphabet‑aware)
```js
const nanoIdAlphabet = '0123456789ABCDEFGHIJKLMNOPQRSTUVWXYZabcdefghijklmnopqrstuvwxyz';
const nanoIdMask = 63; // 2^6 - 1
const nanoIdByteSize = 1.6; // log2(63) ≈ 5.977 bits per char, we use 6 bits per char

/**
 * Generates a URL‑safe, short ID using a custom alphabet.
 */
function makeNanoId(length = 21) {
    const idArr = new Uint8Array(Math.ceil(length * nanoIdByteSize));
    crypto.getRandomValues(idArr);
    let result = '';
    for (let i = 0; i < length; i++) {
        const idx = idArr[i] & nanoIdMask; // ensure value < 63
        result += nanoIdAlphabet[idx];
    }
    return result;
}
```
*Use case*: UI component keys, short slugs.

### 6. ShortID‑like compact base‑62 ID
```js
const base62 = '0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ';

/**
 * Compacts a 32‑bit random number into a 5‑character base‑62 string.
 */
function makeShortId() {
    const rand = new Uint32Array(1);
    crypto.getRandomValues(rand);
    let num = rand[0];
    let out = '';
    for (let i = 0; i < 5; i++) {
        const rem = num % 62;
        out = base62[rem] + out;
        num = Math.floor(num / 62);
    }
    return out;
}
```
*Use case*: URL slugs where length matters.

### 7. Hash‑based ID (SHA‑256 of payload, truncated)
```js
// assumes a global `crypto.subtle` is available
async function makeHashId(payload) {
    const enc = new TextEncoder();
    const data = enc.encode(payload);
    const hashBuf = await crypto.subtle.digest('SHA-256', data);
    const hashArray = Array.from(new Uint8Array(hashBuf));
    // take first 8 bytes (64 bits) for a short ID
    const short = hashArray.slice(0, 8);
    // encode to hex
    return short.map(b => b.toString(16).padStart(2, '0')).join('');
}
```
*Use case*: Deterministic IDs for immutable data (e.g., document content hash).

## Best Practices
- **Match entropy to threat model** – Use `crypto.getRandomValues` for anything exposed to the client or logged in telemetry.  
- **Prefer native APIs** – `crypto.getRandomValues` is built into browsers and Node ≥ 14, avoiding extra bundle weight.  
- **Validate length** – Short IDs (< 10 chars) should have at least 64‑bit entropy to keep collision probability under 10⁻⁹ per million IDs.  
- **Cache generation logic** – For high‑throughput endpoints, reuse a single `Uint8Array` instance to reduce allocations.  
- **Document assumptions** – State whether IDs are sortable, lexicographically comparable, or guaranteed unique only within a session.

## Common Mistakes & Anti‑Patterns
1. **Using `Math.random` for tokens**  
   *Problem*: `Math.random` uses a predictable seed in many environments; an attacker can reconstruct future values.  
   *Fix*: Replace with `crypto.getRandomValues` or a library that wraps it (e.g., `secure-random-uuid`).  
   *Code*: see `makeSecureId` above.

2. **Reusing random bytes across IDs**  
   *Problem*: If you generate a random segment once and append it to many IDs, the entropy per ID drops dramatically.  
   *Fix*: Call the random generator for each ID or ensure you draw fresh bytes per identifier.  
   *Code*: `makeNanoId` draws a new array per call.

3. **Assuming timestamp uniqueness without a counter**  
   *Problem*: High‑frequency systems can generate multiple IDs within the same millisecond, causing collisions.  
   *Fix*: Combine timestamp with a monotonic counter or a random suffix.  
   *Code*: `makeSortableId` adds a per‑process counter.

4. **Exposing raw entropy in URLs**  
   *Problem*: Long base‑64 strings may be truncated by routers or become unwieldy in logs.  
   *Fix*: Encode with a URL‑safe alphabet and consider truncation after confirming collision risk is acceptable.  
   *Code*: `makeSecureId` replaces `+` and `/` and strips padding.
