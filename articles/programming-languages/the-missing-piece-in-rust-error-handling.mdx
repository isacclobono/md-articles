# The Missing Piece in Rust Error Handling

## Introduction

I've spent the last seven years running Rust services in production at a fintech company that processes millions of transactions daily. Our error handling started simple: `Result<T, E>`, the `?` operator, and `thiserror` for derive macros. It worked fine until it didn't.

The breaking point came during a SEV-2 incident where a downstream payment provider started returning intermittent 503s. Our logs showed `DbError(ConnectionRefused)` — technically accurate, useless operationally. Which request? Which customer? Which retry attempt? The stack trace pointed to `fetch_user`, but the request ID, idempotency key, and correlation ID had all been stripped away by the time the error bubbled up to our HTTP handler.

This isn't a Rust problem per se. It's a *context propagation* problem. Every language struggles with it. But Rust's type system gives us tools to solve it properly — if we're willing to build the right abstraction.

What follows is the pattern we evolved after three major rewrites. It's not a crate recommendation. It's a design pattern you can implement in fifty lines of standard library code.

## Why This Matters

Production debugging isn't about reading error messages. It's about reconstructing *state* at the moment of failure.

Consider what a proper incident response requires:
- The request ID to correlate logs across services
- The user ID to assess blast radius
- The idempotency key to determine if retry is safe
- The feature flag state to isolate bad rollouts
- The retry attempt number to distinguish transient from systemic failures

None of this lives in your error types. Nor should it — your domain errors (`InsufficientFunds`, `RateLimited`, `SchemaViolation`) are business logic. Context is operational metadata. Mixing them conflates concerns and bloats your error enums.

Current solutions fall short:

| Approach | Context Support | Propagation | Inspection |
|----------|-----------------|-------------|------------|
| `thiserror` | Manual fields per variant | Automatic via `?` | Pattern matching required |
| `anyhow`/`eyre` | Ad-hoc `.context()` strings | Automatic | String parsing / downcasting |
| `tracing` spans | Rich, structured | Manual (span guards) | Log aggregation only |
| Custom wrapper | Full control | Manual wrapping | Full control |

The gap: **structured, typed context that flows automatically with `?` and can be inspected without downcasting.**

## How It Works

The core insight: wrap any error type in a generic container that carries an immutable context map. Implement `From` for the wrapper so `?` handles propagation transparently. Provide ergonomic extension traits so callers never see the wrapper type unless they want to.

```mermaid
flowchart TD
    A[Function returns Result&lt;T, E&gt;] --> B{Caller adds context?}
    B -- Yes --> C[.with_context(key, value)]
    B -- No --> D[Propagates unchanged]
    C --> E[Result&lt;T, Contextual&lt;E&gt;&gt;]
    E --> F{Next caller uses ?}
    F -- Yes --> G[From::from merges context maps]
    F -- No --> H[Explicit handling]
    G --> I[Result&lt;U, Contextual&lt;E&gt;&gt;]
    I --> J[...propagates up stack...]
    J --> K[HTTP handler inspects .context()]
    K --> L[Structured logging / alerting]
    
    style A fill:#e8f5e9
    style E fill:#fff3e0
    style I fill:#fff3e0
    style K fill:#e3f2fd
    style L fill:#e3f2fd
```

**Step-by-step propagation:**

1. **Leaf function** returns `Result<User, DbError>` — no wrapper, zero overhead
2. **Mid-layer caller** invokes `.with_context("request_id", req.id)` on the `Result`, converting it to `Result<User, Contextual<DbError>>`
3. **Subsequent `?` operations** trigger `From<Contextual<E>> for Contextual<E>` which *merges* context maps (child context wins on key collision)
4. **Top-level handler** receives `Result<Response, Contextual<AppError>>` and reads `.context()` for logging, metrics, or user-facing messages

The merge semantics matter. If `fetch_user` adds `table: "users"` and the HTTP handler adds `request_id: "abc-123"`, both survive. If both add `retry_attempt`, the *outer* value wins — it's more specific.

## Core Concepts

### The Wrapper Type

```rust
use std::collections::HashMap;
use std::fmt;

/// Immutable context map. String keys/values keep it simple and serialization-friendly.
/// In production we use `ahash::AHashMap` for DOS resistance and `Arc<str>` for sharing.
pub type ContextMap = HashMap<String, String>;

/// Wraps any error type with contextual metadata.
/// 
/// Invariants:
/// - `ctx` is only mutated during construction (via `with_context`)
/// - After construction, the wrapper is logically immutable
/// - `inner` is never `None` — this is not an `Option`
#[derive(Debug)]
pub struct Contextual<E> {
    inner: E,
    ctx: ContextMap,
}

impl<E> Contextual<E> {
    /// Construct a new wrapper with empty context.
    #[inline]
    pub fn new(inner: E) -> Self {
        Self {
            inner,
            ctx: ContextMap::new(),
        }
    }

    /// Add a key-value pair. Consumes self to encourage chaining.
    /// 
    /// Takes `Into<String>` so callers can pass `&str`, `String`, or anything
    /// implementing the trait (including integers via `to_string()`).
    pub fn with_context<K, V>(mut self, key: K, value: V) -> Self
    where
        K: Into<String>,
        V: Into<String>,
    {
        self.ctx.insert(key.into(), value.into());
        self
    }

    /// Add multiple pairs at once. Useful for bulk context from a struct.
    pub fn with_context_iter<I, K, V>(mut self, iter: I) -> Self
    where
        I: IntoIterator<Item = (K, V)>,
        K: Into<String>,
        V: Into<String>,
    {
        self.ctx.extend(iter.into_iter().map(|(k, v)| (k.into(), v.into())));
        self
    }

    /// Access the wrapped error.
    #[inline]
    pub fn inner(&self) -> &E {
        &self.inner
    }

    /// Access the context map (read-only).
    #[inline]
    pub fn context(&self) -> &ContextMap {
        &self.ctx
    }

    /// Consume the wrapper, returning the inner error and context separately.
    /// Useful when you need to handle the error type concretely.
    pub fn into_parts(self) -> (E, ContextMap) {
        (self.inner, self.ctx)
    }
}
```

### The Propagation Trait

This is where the ergonomics live. We extend `Result<T, E>` with a method that conditionally wraps the error — only when context is actually added.

```rust
/// Extension trait for adding context to any `Result`.
/// 
/// The return type is `Result<T, Contextual<E>>` — the caller doesn't need
/// to change their function signature unless they *add* context.
pub trait ContextualExt<T, E> {
    /// Attach a key-value pair to the error if this `Result` is `Err`.
    /// 
    /// Returns `Result<T, Contextual<E>>` which implements `From<Contextual<E>>`
    /// for seamless `?` propagation.
    fn with_context<K, V>(self, key: K, value: V) -> Result<T, Contextual<E>>
    where
        K: Into<String>,
        V: Into<String>;

    /// Attach multiple key-value pairs.
    fn with_context_iter<I, K, V>(self, iter: I) -> Result<T, Contextual<E>>
    where
        I: IntoIterator<Item = (K, V)>,
        K: Into<String>,
        V: Into<String>;
}

impl<T, E> ContextualExt<T, E> for Result<T, E> {
    fn with_context<K, V>(self, key: K, value: V) -> Result<T, Contextual<E>>
    where
        K: Into<String>,
        V: Into<String>,
    {
        self.map_err(|e| Contextual::new(e).with_context(key, value))
    }

    fn with_context_iter<I, K, V>(self, iter: I) -> Result<T, Contextual<E>>
    where
        I: IntoIterator<Item = (K, V)>,
        K: Into<String>,
        V: Into<String>,
    {
        self.map_err(|e| Contextual::new(e).with_context_iter(iter))
    }
}
```

### The Merge Implementation

This is the critical piece. When `?` propagates a `Contextual<E>` through a function that *also* adds context, we need to merge the maps.

```rust
impl<E> From<Contextual<E>> for Contextual<E> {
    fn from(mut outer: Contextual<E>) -> Self {
        // This `From` impl is never called directly — it's invoked by `?`
        // when the error type matches. But we need a way to merge context
        // from an *inner* Contextual into an *outer* one.
        // 
        // The actual merge happens in the `?` desugaring via a helper trait.
        outer
    }
}

/// Internal trait for merging context during `?` propagation.
/// 
/// We can't implement `From<Contextual<E>> for Contextual<E>` with merge
/// semantics because that would consume the outer error. Instead, the
/// `?` operator calls `From::from` on the *inner* error. So we implement
/// `From<E> for Contextual<E>` where `E: Into<Contextual<_>>` — but that's
/// recursive. The clean solution: a dedicated merge method exposed via
/// a trait that the `?` desugaring can use.
pub trait ContextMerge<E> {
    fn merge_context(self, other: ContextMap) -> Self;
}

impl<E> ContextMerge<E> for Contextual<E> {
    fn merge_context(mut self, other: ContextMap) -> Self {
        // Outer context wins on collision — it's more specific.
        self.ctx.extend(other);
        self
    }
}

/// This is the actual `From` impl that `?` uses when propagating
/// `Contextual<E>` through a function returning `Result<_, Contextual<E>>`.
impl<E, Inner> From<Inner> for Contextual<E>
where
    Inner: Into<Contextual<E>>,
{
    fn from(inner: Inner) -> Self {
        inner.into()
    }
}
```

Wait — that `From` impl is too broad and causes coherence issues. Let me show the *actual* production pattern we use:

```rust
/// Marker trait for errors that can carry context.
/// Implemented automatically for all `E` via blanket impl.
pub trait ContextCarrier: Sized {
    type Contextual: ContextualAccess<Inner = Self>;
    
    fn contextual(self) -> Self::Contextual;
}

impl<E> ContextCarrier for E {
    type Contextual = Contextual<E>;
    
    fn contextual(self) -> Self::Contextual {
        Contextual::new(self)
    }
}

/// Trait for accessing the inner error and context map.
/// Allows generic code to work with any contextual wrapper.
pub trait ContextualAccess {
    type Inner;
    fn inner(&self) -> &Self::Inner;
    fn context(&self) -> &ContextMap;
    fn into_parts(self) -> (Self::Inner, ContextMap);
}

impl<E> ContextualAccess for Contextual<E> {
    type Inner = E;
    fn inner(&self) -> &E { &self.inner }
    fn context(&self) -> &ContextMap { &self.ctx }
    fn into_parts(self) -> (E, ContextMap) { (self.inner, self.ctx) }
}

/// The key insight: `?` uses `From` on the *error type*.
/// If our function returns `Result<T, Contextual<AppError>>`,
/// and we `?` a `Result<U, Contextual<DbError>>`, we need:
/// `From<Contextual<DbError>> for Contextual<AppError>`
/// 
/// But we can't implement that generically (orphan rule).
/// Solution: require the application error to implement a conversion
/// that merges context.

pub trait IntoContextual<Target> {
    fn into_contextual(self, target_ctx: ContextMap) -> Target;
}

impl<E, T> IntoContextual<Contextual<T>> for Contextual<E>
where
    T: From<E>,
{
    fn into_contextual(self, mut target_ctx: ContextMap) -> Contextual<T> {
        // Merge: inner context first, then outer (target) context wins
        target_ctx.extend(self.ctx);
        Contextual::new(T::from(self.inner)).with_context_iter(target_ctx)
    }
}
```

This is getting complex. Let me simplify to what actually works in practice — the pattern we ship:

```rust
// In your application's error module:
#[derive(Debug, thiserror::Error)]
pub enum AppError {
    #[error("database error: {0}")]
    Db(#[from] DbError),
    
    #[error("validation failed: {0}")]
    Validation(String),
    
    #[error("external service error: {0}")]
    External(#[from] Box<dyn std::error::Error + Send + Sync>),
}

// The conversion that enables ? propagation with context merging
impl From<Contextual<DbError>> for Contextual<AppError> {
    fn from(ctx_err: Contextual<DbError>) -> Self {
        let (inner, mut ctx) = ctx_err.into_parts();
        // Convert the inner error
        let app_err = AppError::from(inner);
        // The outer function's context (added via .with_context) 
        // will be merged by the ? desugaring automatically
        Contextual::new(app_err).with_context_iter(ctx)
    }
}
```

The key realization: **you only need one `From` impl per leaf error type**. The mid-layer functions that add context don't need special handling — they just return `Result<T, Contextual<AppError>>` and the `?` operator does the rest.

## Examples & Code Walkthrough

### Complete Working Example

Here's a realistic service layer showing the pattern end-to-end:
