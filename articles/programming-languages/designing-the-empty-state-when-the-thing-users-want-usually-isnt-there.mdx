# Designing the Empty State When the Thing Users Want Usually Isn't There

## Introduction
Most tutorials show the happy path: a function returns a value, you use it, and the program moves on. In production, the opposite is far more common—requests come back empty, caches miss, users have no profile, or a sensor reports nothing. Treating that emptiness as an exception or a null check scatters business logic across guard clauses and makes the code harder to reason about. I learned this the hard way when a `NullPointerException` erupted in a service that was supposed to guarantee a non‑null user object. The fix wasn’t adding another null check; it was redesigning the type system to make the “nothing” case a first‑class domain state.

## Why This Matters
When absence is modeled poorly, you pay the price in three ways:
1. **Runtime bugs** – missed null checks lead to crashes that are hard to reproduce in testing.
2. **Cognitive load** – developers must constantly ask “could this be null?” instead of focusing on the domain.
3. **API fragility** – callers cannot rely on the type signature to tell them what states are possible, so documentation falls out of sync.

By treating the empty state as a distinct, enumerable possibility, you get compile‑time guarantees that every case is handled, and you make the intent of the API explicit to anyone reading the code.

## How It Works
The core idea is to replace ad‑hoc nulls or zero values with a sum type that explicitly lists every way a value can be absent. In languages with algebraic data types (ADTs) this is a natural `enum`. In languages without built‑in sum types you can emulate them with sealed interfaces, discriminated unions, or a combination of `Option` and custom error types.

The diagram below shows how a simple `Option<T>` flows into a richer domain model that distinguishes *why* a value is missing.

```mermaid
flowchart TD
    A[Request for UserProfile] --> B{Result from Service}
    B -->|Some(profile)| C[Ready State]
    B -->|None| D{Why None?}
    D -->|Cache miss| E[Empty: NotFound]
    D -->|User deleted| F[Empty: Revoked]
    D -->|Account pending| G[Empty: PendingVerification]
    C --> H[Render Profile]
    E --> I[Show “Not Found” UI]
    F --> J[Show “Account Deleted” UI]
    G --> K[Show “Verifying…” UI]
```

**Step‑by‑step:**
1. The service returns an `Option<UserProfile>`.  
2. Instead of immediately pattern‑matching on `Some`/`None`, we lift the `None` into a domain‑specific enum (`ProfileAvailability`).  
3. Each variant carries the reason for absence, enabling the UI to render distinct messages without extra boolean flags.  
4. Because the enum is exhaustive, the compiler forces a match on every case; forgetting a branch is a build error.

## Core Concepts
- **Sum type (ADT)** – a type that can be exactly one of several variants. `Option<T>` is the simplest sum type with two variants.
- **Exhaustiveness checking** – the compiler verifies that a match expression covers all variants; missing a case yields an error.
- **Niche optimization** – compilers can store the `None` variant in unused bit patterns of the underlying representation, making `Option<T>` as cheap as a raw pointer.
- **Domain‑driven emptiness** – instead of a generic “missing” state, you define what “missing” means in your business context (e.g., `NotFound`, `Revoked`, `PendingVerification`).

## Examples & Code Walkthrough
Below are two complete, production‑style snippets that illustrate the pattern in Rust (backend) and TypeScript (frontend). Both are deliberately realistic: they include error handling, comments, and a small amount of boilerplate to show how the type integrates with existing code.

### Rust – A Cursor that Encodes Empty Reasons
```rust
use std::fmt;

/// Why a query might return no rows.
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
enum EmptyReason {
    /// The table exists but the WHERE clause matched nothing.
    NoMatches,
    /// The underlying table was dropped or renamed.
    TableMissing,
    /// The query timed out before any data could be streamed.
    Timeout,
}

/// A lazy iterator that distinguishes between an active stream and a known empty state.
pub enum QueryCursor<T> {
    /// An active source that yields items one by one.
    Streaming(Box<dyn Iterator<Item = T>>),
    /// The query finished with zero items; the reason is preserved for UI/logging.
    Empty { reason: EmptyReason },
}

impl<T> Iterator for QueryCursor<T> {
    type Item = T;

    fn next(&mut self) -> Option<Self::Item> {
        match self {
            QueryCursor::Streaming(iter) => iter.next(),
            QueryCursor::Empty { .. } => None, // always yields None
        }
    }
}

impl<T> QueryCursor<T> {
    /// Consumes the cursor and returns the reason if it was empty.
    pub fn empty_reason(self) -> Option<EmptyReason> {
        match self {
            QueryCursor::Empty { reason } => Some(reason),
            QueryCursor::Streaming(_) => None,
        }
    }
}

/* Example usage */
fn run_query() -> QueryCursor<User> {
    // Imagine this talks to a DB; on error we decide the appropriate EmptyReason.
    if table_missing() {
        QueryCursor::Empty { reason: EmptyReason::TableMissing }
    } else if timeout_occurred() {
        QueryCursor::Empty { reason: EmptyReason::Timeout }
    } else {
        let rows = fetch_rows(); // returns an Iterator<Item=User>
        QueryCursor::Streaming(Box::new(rows))
    }
}

/* In a service layer */
fn handle_request() -> HttpResponse {
    let cursor = run_query();
    match cursor.empty_reason() {
        Some(EmptyReason::NoMatches) => HttpResponse::Ok().json(vec![]),
        Some(EmptyReason::TableMissing) => {
            error!("Database schema mismatch");
            HttpResponse::InternalServerError().finish()
        }
        Some(EmptyReason::Timeout) => {
            warn!("Query timed out");
            HttpResponse::GatewayTimeout().finish()
        }
        None => {
            // Stream results; collect or pipe directly to the response body.
            let users: Vec<User> = cursor.collect();
            HttpResponse::Ok().json(users)
        }
    }
}
```
**What this gives you:**
- The type system forces you to consider why a query returned nothing.
- The `Iterator` implementation is unchanged for the happy path; callers still use a `for` loop or `.collect()`.
- Adding a new `EmptyReason` variant causes a compile‑time error anywhere you pattern‑match on the cursor without handling it.

### TypeScript – A Discriminated Union for UI Availability
```ts
/** Reasons why a profile might not be displayable. */
type AvailabilityError =
  | { type: 'notFound'; message: string }
  | { type: 'revoked'; message: string }
  | { type: 'pendingVerification'; progress: number }
  | { type: 'forbidden'; policy: string };

/** The shape of data the UI actually needs. */
type Availability<T, E = AvailabilityError> =
  | { state: 'ready'; data: T }
  | { state: 'empty'; reason: E }
  | { state: 'loading'; progress: number } // 0‑100
  | { state: 'error'; error: unknown };

/* Renderer – exhaustiveness is checked by the compiler. */
function renderProfile<T>(avail: Availability<Profile, T>): ReactNode {
  switch (avail.state) {
    case 'ready':
      return <ProfileView data={avail.data} />;
    case 'empty':
      switch (avail.reason.type) {
        case 'notFound':
          return <Alert variant="warning">Profile not found.</Alert>;
        case 'revoked':
          return <Alert variant="danger">This account has been revoked.</Alert>;
        case 'pendingVerification':
          return (
            <ProgressBar
              now={avail.reason.progress}
              label={`Verifying… ${avail.reason.progress}%`}
            />
          );
        case 'forbidden':
          return <Alert variant="secondary">{avail.reason.policy}</Alert>;
      }
    case 'loading':
      return <SkeletonLoader />;
    case 'error':
      return <Alert variant="danger">Something went wrong.</Alert>;
    // No default needed – if we add a new variant, TS will complain
    // that not all branches are covered.
  }
}

/* Example of converting a service Result<Profile, ApiError> into Availability */
function toAvailability(
  result: Result<Profile, ApiError>
): Availability<Profile> {
  if (result.status === 'loading') {
    return { state: 'loading', progress: result.progress ?? 0 };
  }
  if (result.status === 'error') {
    // Map backend errors to our domain reasons.
    switch (result.error.code) {
      case 'PROFILE_NOT_FOUND':
        return { state: 'empty', reason: { type: 'notFound', message: result.error.message } };
      case 'PROFILE_REVOKED':
        return { state: 'empty', reason: { type: 'revoked', message: result.error.message } };
      case 'VERIFICATION_PENDING':
        return {
          state: 'empty',
          reason: { type: 'pendingVerification', progress: result.error.progress ?? 0 },
        };
      case 'FORBIDDEN':
        return {
          state: 'empty',
          reason: { type: 'forbidden', policy: result.error.policy ?? 'access denied' },
        };
      default:
        return { state: 'error', error: result.error };
    }
  }
  // status === 'success'
  return { state: 'ready', data: result.value };
}
```
**Why this works in TS:**
- The `state` discriminant lets the compiler narrow the type in each `switch` case.
- Adding a new `AvailabilityError` variant forces you to update the inner `switch`; forgetting to do so yields a TS error (`Type '"newReason"' is not assignable to type '...'`).
- The UI never sees a raw `null` or `undefined`; all possible presentations are explicit.

## Best Practices
1. **Prefer sum types over nullable pointers** – if your language offers `Option`, `Result`, or sealed unions, use them as the primary way to model absence.
2. **Enrich the `None` variant with domain context** – instead of a bare `None`, carry an enum that explains why the value is missing. This turns a control‑flow concern into data that can be logged, audited, or presented to the user.
3. **Leverage exhaustiveness checks** – write your pattern matches so that the compiler will error if you forget a case. Treat those errors as documentation reminders.
4. **Keep the representation cheap** – rely on niche optimizations (most compilers do this automatically for `Option<&T>` or `Option<NonZeroU64>`). Avoid wrapping the sum type in additional heap allocations unless you truly need dynamic dispatch.
5. **Document the meaning of each variant** – a short comment beside each enum case saves future maintainers from guessing whether `EmptyReason::Timeout` refers to a network timeout or a query timeout.

## Common Mistakes & Anti-Patterns
| Mistake | Why it’s harmful | Fix |
|---------|------------------|-----|
| **Using `null` as a catch‑all for “missing”, “zero”, and “error”.** | Callers cannot distinguish the cases, leading to brittle conditionals and silent bugs. | Replace `T | null` with `Option<T>` and, if needed, a richer `Result<T, E>` or custom enum. |
| **Providing a default instance via `Default`/`empty()` and treating it as a real value.** | The type system thinks you have a valid object, so you lose the ability to enforce handling of the empty case. | Keep the empty state as a distinct variant; if you need a neutral object for APIs, wrap it in `Some(neutral)` rather than collapsing the variants. |
| **Floating boolean flags alongside an `Option` (e.g., `isLoading` + `data: Option<T>`).** | The flags can become inconsistent with the actual data source, creating impossible states. | Encode loading, error, and empty states directly in the sum type (see `Availability<T,E>`). |
| **Ignoring the compiler’s exhaustiveness warnings.** | Over time, new variants are added and old match expressions silently miss them, causing runtime surprises. | Treat exhaustiveness warnings as errors in your CI build (`#![deny(non_exhaustive_omitted_patterns)]` in Rust, `strict` TS settings). |
| **Heap‑allocating the sum type unnecessarily (e.g., `Box<Option<T>>` in Rust).** | Adds an extra indirection and allocation for no benefit. | Use the plain enum; the compiler will optimize the layout. |

## Performance Considerations
- **Memory:** `Option<T>` for pointer-sized `T` has the same size as `T` itself because the compiler uses the null pointer niche. For non‑pointer types, the size is `size_of::<T>() + 1` byte (the discriminant), which is still minimal.
- **CPU:** Branching on the discriminant is a single integer comparison; modern CPUs predict this well when one variant dominates (common in hot paths). The overhead is negligible compared to the cost of a cache miss or a network round‑trip.
- **Allocation:** As shown in the `QueryCursor` example, the active variant can hold a boxed iterator only when needed; the empty variant holds only a discriminant and a small enum, avoiding heap allocation.
- **Scalability:** Because the empty state is data, not control flow, you can propagate it through pipelines, batch processes, or distributed systems without accumulating nested `if` checks. The resulting code is easier to parallelize and reason about under back‑pressure.

## Frequently Asked Questions (FAQ)
**Q: Isn’t wrapping everything in an `Option` just moving the null check from runtime to compile time?**  
A: It moves the *decision* about what to do with the missing case into the type system. You still write a branch, but the compiler guarantees you won’t forget a case, and the branch can carry meaningful data (e.g., a reason code) instead of a bare `nil`.

**Q: My language doesn’t have algebraic data types—how can I get this benefit?**  
A: You can emulate them with:
- Interfaces + sealed classes (Java, C#),
- Discriminated unions (TypeScript, F#),
- A pair of values (`T`, `bool hasValue`) plus a strict linter that forbids direct access without checking the flag,
- Or a library that provides `Option`/`Result` types (e.g., `vavr` for Java, `option-t` for Haskell).

**Q: Won’t adding extra variants make my APIs harder to consume?**  
A: The opposite—consumers get a self‑documenting contract. Instead of guessing what `null` means, they read the enum variants and know exactly which situations to handle. IDE auto‑completion also lists the cases, reducing lookup time.

**Q: How do I deal with legacy code that already uses nulls?**  
A: Introduce a thin translation layer at the boundaries. For example, a wrapper function that converts `null` → `None` and non‑null → `Some(value)`. Over time, migrate internal callers to use the wrapper directly, and let the compiler guide you to eliminate the remaining raw pointer checks.

**Q: Does this approach increase binary size?**  
A: Not significantly. The discriminant is usually a single byte, and many compilers lay out the variants to reuse existing memory layout (niche optimization). In practice, the size impact is dwarfed by the benefits of safer code.
