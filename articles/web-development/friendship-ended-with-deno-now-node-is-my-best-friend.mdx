# Friendship ended with Deno, now Node is my best friend

## Introduction

Last Tuesday, our staging cluster threw a cryptic ImportError at 3 AM. The culprit? A Deno prototype that worked on my laptop but failed in Docker because the `std/http` module resolution behaved differently under Linux. After six months of fighting the runtime, we pulled the plug and migrated to Node.js. This isn't a Deno hate post—it's a postmortem on why Node remains the safer bet for production web services in 2024.

## Why This Matters

When you're running a production API handling 10k RPS, you don't care about theoretical purity. You care about whether your on-call engineer can find a Stack Overflow answer at 2 AM. Node's ecosystem means every edge case has been documented, every native addon has bindings, and your CI pipeline doesn't need custom runtime hacks. The cost of debugging a Deno-specific race condition in async pipelines often exceeds the development speed gains from its zero-config setup.

## How It Works

Node's module resolution follows the CommonJS and ESM specifications, looking in `node_modules` directories up the file tree. When you use `import { createServer } from 'node:http'`, Node bypasses the file system and returns the built-in C++ binding directly. This differs from Deno's approach of fetching modules from URLs or local std paths at runtime. The `node:` protocol acts as a namespace guard, ensuring you're importing the runtime's native implementation rather than an npm package with the same name.
