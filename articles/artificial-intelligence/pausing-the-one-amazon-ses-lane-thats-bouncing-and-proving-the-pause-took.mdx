# Pausing the one Amazon SES lane that's bouncing, and proving the pause took

## Introduction
During a recent incident in our production cluster we observed a single Amazon SES lane start bouncing at a 15% rate. The bounce storm threatened to exhaust our sending quota and damage our sender reputation. Instead of throttling the entire service, we isolated the problematic lane, paused its outbound traffic, and verified that the pause actually took effect. This article shows how we built that safety net and what you can learn to avoid similar outages.

## Why This Matters
Email delivery is a critical path for many services, and a bounce storm can quickly cascade into higher costs, throttling, and loss of trust. By pausing only the lane that is misbehaving, you contain the problem while keeping other lanes operational. The ability to prove that the pause succeeded gives you confidence to resume traffic once the issue is resolved.

## How It Works
Our solution consists of three core pieces:

1. **Metric collector** – a lightweight service that reads the bounce‑rate metric for each SES lane from CloudWatch on a short interval.
2. **Pause controller** – a Lambda function that flips a pause flag in a central store (DynamoDB) when the bounce‑rate exceeds a configurable threshold.
3. **Verification worker** – another Lambda that reads the flag and confirms that no new send requests have been issued for the lane, emitting a success or failure event to CloudWatch.

The flow looks like this:

```mermaid
flowchart TD
    A[SES Lane] --> B[CloudWatch Bounce Metric]
    B --> C{Metric Collector}
    C -->|BounceRate > Threshold| D[Pause Controller Lambda]
    D --> E[Write Pause Flag to DynamoDB]
    E --> F[SES Sending API (check flag before sending)]
    F --> G[Verification Worker Lambda]
    G --> H[Read Pause Flag from DynamoDB]
    H --> I{Flag Set?}
    I -->|Yes| J[Emit Verification Success to CloudWatch]
    I -->|No| K[Emit Verification Failure to CloudWatch]
```

### Step‑by‑step technical explanation
1. **Metric collection** – The collector runs every 30 seconds, fetches the `BounceRate` metric for each dedicated sending lane, and writes the latest value to a local in‑memory map. If a lane’s rate exceeds `MAX_BOUNCE_RATE` for three consecutive samples, it flags the lane for pause.
2. **Pause decision** – The controller Lambda reads the flag map, then writes a `paused = true` entry for the lane into DynamoDB under the key `ses-lane-{lane-id}`. The write includes a timestamp and the reason, enabling auditability.
3. **Sending gating** – All outbound SES calls go through a wrapper function. Before invoking `client.send_email`, it checks the pause flag in DynamoDB. If the flag is true, the call is skipped and a metric `PausedSesLane` is incremented.
4. **Verification** – The verification worker polls the same flag every minute. If the flag remains set for a configurable “settling period” (e.g., 2 minutes) and no new send requests are observed, it publishes a `PauseVerified` event. Otherwise it logs a failure.

## Core Concepts
- **Lane** – In SES, a lane is identified by a dedicated sending domain or a specific configuration set. We treat each lane as an independent logical queue.
- **Pause flag** – A boolean value stored in DynamoDB. It is the single source of truth for “pause” state.
- **Idempotent verification** – The verification Lambda is designed to be safe to run repeatedly; it only reads the flag and does not modify state.
- **Back‑pressure** – The collector respects CloudWatch’s 1‑minute metric resolution to avoid throttling the API.

## Examples & Code Walkthrough

### 1. Metric collector (Python)

```python
import boto3
import time
from collections import defaultdict

cloudwatch = boto3.client('cloudwatch')
DYNAMO = boto3.resource('dynamodb')
TABLE = DYNAMO.Table('ses-lane-pause-flags')

MAX_BOUNCE_RATE = 0.10   # 10%
SAMPLE_COUNT = 3
INTERVAL = 30  # seconds

def fetch_bounce_rate(lane_id: str) -> float:
    end_time = int(time.time())
    start_time = end_time - 60  # last minute
    response = cloudwatch.get_metric_statistics(
        Namespace='AWS/SES',
        MetricName='BounceRate',
        Dimensions=[
            {'Name': 'SentWith', 'Value': lane_id},
            {'Name': 'SubmissionType', 'Value': 'API'}
        ],
        StartTime=start_time,
        EndTime=end_time,
        Period=60,
        Statistics=['Average']
    )
    # CloudWatch returns a list; we take the first datapoint
    datapoints = response['Datapoints']
    if not datapoints:
        return 0.0
    return float(datapoints[0]['Average'])

def main_loop():
    # In‑memory map of latest rates per lane
    rates = defaultdict(float)

    while True:
        for lane in get_all_lanes():  # implementation omitted for brevity
            rate = fetch_bounce_rate(lane)
            rates[lane] = rate
            # Store raw rate in DynamoDB for audit (optional)
        # Evaluate pause condition
        for lane, rate in rates.items():
            if rate > MAX_BOUNCE_RATE:
                # count consecutive exceedances
                if not hasattr(main_loop, 'exceed_counts'):
                    main_loop.exceed_counts = {}
                counts = main_loop.exceed_counts.setdefault(lane, 0)
                counts += 1
                if counts >= SAMPLE_COUNT:
                    TABLE.update_item(
                        Key={'lane_id': lane},
                        UpdateExpression='SET #f = :paused, #t = :timestamp',
                        ExpressionAttributeNames={'#f': 'paused', '#t': 'updated_at'},
                        ExpressionAttributeValues={':paused': True, ':timestamp': int(time.time())}
                    )
                    print(f'Pausing lane {lane} due to bounce rate {rate:.2%}')
        time.sleep(INTERVAL)

if __name__ == '__main__':
    main_loop()
```

### 2. Pause controller (AWS Lambda, Python)

```python
import json
import boto3
import os

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table(os.environ['PAUSE_TABLE'])

def lambda_handler(event, context):
    # Event format: {"lane_id": "my-lane-123"}
    lane_id = event['lane_id']
    try:
        table.update_item(
            Key={'lane_id': lane_id},
            UpdateExpression='SET #p = :paused, #u = :updated',
            ExpressionAttributeNames={'#p': 'paused', '#u': 'updated_at'},
            ExpressionAttributeValues={':paused': True, ':updated': int(time.time())}
        )
        return {'status': 'paused', 'lane': lane_id}
    except Exception as e:
        # Log and re‑raise so the monitoring system can react
        print(f'Failed to pause lane {lane_id}: {e}')
        raise
```

The Lambda is triggered by the CloudWatch metric alarm that fires when the collector flags a lane.

### 3. Verification worker (Python Lambda)

```python
import boto3
import time
import os

dynamodb = boto3.resource('dynamodb')
table = dynamodb.Table(os.environ['PAUSE_TABLE'])
cloudwatch = boto3.client('cloudwatch')

VERIFY_WINDOW = 120  # seconds to wait after pause
CHECK_INTERVAL = 30

def lambda_handler(event, context):
    lane_id = event['lane_id']
    start = time.time()
    while time.time() - start < VERIFY_WINDOW:
        resp = table.get_item(Key={'lane_id': lane_id})
        if 'Item' not in resp or not resp['Item'].get('paused'):
            # still active, keep waiting
            time.sleep(CHECK_INTERVAL)
            continue

        # Ensure no new send calls have been made
        # We check a dedicated CloudWatch metric emitted by the sending wrapper
        metric = cloudwatch.get_metric_statistics(
            Namespace='Custom/SES',
            MetricName='SendCalls',
            Dimensions=[{'Name': 'Lane', 'Value': lane_id}],
            StartTime=datetime.utcfromtimestamp(start - 60),
            EndTime=datetime.utcfromtimestamp(time.time()),
            Period=60,
            Statistics=['Sum']
        )
        if any(datapoint['Sum'] > 0 for datapoint in metric['Datapoints']):
            # still sending – verification fails
            cloudwatch.put_metric_data(
                Namespace='Custom/SES',
                MetricData=[{'MetricName': 'PauseVerificationFailed', 'Value': 1, 'Unit': 'Count'}]
            )
            return {'status': 'failed', 'lane': lane_id}
        else:
            # no new sends observed
            cloudwatch.put_metric_data(
                Namespace='Custom/SES',
                MetricData=[{'MetricName': 'PauseVerificationSucceeded', 'Value': 1, 'Unit': 'Count'}]
            )
            return {'status': 'verified', 'lane': lane_id}
    # Timeout – treat as failure
    cloudwatch.put_metric_data(
        Namespace='Custom/SES',
        MetricData=[{'MetricName': 'PauseVerificationTimeout', 'Value': 1, 'Unit': 'Count'}]
    )
    return {'status': 'timeout', 'lane': lane_id}
```

The wrapper that sends emails (see below) increments a custom metric `SendCalls` with the lane dimension, enabling the verification step to confirm the pause.

### 4. Sending wrapper (Python)

```python
import boto3
import os
import time
from botocore.exceptions import ClientError

ses = boto3.client('ses')
TABLE = boto3.resource('dynamodb').Table(os.environ['PAUSE_TABLE'])

def should_send(lane_id: str) -> bool:
    try:
        item = TABLE.get_item(Key={'lane_id': lane_id})
        if item.get('Item', {}).get('paused'):
            return False
        return True
    except ClientError as e:
        print(f'Error reading pause flag for {lane_id}: {e}')
        return True  # fail‑open on read error

def send_email(lane_id: str, message: dict):
    if not should_send(lane_id):
        print(f'Skipping send for lane {lane_id} – pause active')
        return
    try:
        ses.send_email(
            Source=message['source'],
            Destination=message['destination'],
            Message=message['message']
        )
        # Emit metric for verification
        cloudwatch.put_metric_data(
            Namespace='Custom/SES',
            MetricData=[{'MetricName': 'SendCalls', 'Value': 1, 'Unit': 'Count',
                         'Dimensions': [{'Name': 'Lane', 'Value': lane_id}]}
        )
    except ClientError as e:
        print(f'Send failed for lane {lane_id}: {e}')
        raise
```

All three Lambdas are deployed in the same VPC to keep network latency low and to allow IAM roles that grant read/write access to the necessary resources.

## Best Practices
- **Per‑lane isolation** – Keep bounce metrics, pause flags, and send‑call counters separate per lane; this prevents cascade failures.
- **Idempotent writes** – Use conditional updates (`ExpectedCondition`) when writing the pause flag to avoid duplicate entries.
- **Audit trail** – Store the pause timestamp and reason in DynamoDB; surface it via CloudWatch Logs Insights for post‑mortem analysis.
- **Graceful resume** – After the underlying issue resolves, set `paused = false` and let the verification worker confirm the lane is healthy before re‑enabling traffic.
- **Alerting** – Emit a CloudWatch alarm on `PauseVerificationFailed` so the on‑call engineer is notified if the pause cannot be proven.

## Common Mistakes & Anti‑Patterns
| Mistake | Why it hurts | Fix |
|---------|--------------|-----|
| Pausing the whole SES service instead of a single lane | Loses all email capability, impacts other customers | Scope the flag to the specific lane identifier; use separate DynamoDB items. |
| Storing the pause flag only in memory | Loss of state on Lambda restart or scaling event | Persist the flag in a durable store (DynamoDB, Parameter Store). |
| Ignoring CloudWatch metric lag | Verification may report success while sends are still in flight | Use a settling window and verify that no new `SendCalls` appear for the lane. |
| Hard‑coding region or table name | Breaks when moving between environments | Parameterize ARNs, table names, and thresholds via environment variables or SSM. |

## Performance Considerations
- **Collector** runs every 30 seconds; each `get_metric_statistics` call costs ~0.5 USD per month per lane, negligible at scale.
- **Lambda functions** have a typical cold start of < 100 ms; the pause controller and verification worker are lightweight (under 50 ms compute time).
- **DynamoDB** provisioned throughput of 5 RCU/5 WCU per lane is more than sufficient; the write pattern is append‑only, so no hot partitions.
- **Metric resolution** – Using 1‑minute statistics keeps API calls low while still providing timely detection. If sub‑minute detection is required, enable high‑resolution custom metrics.

## Frequently Asked Questions (FAQ)

**Q1: Can I pause a lane without affecting other lanes?**  
A: Yes. The pause flag is scoped to a lane identifier; other lanes continue to send normally because the wrapper checks the flag only for the lane it belongs to.

**Q2: What if the bounce metric is delayed?**  
A: The collector uses a three‑sample consecutive‑exceedance rule to mitigate short spikes. If you need tighter detection, lower `SAMPLE_COUNT` or increase the metric frequency via a custom high‑resolution metric.

**Q3: How do I resume sending after the issue is fixed?**  
A: Update the DynamoDB item to set `paused = false`. The verification worker will automatically confirm the lane is healthy before you re‑enable traffic, or you can manually trigger a “resume” Lambda that clears the flag.

**Q4: Does pausing impact delivery guarantees?**  
A: SES guarantees are per‑lane. Pausing a lane simply stops new send requests for that lane; any messages already in flight will still be delivered unless the service throttles them.

**Q5: Is there a cost to the verification step?**  
A: The verification Lambda reads the pause flag (a single DynamoDB GetItem) and queries a custom metric (negligible). The additional CloudWatch metric writes are minimal.
