# Presentation: Ontology‐Driven Observability: Building the E2E Knowledge Graph at Netflix Scale

## Introduction

Traditional observability relies heavily on metrics, logs, and distributed tracing. Each of these modalities provides valuable signals, but they operate in isolation. When an incident erupts—say, a latency spike affecting checkout flows—engineers often find themselves corralling disparate pieces of evidence to reconstruct causality. That process is time-consuming and error-prone. Our team at Netflix identified a pressing gap: we needed a system capable of constructing an executable map of system behavior that could answer not just *what* happened, but *why* across service boundaries simultaneously.

The solution emerged as an ontology‑driven knowledge graph. By treating every observable entity as a node and every relationship between those entities as an edge governed by formal semantics, we can build a living model that evolves alongside the system. This approach transforms raw telemetry into structured knowledge that supports automated diagnosis, predictive alerting, and cross‑service dependency analysis at scale.

## Why This Matters

Observability at modern cloud scale faces three concrete challenges. First, event volume grows exponentially with deployment frequency; a single request may generate dozens of log entries, trace spans, and metric samples per second. Processing this stream linearly is unsustainable. Second, correlated failures rarely stay within a single microservice boundary—they cascade through shared databases, message queues, and API gateways. Third, debugging requires context that spans multiple pipelines, making manual correlation effortful. 

An ontology layer solves these problems by providing a unified vocabulary and inference engine. Instead of parsing unstructured text from logs, we extract structured facts and bind them to stable identifiers. The resulting graph enables deductive reasoning: if a user session shows high error rates, the graph can automatically discover which downstream service is likely responsible based on relationship weights rather than ad‑hoc hypothesis testing. This reduces mean time to resolution from hours to minutes while preserving auditability.

## How It Works

Our implementation follows a four‑stage pipeline: event collection, ontological normalization, graph construction, and semantic querying. Below is the core architecture visualized.

### Step‑by‑Step Mechanism

1. **Event Collection** – Every service emits enriched events containing a unique identifier (`event_id`), a timestamp, and contextual attributes such as request IDs, user IDs, and topology labels. These events land on partitioned Kafka topics keyed by service name.

2. **Normalization** – A streaming processor runs three parallel steps. The *Triple Extractor* parses each log line using a configurable rule set and emits RDF triples in the form `<entity> <predicate> <object>`. The *Schema Validator* checks each triple against an OWL‑style ontology defined upfront; invalid triples are routed to a quarantine bucket for manual review. Finally, the *Entity Registry* materializes persistent representations of services, databases, and user cohorts as first‑class nodes.

3. **Graph Construction** – The *Node Adapter* creates `OntologyNode` objects for each distinct entity, assigning logical types such as `Service`, `Database`, `UserSession`, or `ExternalAPI`. Concurrently, the *Relation Classifier* examines incoming triples and assigns relationship types (`INVOKES`, `DEPENDS_ON`, `OWNED_BY`). Edges are stored in a directed multi‑graph format, allowing multiple paths between the same pair of nodes.

4. **Querying** – Business analysts or automation pipelines issue SPARQL‑compatible queries against the graph. The *Query Engine* traverses paths weighted by inferred strengths, returning aggregated statistics, failure propagation chains, and root cause hypotheses. Results are cached in Redis to amortize expensive graph traversals during peak load.

## Core Concepts

The foundation of the system rests on three interlocking concepts.

### Ontology Definition

Before any telemetry flows into the store, we define a machine‑readable schema using OWL‑RL extensions. Nodes carry properties like `capacity`, `latency_budget`, and `dependency_hierarchy`. Relationships inherit types such as `CausesFailure`, `RoutesRequest`, or `ManagesData`. This schema drives validation, prevents inconsistent state, and guides the inference algorithm.

### Triple Storage and Inference

Each atomic observation becomes an RDF triple. To support reasoning over transitive closures—such as recognizing that a database outage caused service degradation because both depend on the same shard—we run a lightweight forward chaining inference engine nightly. The engine propagates known facts through the graph, expanding the effective reach of individual observations without requiring linear scan over every possible path.

### Temporal Alignment

Observations arrive at different times relative to system state. Our temporal index maps each event to a normalized timeline, aligning occurrences across services that may have clock skew. This ensures that causal links respect chronological order before being applied to the graph.
