# How I Built a 60fps Flutter E-Commerce App with Clean Architecture in Kannur

## Introduction

We built a Flutter e‑commerce app that stays at 60 frames per second while handling product listings, cart updates, and payment flows. The challenge was to keep UI smooth under heavy data loads and intermittent network conditions in a region with variable connectivity.

## Why This Matters

Engineers often face jank when rendering large catalogs or when network latency spikes. Maintaining a responsive UI without sacrificing architectural clarity is a practical pain point that directly impacts user retention and conversion rates.

## How It Works

Below is the high‑level flow of requests and data transformations.

```mermaid
flowchart TD
    A[Flutter UI] --> B[Presentation Layer (Bloc)]
    B --> C[Domain Layer (Use Cases)]
    C --> D[Data Layer (Repository)]
    D --> E[Remote Data Source (REST API)]
    D --> F[Local Data Source (SQLite)]
    E --> G[Network Interceptor]
    G --> H[Response Parsing]
    H --> I[Cache Update]
    I --> D
    D --> J[UI Refresh]
    J --> A
```

The diagram shows the unidirectional flow enforced by the Bloc pattern. The UI never talks directly to the repository; instead it receives state objects from the Bloc, which are produced by the use‑case class. The repository abstracts both remote and local sources, allowing the same code path to handle offline scenarios.

## Core Concepts

- **Clean Architecture**: separates concerns into presentation, domain, and data layers. Each layer depends only on the layer directly inward, preventing circular dependencies.
- **Bloc**: a state‑management library that enforces a single source of truth for UI state. Events flow into the Bloc, which emits new states based on business logic.
- **Repository Pattern**: defines an abstract contract for data access. Concrete implementations handle remote APIs, local DB, and caching.
- **Domain Model**: immutable data classes that represent core business entities such as Product, Cart, and Order.
- **Error Handling**: a unified `AppError` enum with `network`, `validation`, and `internal` categories. All async functions return either a success value or an error, never throw uncaught exceptions.

```dart
import 'package:meta/meta.dart';

abstract class GetProductListUseCase {
  Future<List<Product>> call();
}

class GetProductListUseCaseImpl implements GetProductListUseCase {
  final ProductRepository repository;

  GetProductListUseCaseImpl(this.repository);

  @override
  Future<List<Product>> call() async {
    try {
      return await repository.fetchProductList();
    } on AppError catch (e) {
      // Convert repository‑specific errors to domain‑level errors
      throw e;
    }
  }
}
```

### Data Layer – Repository Implementation

```dart
// product_repository_impl.dart
import 'dart:async';
import 'package:http/http.dart' as http;
import 'package:your_app/domain/entities/product.dart';
import 'package:your_app/domain/repositories/product_repository.dart';
import 'package:your_app/data/sources/remote_product_source.dart';

class ProductRepositoryImpl implements ProductRepository {
  final RemoteProductSource remoteSource;
  final LocalProductSource localSource;

  ProductRepositoryImpl(this.remoteSource, this.localSource);

  @override
  Future<List<Product>> fetchProductList() async {
    // 1. Try cache first
    final cached = await localSource.getCachedList();
    if (cached != null) {
      // Refresh background
      _refreshFromNetwork();
      return cached;
    }

    // 2. Fetch from network
    final response = await remoteSource.getProductList();
    if (response.statusCode == 200) {
      final products = response.body;
      await localSource.saveProductList(products);
      return products;
    } else {
      throw AppError.network('Server returned ${response.statusCode}');
    }
  }

  void _refreshFromNetwork() async {
    try {
      final response = await remoteSource.getProductList();
      if (response.statusCode == 200) {
        await localSource.saveProductList(response.body);
      }
    } catch (_) {
      // Swallow network errors; cached data remains valid
    }
  }
}
```

### Presentation Layer – Bloc

```dart
// product_list_bloc.dart
import 'package:bloc/bloc.dart';
import 'package:your_app/domain/usecases/get_product_list_use_case.dart';
import 'package:your_app/domain/entities/product.dart';

enum ProductListEvent { fetch }

class ProductListBloc extends Bloc<ProductListEvent, List<Product>> {
  final GetProductListUseCase useCase;

  ProductListBloc(this.useCase) : super([]) {
    on<_fetch>(_onFetch);
  }

  Future<void> _onFetch(_fetch event, Emitter<List<Product>> emit) async {
    emit([]); // loading state could be handled separately
    final products = await useCase();
    emit(products);
  }
}
```

### UI – ListView with Automatic Refresh

```dart
class ProductListPage extends StatelessWidget {
  const ProductListPage({Key? key}) : super(key: key);

  @override
  Widget build(BuildContext context) {
    final bloc = context.read<ProductListBloc>();
    return BlocBuilder<ProductListBloc, List<Product>>(
      builder: (context, products) {
        return Scaffold(
          appBar: AppBar(title: const Text('Kannur Market')),
          body: ListView.builder(
            itemCount: products.length,
            itemBuilder: (_, index) => _buildItem(products[index]),
          ),
        );
      },
    );
  }

  Widget _buildItem(Product product) {
    return Card(
      margin: const EdgeInsets.all(8),
      child: ListTile(
        leading: Image.network(product.imageUrl),
        title: Text(product.name),
        subtitle: Text('\$${product.price}'),
        trailing: IconButton(
          icon: const Icon(Icons.add_shopping_cart),
          onPressed: () => _addToCart(product),
        ),
      ),
    );
  }

  void _addToCart(Product product) {
    // Simple cart provider example
    CartProvider.of(context).add(product);
  }
}
```

## Best Practices

1. **Keep the UI thin** – let the Bloc handle loading, error, and data states. UI widgets should only react to state changes.  
2. **Use immutable models** – `freeze` data classes to avoid accidental mutation that can cause jank.  
3. **Batch network calls** – debounce rapid user actions (e.g., scrolling) to reduce unnecessary requests.  
4. **Cache aggressively** – store JSON responses in SQLite with a TTL; fall back to cached data when offline.  
5. **Test at every layer** – unit test use cases, widget test Bloc events, and integration test the full flow with a mock server.

## Common Mistakes & Anti-Patterns

| Mistake | Why It Fails | Fix |
|---------|--------------|-----|
| Directly calling the repository from UI widgets | Breaks separation of concerns and makes testing hard | Introduce a Bloc or Provider that mediates all data access |
| Throwing uncaught exceptions in async code | Crashes the app and hides error context | Wrap calls in `try/catch` and emit an error state via Bloc |
| Storing large images in memory | Causes GC spikes and frame drops | Load images with `Image.network` and use `FadeInImage` with placeholders |
| Ignoring network timeouts | UI freezes when the server is slow | Set a timeout on `http` client and show a retry UI |

## Performance Considerations

- **CPU**: The Bloc processes events on the main isolate; heavy JSON parsing should be moved to a background isolate to keep 60 fps.  
- **Memory**: SQLite cache size limited to 5 MB per product list; monitor with `dart:developer` timeline.  
- **Network**: Use HTTP/2 multiplexing and compress payloads with Gzip; set `Connection: keep-alive` to reduce handshake overhead.  
- **Big‑O**: The list‑fetch operation is O(n) for parsing and O(1) for cache lookup, which is optimal for UI rendering.

## Frequently Asked Questions (FAQ)

**Q1: How do I handle offline cart updates?**  
A: Store cart items in SQLite with a transaction. When the device regains connectivity, dispatch a `syncCart` event that posts each pending item to the server and removes it locally on success.

**Q2: Is Bloc overkill for a small app?**  
A: Not if you anticipate growth. The extra layer prevents the “spaghetti” code that appears when UI directly manipulates data models.

**Q3: Can I replace SQLite with Hive?**  
A: Yes. The repository contract stays the same; only the concrete `LocalProductSource` implementation changes.
