# Automated Accessibility Testing at Slack

## Introduction
Slack has grown from a small team chat tool to a platform used by millions worldwide. The diversity of our user base demands that every interface be perceivable, operable, understandable, and robust. When a new feature ships without accessibility checks, we risk excluding users and violating compliance mandates. This article describes the production‑grade pipeline we built to catch accessibility issues early, automatically, and at scale.

## Why This Matters
Accessibility is not a nice‑to‑have; it is a legal requirement under WCAG 2.1 AA and internal policy. Manual QA cannot keep pace with the frequency of UI changes in a micro‑service environment. Automated testing provides immediate feedback to developers, reduces regressions, and keeps our CI pipeline healthy. The result is a more inclusive product and fewer post‑release hotfixes.

## How It Works
Our solution consists of a lightweight test runner that launches a headless browser, injects the open‑source axe‑core engine, and returns a structured report. The runner is orchestrated by a CI job that triggers on pull‑request merges or nightly schedules. Violations cause the job to fail, surface details in a dashboard, and push alerts to a Slack channel.

```mermaid

    FE[Slack Frontend (React)] --> CI[CI Pipeline (GitHub Actions)]

The axe library scans the rendered DOM, produces a JSON payload, and the report generator converts it into human‑readable HTML while also emitting a concise JSON summary for CI consumption. A dashboard aggregates results over time, and a webhook notifies the responsible team when a build fails.

## Core Concepts
- **Modularity** – The runner, browser driver, axe integration, and reporting are separate modules, making the codebase easy to extend.
- **Extensibility** – Rule sets can be swapped or augmented with custom assertions that reflect Slack‑specific accessibility policies.
- **Determinism** – Snapshot‑based UI testing and fixed viewport sizes guarantee reproducible builds across CI runners.
- **Observability** – Structured logs, Prometheus metrics, and Slack webhook alerts give the team visibility into test health and flakiness.

## Examples & Code Walkthrough

### 9.1 Node.js test runner
The following script launches a headless browser, navigates to a Slack page, injects axe‑core, and exits with a non‑zero status if any violation is found. Defensive error handling ensures the CI job fails cleanly.

```js
#!/usr/bin/env node
const puppeteer = require('puppeteer');
const axe = require('axe-core');

async function run() {
  const browser = await puppeteer.launch({ headless: true });
  const page = await browser.newPage();

  try {
    // Replace with the actual URL of the component under test
    await page.goto('https://app.slack.com/client/T00000000/C00000000');

    // Load axe-core into the page context
    await page.addScriptTag({ path: require.resolve('axe-core') });

    // Execute axe and capture results
    const results = await page.evaluate(async () => {
      const axe = window.axe;
      return await axe.run();
    });

    if (results.violations.length > 0) {
      console.error('Accessibility violations detected:');
      results.violations.forEach(violation => {
        console.error(`${violation.id} - ${violation.description}`);
        violation.nodes.forEach(node => {
          console.error('  →', node.target.join(', '));
        });
      });
      process.exit(1); // signal failure to CI
    }

    console.log('No accessibility violations found.');
  } catch (err) {
    console.error('Test runner failed:', err);
    process.exit(2);
  } finally {
    await browser.close();
  }
}

run();
```

### 9.2 Cypress custom command
Integrating accessibility checks directly into UI tests keeps the workflow familiar for front‑end engineers.

```js
// cypress/support/commands.js
Cypress.Commands.add('checkA11y', () => {
  // This command runs after a page has been visited
  return page.evaluate(async () => {
    const axe = window.axe;
    const results = await axe.run();
    if (results.violations.length > 0) {
      // Throwing an error makes the test fail
      throw new Error(`Accessibility violations: ${results.violations.length}`);
    }
  });
});
```

Usage in a spec:

```js
describe('Message composer', () => {
  it('should be accessible', () => {
    cy.visit('/editor');
    cy.checkA11y(); // fails the test if any violation exists
  });
});
```

## Best Practices
- **Pin browser version** – Use a Docker image with a fixed Chromium version to avoid flaky rendering differences.
- **Throttle network** – Simulate realistic conditions with `page.emulateNetworkConditions` to surface performance‑related a11y issues.
- **Limit scope** – Run axe on specific routes or components rather than the entire site; this reduces runtime and noise.
- **Persist logs** – Store the JSON report as an artifact in CI so developers can inspect details after a failure.
- **Balance rule coverage** – Start with the WCAG baseline, then add Slack‑specific rules (e.g., focus‑visible, color‑contrast) and prune those that cause excessive false positives.

## Common Mistakes & Anti-Patterns
1. **Running axe on the entire site in CI** – This inflates runtime and drowns developers in noise.  
   *Fix*: Scope the test to the changed route or component using a query selector passed to `axe.run`.

2. **Relying on default axe thresholds** – Some violations are intentional (e.g., decorative images with `aria-hidden`).  
   *Fix*: Write custom assertions that ignore specific nodes or adjust the severity threshold.

3. **Ignoring flaky waiting strategies** – Hard `await page.waitForNavigation()` can cause timeouts when the app loads slowly.  
   *Fix*: Use `await page.waitForSelector('selector=...', { timeout: 10000 })` and retry logic for transient elements.

4. **Not cleaning up browser contexts** – Leaking contexts leads to memory bloat in long‑running CI jobs.  
   *Fix*: Wrap the browser launch in a `try/finally` block and close the browser even on error, as shown in the runner script.

## Performance Considerations
The headless Chromium instance consumes roughly 200 MB of RAM per concurrent test. With a modest CI pool (4 runners), total memory usage stays under 1 GB, well within typical runner limits. CPU usage is dominated by the axe analysis, which is O(N) in the size of the DOM; a typical Slack page (≈5 k nodes) finishes in under 3 seconds. Parallelizing tests across multiple CI jobs linearly reduces overall pipeline time. Caching the browser launcher image and reusing the same context for multiple pages further cuts overhead.

## Frequently Asked Questions (FAQ)

**Q1: Do we need to run axe on every UI test?**  
A: No. We run it on a curated subset of critical flows (e.g., onboarding, message composer) and rely on visual regression tools for the rest. This keeps CI fast while still catching major issues.

**Q2: How do we handle native desktop clients?**  
A: The same axe‑core library can be used via Electron’s `webContents` API. We maintain a separate script that launches the Electron process in headless mode and runs axe against the rendered DOM.

**Q3: What if a violation is false‑positive due to a dynamic component?**  
A: Add a custom rule or a post‑processing filter that excludes nodes matching a known dynamic selector. Document the rationale in the rule configuration file.

**Q4: Can we integrate the results into Storybook?**  
A: Yes. By exposing a Cypress command that runs axe inside Storybook’s test environment, we can surface accessibility metrics alongside component stories.

## Conclusion
Automated accessibility testing at Slack turned a manual, error‑prone process into a reliable, repeatable pipeline that fails fast and informs developers instantly. The approach is portable to any large‑scale web application, and the lessons learned — scope, observability, and deterministic execution — are applicable across the industry.
