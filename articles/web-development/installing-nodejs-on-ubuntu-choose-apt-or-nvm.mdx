# Installing Node.js on Ubuntu: Choose APT or nvm

## Introduction

Node.js runs the build pipelines, CI runners, and production services behind most modern JavaScript ecosystems. On Ubuntu, you have two fundamentally different paths to get it installed: the distribution's APT repository or the community-maintained Node Version Manager (nvm). They solve different problems. APT gives you a system-wide, package-manager-controlled runtime that updates alongside your OS security patches. nvm gives you per-user, per-shell, per-project version isolation. Choosing the wrong one creates friction that compounds across onboarding, CI/CD, and incident response.

I've seen teams waste days debugging "works on my machine" issues because a developer's global `node` binary differed from the CI agent's by a minor patch version. I've also watched ops teams block security updates because a legacy service pinned to Node 14 couldn't tolerate the APT upgrade to Node 18. This article walks through both approaches with production-tested commands, the architectural trade-offs, and the gotchas that only surface at 2 AM during an outage.

## Why This Matters

Version drift isn't theoretical. Native add-ons (think `bcrypt`, `sharp`, `canvas`) compile against specific V8 ABIs. A patch version mismatch between your laptop and your build server breaks `npm install` with cryptic `gyp` errors. Security teams mandate timely CVE patching, but LTS lines (18.x, 20.x, 22.x) have different end-of-life schedules. If your deployment strategy can't switch Node versions atomically, you're either running vulnerable runtimes or blocking deployments.

The choice also dictates your developer experience. APT installs require `sudo` and affect every user on the host—problematic on shared jump boxes or multi-tenant CI runners. nvm installs live in `$HOME/.nvm`, require zero elevated privileges, and let you `nvm use 20` in one terminal tab while `nvm use 18` runs in another. But nvm adds shell initialization overhead (~100-300ms) and doesn't integrate with `apt upgrade` for security patches. You own the update cadence.

## How It Works

The fundamental difference is **ownership of the `node` binary path**. APT places a single `node` binary in `/usr/bin/node`, managed by `dpkg`. nvm manipulates your `PATH` at shell startup, prepending `$NVM_DIR/versions/node/vX.Y.Z/bin` so `node` resolves to whichever version you last activated.

**APT flow**: Package manager owns the binary. Updates happen through the OS patch cycle. You get one version globally. Pinning requires `/etc/apt/preferences.d/` configuration.

**nvm flow**: Shell function intercepts `node`, `npm`, `npx` commands. It rewrites `PATH` dynamically per invocation. Versions live in isolated directories under `~/.nvm/versions/node/`. No system packages modified.

## Core Concepts

### APT Package Anatomy
The `nodejs` Debian package bundles the Node binary, `npm`, and `corepack` into `/usr/bin/`. It declares dependencies on `libc6`, `libstdc++6`, `libicu70` (or whatever ICU version Ubuntu ships). The NodeSource repository (`deb.nodesource.com`) provides newer LTS lines than Ubuntu's default universe repository by building against the target distro's libc.

### nvm Directory Layout
```
~/.nvm/
├── nvm.sh                 # Main entry point, defines nvm() function
├── bash_completion        # Tab completion for nvm commands
├── alias/                 # Named aliases (default, lts/*, etc.)
│   └── default -> v20.12.0
└── versions/node/
    ├── v18.20.0/
    │   ├── bin/node
    │   ├── bin/npm
    │   └── lib/node_modules/
    ├── v20.12.0/
    │   ├── bin/node
    │   ├── bin/npm
    │   └── lib/node_modules/
    └── v21.7.0/
        ├── bin/node
        ├── bin/npm
        └── lib/node_modules/
```

Each version is a complete, independent Node installation. `npm` and `corepack` are bundled per-version. Global packages (`npm install -g`) install into the active version's `lib/node_modules/`.

### Shell Integration Mechanics
nvm doesn't modify your shell's `PATH` permanently. Instead, it defines a shell function named `nvm` that:
1. Lazily loads the real implementation from `$NVM_DIR/nvm.sh` on first invocation
2. Manipulates `PATH` for the current shell process only
3. Sets `NVM_BIN` and `NVM_INC` for build tools that need Node headers

This lazy-loading design keeps shell startup fast—`nvm.sh` only executes when you actually run `nvm`, `node`, `npm`, or `npx` (via shim functions).

## Examples & Code Walkthrough

### APT: Installing a Specific LTS from NodeSource

```bash
#!/usr/bin/env bash
# install-node-apt.sh — Idempotent Node.js 20.x LTS install via NodeSource
# Run with: sudo bash install-node-apt.sh

set -euo pipefail

NODE_MAJOR="${1:-20}"           # Allow override: ./install-node-apt.sh 18
DISTRO="$(. /etc/os-release && echo "${UBUNTU_CODENAME:-$VERSION_CODENAME}")"
KEYRING_PATH="/usr/share/keyrings/nodesource.gpg"
SOURCE_LIST="/etc/apt/sources.list.d/nodesource.list"

log() { printf '\033[1;32m[%s]\033[0m %s\n' "$(date -Is)" "$*"; }
err() { printf '\033[1;31m[%s] ERROR:\033[0m %s\n' "$(date -Is)" "$*" >&2; }

# 1. Prerequisites
log "Installing prerequisites..."
apt-get update -qq
apt-get install -y -qq ca-certificates curl gnupg

# 2. Add NodeSource signing key (de-armored, stored in keyring)
log "Adding NodeSource GPG key for Node ${NODE_MAJOR}.x..."
curl -fsSL "https://deb.nodesource.com/gpgkey/nodesource-repo.gpg.key" \
  | gpg --dearmor -o "${KEYRING_PATH}"

# 3. Configure APT source with signed-by directive
log "Configuring APT repository for ${DISTRO}..."
cat > "${SOURCE_LIST}" <<EOF
deb [signed-by=${KEYRING_PATH}] https://deb.nodesource.com/node_${NODE_MAJOR}.x ${DISTRO} main
# deb-src [signed-by=${KEYRING_PATH}] https://deb.nodesource.com/node_${NODE_MAJOR}.x ${DISTRO} main
EOF

# 4. Install
log "Installing nodejs package..."
apt-get update -qq
apt-get install -y -qq nodejs

# 5. Verify
NODE_VER="$(node -v)"
NPM_VER="$(npm -v)"
log "Node.js ${NODE_VER} installed (npm ${NPM_VER})"

# 6. Optional: pin to prevent accidental major version upgrade
cat > /etc/apt/preferences.d/nodejs-pin <<EOF
Package: nodejs
Pin: release o=NodeSource, n=${DISTRO}, l=NodeSource
Pin-Priority: 1001
EOF
log "Pinned nodejs to NodeSource ${NODE_MAJOR}.x (priority 1001)"
```

**Key details**:
- `set -euo pipefail` makes the script fail fast on errors, unset variables, or pipeline failures
- `signed-by` in the sources list enforces GPG verification without trusting the key globally
- The pin file (priority 1001) ensures `apt upgrade` never pulls a different major version from NodeSource, even if Ubuntu's universe repo has a newer one
- `UBUNTU_CODENAME` fallback handles both Ubuntu and derivatives (Pop!_OS, Mint)

### nvm: Automated Bootstrap for CI/CD Agents

```bash
#!/usr/bin/env bash
# bootstrap-nvm.sh — Install nvm and Node versions for CI runners
# Usage: source bootstrap-nvm.sh [--lts=20] [--also=18,22]

set -euo pipefail

NVM_VERSION="v0.39.7"
NVM_DIR="${HOME}/.nvm"
LTS_VERSION="20"
ALSO_VERSIONS=()

# Parse args
while [[ $# -gt 0 ]]; do
  case $1 in
    --lts=*) LTS_VERSION="${1#*=}" ;;
    --also=*) IFS=',' read -ra ALSO_VERSIONS <<< "${1#*=}" ;;
    *) err "Unknown option: $1"; exit 1 ;;
  esac
  shift
done

log() { printf '\033[1;36m[%s]\033[0m %s\n' "$(date -Is)" "$*"; }

# 1. Install build dependencies for native modules
log "Installing build dependencies..."
sudo apt-get update -qq
sudo apt-get install -y -qq build-essential libssl-dev python3 pkg-config

# 2. Install nvm (non-interactive, no shell rc modification)
log "Installing nvm ${NVM_VERSION}..."
export PROFILE=/dev/null  # Prevent nvm from modifying ~/.bashrc
curl -fsSL "https://raw.githubusercontent.com/nvm-sh/nvm/${NVM_VERSION}/install.sh" | bash

# 3. Load nvm into current shell
# shellcheck source=/dev/null
[ -s "${NVM_DIR}/nvm.sh" ] && \. "${NVM_DIR}/nvm.sh"

# 4. Install requested versions
log "Installing Node LTS ${LTS_VERSION}..."
nvm install "lts/${LTS_VERSION}"

for ver in "${ALSO_VERSIONS[@]}"; do
  log "Installing Node ${ver}..."
  nvm install "${ver}"
done

# 5. Set default alias
nvm alias default "lts/${LTS_VERSION}"

# 6. Verify all installed versions
log "Installed versions:"
nvm list

# 7. Output shell snippet for persistence (CI can eval this)
cat <<'EOF'

# Add to your shell RC file (~/.bashrc, ~/.zshrc, or CI config):
export NVM_DIR="$HOME/.nvm"
[ -s "$NVM_DIR/nvm.sh" ] && \. "$NVM_DIR/nvm.sh"
[ -s "$NVM_DIR/bash_completion" ] && \. "$NVM_DIR/bash_completion"
EOF
```

**Production notes**:
- `PROFILE=/dev/null` prevents the installer from mutating shell RC files—critical for ephemeral CI containers
- `build-essential` + `libssl-dev` ensures `npm install` can compile native add-ons (e.g., `@img/sharp-libvips-linuxmusl-x64`)
- The script outputs the shell snippet so CI systems can `eval "$(bash bootstrap-nvm.sh)"` and persist nvm across steps
- `nvm install "lts/20"` resolves to the latest 20.x release automatically

### Project-Level Version Pinning with `.nvmrc`

```bash
# .nvmrc — Commit this to your repo
# Supports: major (20), major.minor (20.12), LTS alias (lts/iron), or exact (v20.12.0)
lts/iron
```

```bash
# .bashrc or .zshrc addition — Auto-switch on directory change
# Place AFTER nvm initialization
cdnvm() {
  cd "$@"
  if [[ -f .nvmrc ]]; then
    local requested_version
    requested_version="$(cat .nvmrc)"
    local current_version
    current_version="$(nvm version 2>/dev/null || echo 'none')"
    if [[ "$current_version" != "$requested_version" ]]; then
      nvm use --silent 2>/dev/null || nvm install --silent
    fi
  fi
}
alias cd=cdnvm
```

This `cdnvm` wrapper makes `cd` version-aware. When you `cd` into a project with `.nvmrc`, it silently switches or installs the required version. The `--silent` flag suppresses nvm's verbose output. We used this pattern at my previous org across 200+ microservices—eliminated "wrong Node version" class of CI failures entirely.

## Best Practices

1. **Default to nvm for development machines**. Developers need version switching. The 200ms shell startup cost is negligible compared to context-switching friction.

2. **Use APT for immutable servers and containers**. If you're building a Docker image or provisioning a VM that runs a single service, APT is simpler. No shell initialization, no PATH manipulation, smaller attack surface.

3. **Pin explicitly in both worlds**. 
   - APT: `/etc/apt/preferences.d/nodejs-pin` with `Pin: version 20.*`
   - nvm: `.nvmrc` in repo root + `nvm alias default lts/iron`

4. **Never `sudo npm install -g` with nvm**. It defeats the isolation model. If you need a global CLI tool, use `corepack` (bundled with Node 16.9+) or `npx`.

5. **Automate nvm installation in CI**. Don't rely on pre-installed nvm. The bootstrap script above runs in ~45 seconds on GitHub Actions and gives you reproducible versions.

6. **Monitor NodeSource repository health**. Their build pipeline occasionally lags 1-2 weeks behind upstream Node releases. Subscribe to their GitHub releases for notifications.

## Common Mistakes & Anti-Patterns

### Mistake 1: Mixing APT and nvm on the Same User
```bash
# ❌ BAD: APT node in /usr/bin, nvm node in ~/.nvm — which wins?
sudo apt install nodejs
curl -o- https://raw.githubusercontent.com/nvm-sh/nvm/v0.39.7/install.sh | bash
nvm install 20
node -v  # Unpredictable: depends on PATH order
```
**Fix**: Pick one. If you need nvm, purge the APT package first: `sudo apt purge -y nodejs && sudo apt autoremove -y`.

### Mistake 2: Forgetting `corepack` Enable
```bash
# ❌ BAD: yarn/pnpm not available despite Node 16.9+
node -v  # v20.12.0
yarn --version  # Command not found
```
**Fix**: Run `corepack enable` once per Node version (nvm) or system-wide (APT). It creates shims for `yarn`, `pnpm`, `pnpmx` in the same bin directory as `node`.

### Mistake 3: nvm in Non-Interactive Shells Without Loading
```yaml
# ❌ BAD: GitHub Actions step fails
- run: nvm use 20 && npm ci
  # nvm: command not found
```
**Fix**: Source nvm explicitly in each step, or use `actions/setup-node` which handles this:
```yaml
- uses: actions/setup-node@v4
  with:
    node-version-file: '.nvmrc'
    cache: 'npm'
```
