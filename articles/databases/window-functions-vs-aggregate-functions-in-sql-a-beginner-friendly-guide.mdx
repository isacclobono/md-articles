# Window Functions vs Aggregate Functions in SQL: A Beginner-Friendly Guide

## Introduction
When you start writing SQL queries you quickly encounter two families of functions that look similar but behave very differently: aggregate functions and window functions. Both let you compute values across multiple rows, yet the shape of the result set they return is distinct. Understanding the difference is essential for writing reports, building analytics pipelines, and avoiding subtle bugs that can corrupt dashboards or cause unnecessary load on your database.

## Why This Matters
In production systems you often need to calculate running totals, rank items within a partition, or compare a row to the average of its peers. If you reach for an aggregate function when a window function is required (or vice‑versa) you either lose rows you need to keep or you force the planner to materialize intermediate results that could have been avoided. The wrong choice can turn a simple SELECT into a costly multi‑stage query, increase latency, and make your code harder to maintain. Knowing when each tool fits lets you write queries that are both correct and efficient.

## How It Works
Aggregate functions collapse groups of rows into a single output row per group. Window functions, by contrast, compute a value for each row while preserving the original row count; they can look at a sliding frame of rows defined by an OVER clause.

```mermaid
flowchart TD
    A[Input Rows] --> B{Function Type}
    B -->|Aggregate| C[GROUP BY cols]
    C --> D[Compute SUM/COUNT/AVG per group]
    D --> E[One output row per group]
    B -->|Window| F[Define OVER (PARTITION BY ... ORDER BY ...)]
    F --> G[Compute function for each row using frame]
    G --> H[Same number of output rows as input]
```

*Step‑by‑step*  
1. **Parse the query** – the planner identifies whether an aggregate or window function is present.  
2. **Aggregate path** – rows are hashed or sorted by the GROUP BY columns, then the function is applied to each bucket, producing a reduced result set.  
3. **Window path** – rows are sorted according to the PARTITION BY and ORDER BY specifications; a frame (e.g., ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) is defined for each row, and the function is evaluated against that frame without removing any rows.  
4. **Output** – aggregates emit fewer rows; windows emit the same count but with extra columns.

## Core Concepts
- **Aggregate Functions**: `SUM()`, `COUNT()`, `AVG()`, `MIN()`, `MAX()`. They operate on a set of rows and return a single scalar per group.  
- **Window Functions**: Any aggregate can be used as a window function when paired with an `OVER` clause. Pure window functions include `ROW_NUMBER()`, `RANK()`, `DENSE_RANK()`, `LAG()`, `LEAD()`, `NTILE()`.  
- **Partitioning**: `PARTITION BY` divides the result set into windows; each partition is processed independently.  
- **Framing**: Optional `ROWS` or `RANGE` clause limits which rows within a partition the function sees (e.g., a moving average).  
- **Null Handling**: Most aggregates ignore NULLs; window functions propagate NULLs according to the frame definition.

## Examples & Code Walkthrough
Assume a simple e‑commerce schema:

```sql
CREATE TABLE orders (
    order_id      BIGINT PRIMARY KEY,
    customer_id   BIGINT NOT NULL,
    order_ts      TIMESTAMPTZ NOT NULL,
    amount_cents  INTEGER NOT NULL CHECK (amount_cents >= 0)
);
```

### Aggregate Example – Daily Revenue per Customer
```sql
SELECT
    customer_id,
    DATE(order_ts) AS order_date,
    SUM(amount_cents) AS daily_total_cents
FROM orders
WHERE order_ts >= '2024-01-01'
GROUP BY customer_id, DATE(order_ts)
ORDER BY customer_id, order_date;
```
*What happens*: The planner groups rows by `(customer_id, order_date)` and computes a sum for each group. The result set has one row per customer‑day.

### Window Example – Running Total per Customer
```sql
SELECT
    order_id,
    customer_id,
    order_ts,
    amount_cents,
    SUM(amount_cents) OVER (
        PARTITION BY customer_id
        ORDER BY order_ts
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total_cents
FROM orders
WHERE order_ts >= '2024-01-01'
ORDER BY customer_id, order_ts;
```
*What happens*: For each row, the engine looks at all preceding rows in the same customer partition (including the current row) and returns the cumulative sum. The output row count matches the input.

### Combining Both – Percent of Daily Total
```sql
WITH daily AS (
    SELECT
        customer_id,
        DATE(order_ts) AS order_date,
        SUM(amount_cents) AS daily_total_cents
    FROM orders
    WHERE order_ts >= '2024-01-01'
    GROUP BY customer_id, DATE(order_ts)
)
SELECT
    o.order_id,
    o.customer_id,
    o.order_ts,
    o.amount_cents,
    d.daily_total_cents,
    ROUND(
        100.0 * o.amount_cents / NULLIF(d.daily_total_cents, 0),
        2
    ) AS pct_of_daily
FROM orders o
JOIN daily d
  ON o.customer_id = d.customer_id
 AND DATE(o.order_ts) = d.order_date
WHERE o.order_ts >= '2024-01-01'
ORDER BY o.customer_id, o.order_ts;
```
*Note*: The CTE `daily` uses an aggregate to collapse to daily totals; the outer query then joins back to the original rows to compute a percentage. This pattern is common when you need both aggregated and row‑level details.

## Best Practices
1. **Prefer window functions when you need to keep the original row count** – e.g., rankings, running totals, or comparative metrics.  
2. **Use aggregates for summary tables or materialized views** where you intentionally want fewer rows.  
3. **Always specify an ORDER BY inside the OVER clause for functions that depend on sequence** (ROW_NUMBER, RANK, LAG/LEAD). Without it the result is nondeterministic.  
4. **Filter before windowing** when possible. A WHERE clause reduces the number of rows the window has to process, saving CPU and memory.  
5. **Watch out for NULLs** – use `NULLIF` or `COALESCE` when dividing or when you need a default value.  
6. **Index the columns used in PARTITION BY and ORDER BY** to allow the planner to avoid costly sorts.  
7. **Test with EXPLAIN ANALYZE** to verify that the planner is using an index-only scan or a hash aggregate as expected.

## Common Mistakes & Anti-Patterns
| Mistake | Why it’s problematic | Fix |
|---------|----------------------|-----|
| **Using `SUM()` without `GROUP BY` when you want a per‑row total** | Returns a single scalar, collapsing the whole table; you lose row context. | Convert to a window function: `SUM(amount) OVER (PARTITION BY customer_id ORDER BY order_ts)`. |
| ** forgetting `ORDER BY` in `OVER` for `ROW_NUMBER()`** | The numbering becomes arbitrary and can differ between executions, causing flaky reports. | Add `ORDER BY` that reflects the logical sequence (e.g., `ORDER BY order_ts`). |
| **Applying a window function on a huge table without filtering first** | The window may need to sort or hash millions of rows, spilling to disk and slowing the query. | Push predicates into a WHERE clause or use a materialized view / pre‑aggregated summary table. |
| **Assuming `COUNT(*) OVER()` equals the group count** | `COUNT(*) OVER()` returns the total rows in the partition, not the count per group unless you partition correctly. | Ensure your `PARTITION BY` matches the grouping you intend, or use a separate aggregate CTE. |
| **Using `LAG()` without checking for NULLs on the first row** | The first row in each partition will produce NULL, which can break downstream calculations if not handled. | Wrap with `COALESCE(lag_value, 0)` or filter out the first row if it’s not meaningful. |

## Performance Considerations
- **Aggregate functions** typically involve a hash or sort step followed by a single pass over each bucket. Complexity is roughly O(N log N) for sorting or O(N) for hashing, plus the cost of the aggregation operation itself. Memory usage grows with the number of distinct groups.  
- **Window functions** require sorting (or using an existing index) on the `PARTITION BY` and `ORDER BY` columns, then a linear scan to evaluate the frame. If the frame is unbounded preceding (e.g., running total), the engine can keep a cumulative accumulator, making the per‑row cost O(1) after the initial sort.  
- **Spill to disk** occurs when the working set exceeds `work_mem`. Monitoring `EXPLAIN ANALYZE` for “external merge” or “hashagg” with “disk: true” indicates you may need to increase `work_mem` or add supporting indexes.  
- **Parallelism**: Modern Postgres versions can parallelize both aggregates and windows, but windows with overlapping frames sometimes limit parallel speedup.  
- **Network**: If you’re pulling results to an application server, remember that windows return the same row count as the source, while aggregates can dramatically reduce payload size.

## Real-World Usage
- **Netflix** uses window functions to compute per‑title rolling averages of streaming bitrate across time windows, enabling real‑time quality dashboards without pre‑aggregating to minute‑level tables.  
- **Uber** leverages aggregate functions in their nightly ETL jobs to produce city‑level trip counts and revenue summaries that feed into billing systems.  
- **Cloudflare** relies on window functions to calculate sliding‑window request rates per API key for rate‑limiting, preserving each log entry for anomaly detection while still providing a per‑key metric.  

These organizations choose the tool that matches the semantics of the metric: aggregates for business‑level summaries, windows for user‑facing, time‑series, or comparative analytics.

## Frequently Asked Questions (FAQ)
**Q: Can I use an aggregate function inside a window function?**  
A: Yes. Any aggregate (SUM, AVG, etc.) can be turned into a window function by adding an `OVER` clause. The semantics change from collapsing groups to computing a value per row over a defined frame.

**Q: Do window functions always require a sort?**  
A: If the data is already ordered according to the `PARTITION BY` and `ORDER BY` columns (e.g., via an index), the planner can avoid an explicit sort. Otherwise a sort step is unavoidable.

**Q: Is there a performance difference between `COUNT(*)` and `COUNT(column)` as a window?**  
A: `COUNT(*)` counts rows; `COUNT(column)` counts non‑NULL values. The latter may involve an extra null‑check per row, but the difference is usually negligible compared to the sorting cost.

**Q: Can I combine multiple window functions in the same SELECT?**  
A: Absolutely. Each function gets its own `OVER` clause; you can mix different partitions, orders, and frames as needed.

**Q: What happens if I forget the `PARTITION BY`?**  
A: The entire result set becomes a single partition. For running totals this means a global cumulative sum across all customers, which is rarely what you want.

## Conclusion
Aggregate and window functions are two sides of the same coin: both let you derive insight from collections of rows, but they differ in how they shape the output. Aggregates shrink the data set; windows enrich it while keeping the original row count. By matching the function type to the analytical goal, writing clear `OVER` clauses, indexing appropriately, and watching for common pitfalls, you can harness SQL’s full expressive power without sacrificing performance. Keep these patterns in mind the next time you design a report, build a metrics pipeline, or troubleshoot a slow query—you’ll write cleaner, faster, and more maintainable SQL.
