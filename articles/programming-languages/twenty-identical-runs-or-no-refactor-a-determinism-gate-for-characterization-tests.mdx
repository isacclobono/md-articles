# Twenty Identical Runs or No Refactor: A Determinism Gate for Characterization Tests

## Introduction

We’ve all been there. A team gathers to refactor a legacy module—something that’s been stable for years but is now a bottleneck. The code is complex, the tests are sparse, and the only safety net is a set of characterization tests (golden file tests, snapshot tests) that were written once and never updated. The refactoring begins, confidence is high, and then—subtle behavioral regressions slip through. Tests that passed in CI suddenly fail in production, or worse, pass but produce slightly different output that corrupts data downstream.

The root cause? Characterization tests that are flaky or non-deterministic. They rely on a single run, which can mask intermittent failures due to timing, random seeds, or environmental factors. In this article, we introduce the **Determinism Gate**: a rigorous protocol that requires 20 identical test runs before allowing refactoring to proceed. It’s a simple, statistical safety net that forces teams to confront non-determinism head-on.

## Why This Matters

Characterization tests are the last line of defense when refactoring legacy code. They capture the current behavior of a system—often as golden files, snapshots, or expected output logs—and ensure that changes don’t alter that behavior. But here’s the catch: if the original behavior is itself non-deterministic, a single test run can give a false sense of security.

Imagine a Python module that uses `datetime.now()` without a fixed seed. One run might produce output A, another run might produce output B. If the characterization test only runs once, it captures whichever output happens to be generated that day. The test passes, the refactor proceeds, and later—when the system runs under different conditions—the output diverges, causing silent failures.

This isn’t just a theoretical concern. In our production cluster, we once refactored a data processing pipeline that relied on `random` without a fixed seed. The characterization test passed 100 times in a row during development, but in production, the randomness caused edge-case failures that corrupted customer data. The cost? Three days of incident response and a rollback that undid two weeks of work.

The Determinism Gate solves this by enforcing a statistical threshold: 20 consecutive identical runs. This isn’t arbitrary—it’s based on the idea that if a system is truly deterministic, 20 runs should produce identical output. If they don’t, the system is flaky, and refactoring should be paused until the flakiness is resolved.

## How It Works

The Determinism Gate is a workflow that sits between your characterization test suite and the decision to merge a refactoring PR. It’s a gate that opens only when the system proves its determinism under repeated runs.

### Mermaid Diagram: Determinism Gate Workflow

```mermaid
flowchart TD
    A[Start Refactor PR] --> B{Run Determinism Gate}
    B --> C[Execute Test Suite 20x]
    C --> D{All Outputs Identical?}
    D -- Yes --> E[Gate Open: Allow Refactor]
    D -- No --> F[Gate Closed: Fix Flakiness]
    F --> G[Analyze Divergent Runs]
    G --> H[Identify Non-Deterministic Source]
    H --> I[Apply Fix (e.g., Seed Injection)]
    I --> C
    E --> J[Merge Refactor]
```

**Step-by-step breakdown:**

1. **Trigger**: The gate is triggered when a refactoring PR is opened or when a characterization test is first created.
2. **Execution**: The test suite is run 20 times in isolation, with no parallelism or shared state.
3. **Comparison**: Each run’s output (stdout, stderr, exit code, golden files) is hashed and compared to the previous runs.
4. **Decision**:
   - **All 20 runs identical**: The gate opens. The refactoring is allowed to proceed.
   - **Any run diverges**: The gate closes. The team must investigate the flakiness, fix the root cause (e.g., inject fixed seeds, isolate environmental dependencies), and re-run the gate.

The key insight is that this gate is **fail-fast**. It doesn’t just check for determinism—it forces teams to confront non-determinism before it can be masked by a single passing run.

## Core Concepts

### 1. Determinism vs. Stability
- **Determinism**: Given the same input, the system produces the same output every time.
- **Stability**: The system produces correct output under normal conditions, even if non-deterministic.
The gate enforces determinism, not stability. A system can be stable but non-deterministic (e.g., a load balancer that randomly selects servers). The gate would fail such a system, which is the point: refactoring a non-deterministic system is risky because you can’t reliably compare behavior.

### 2. The 20-Run Threshold
Why 20? It’s a statistical compromise between thoroughness and practicality. With 20 runs, you capture 95% confidence that the system is deterministic (assuming a binomial distribution of failures). Fewer runs risk missing intermittent failures; more runs increase CI time without meaningful gains.

### 3. Output Hashing
To compare outputs efficiently, we hash the concatenated stdout, stderr, and exit code. This creates a unique signature for each run. If the signatures match, the outputs are identical (with negligible collision probability for SHA-256).

### 4. Environmental Isolation
Non-determinism often comes from the environment—OS differences, library versions, or system time. The gate should run in a controlled environment (e.g., Docker container, virtualenv) to eliminate these variables.

## Examples & Code Walkthrough

### Example 1: Python Determinism Checker

Here’s a Python script that runs a test command 20 times and compares outputs using hashing. It’s designed to be dropped into a CI pipeline or run locally.

```python
# determinism_gate.py
import hashlib
import subprocess
import sys
import os
from typing import Set

def run_test(command: str, runs: int = 20) -> bool:
    """
    Runs a test command `runs` times and checks for deterministic output.
    Returns True if all runs produce identical output, False otherwise.
    """
    signatures: Set[str] = set()
    for i in range(runs):
        # Run the command and capture output
        result = subprocess.run(
            command,
            shell=True,
            capture_output=True,
            text=True,
            # Inherit environment variables for consistency
            env=os.environ.copy()
        )
        # Create a unique signature from stdout, stderr, and exit code
        output = result.stdout + result.stderr + str(result.returncode)
        signature = hashlib.sha256(output.encode()).hexdigest()
        signatures.add(signature)
        
        # Early exit if divergence is detected
        if len(signatures) > 1:
            print(f"Run {i+1} diverged! Signatures: {signatures}")
            return False
    
    print(f"All {runs} runs identical. Gate open.")
    return True

if __name__ == "__main__":
    if len(sys.argv) < 2:
        print("Usage: python determinism_gate.py '<command>' [runs]")
        sys.exit(1)
    
    command = sys.argv[1]
    runs = int(sys.argv[2]) if len(sys.argv) > 2 else 20
    
    if not run_test(command, runs):
        sys.exit(1)
```

**Walkthrough**:
- The script takes a shell command as an argument (e.g., `python -m pytest test_module.py`).
- It runs the command 20 times, capturing stdout, stderr, and exit code.
- Each run’s output is hashed with SHA-256 to create a signature.
- If any run produces a different signature, the script exits with code 1 (failure).
- If all runs match, it exits with code 0 (success).

### Example 2: Shell Script for CI Pipelines

For teams using shell-based CI (e.g., GitHub Actions, GitLab CI), here’s a lightweight Bash script:

```bash
#!/bin/bash
# determinism_gate.sh
set -euo pipefail

COMMAND="$1"
RUNS="${2:-20}"
FIRST_OUTPUT=""

for ((i=1; i<=$RUNS; i++)); do
    OUTPUT=$(eval "$COMMAND" 2>&1)
    if [ -z "$FIRST_OUTPUT" ]; then
        FIRST_OUTPUT="$OUTPUT"
    elif [ "$OUTPUT" != "$FIRST_OUTPUT" ]; then
        echo "Run $i diverged! Failing."
        exit 1
    fi
done

echo "All $RUNS runs identical. Gate open."
```

**Walkthrough**:
- The script takes a command and an optional run count (default 20).
- It captures the output of each run and compares it to the first run.
- If any run differs, it exits with code 1.
- If all runs match, it exits with code 0.

### Example 3: Integrating with GitHub Actions

Here’s how to gate a refactoring PR using the Determinism Gate in GitHub Actions:

```yaml
name: Determinism Gate
on:
  pull_request:
    paths:
      - 'refactor/**'

jobs:
  determinism-check:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Set up Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.9'
      - name: Install dependencies
        run: |
          pip install -r requirements.txt
      - name: Run Determinism Gate
        run: |
          python determinism_gate.py "python -m pytest tests/characterization/" 20
```

**Walkthrough**:
- The workflow triggers on PRs that modify files in the `refactor/` directory.
- It sets up Python, installs dependencies, and runs the Determinism Gate script.
- If the gate fails, the PR is blocked from merging.

## Best Practices

### 1. Run in Isolation
Always run the Determinism Gate in a clean, isolated environment. Use Docker or virtualenv to eliminate OS/library version drift. For example:

```dockerfile
FROM python:3.9-slim
WORKDIR /app
COPY . .
RUN pip install -r requirements.txt
CMD ["python", "determinism_gate.py", "python -m pytest tests/characterization/"]
```

### 2. Cache Dependencies
To reduce CI time, cache test dependencies between runs. In GitHub Actions:

```yaml
- name: Cache dependencies
  uses: actions/cache@v3
  with:
    path: |
      ~/.cache/pip
      venv
    key: ${{ runner.os }}-pip-${{ hashFiles('requirements.txt') }}
    restore-keys: |
      ${{ runner.os }}-pip-
```

### 3. Seed Injection for Randomness
If your tests use randomness, inject fixed seeds. For Python’s `random` module:

```python
import random

def test_deterministic_behavior():
    random.seed(42)  # Fixed seed
    result = generate_random_data()
    assert result == expected_output
```

For more complex cases, use libraries like `pytest-randomly` with a fixed seed:

```bash
pip install pytest-randomly
pytest --randomly-seed=12345 tests/
```

### 4. Log Divergent Runs
When runs diverge, capture detailed logs to aid debugging. Modify your script to save outputs for later analysis:

```python
if len(signatures) > 1:
    # Save divergent run outputs for debugging
    with open(f"run_{i+1}_output.txt", "w") as f:
        f.write(result.stdout + result.stderr)
    print(f"Run {i+1} diverged! Output saved to run_{i+1}_output.txt")
    return False
```

## Common Mistakes & Anti-Patterns

### Mistake 1: Running Tests in Parallel
**Anti-Pattern**: Running the 20 test runs in parallel to save time.
**Why It’s Bad**: Parallel runs can introduce race conditions, shared state, or resource contention that wouldn’t occur in production. This defeats the purpose of the gate.
**Fix**: Always run tests sequentially in the gate.

### Mistake 2: Ignoring Environmental Factors
**Anti-Pattern**: Running the gate on multiple OS versions or hardware configurations without isolation.
**Why It’s Bad**: Different environments can produce different outputs, causing false positives (gate fails even though the system is deterministic).
**Fix**: Use a single, controlled environment (e.g., Docker) for all runs.

### Mistake 3: Overlooking Non-Output Determinism
**Anti-Pattern**: Only comparing stdout/stderr, ignoring side effects like file writes or database changes.
**Why It’s Bad**: A system can produce identical stdout but write different files or modify a database, leading to silent failures.
**Fix**: Hash all observable outputs, including golden files, database states, and logs.

### Mistake 4: Hardcoding the Run Count
**Anti-Pattern**: Hardcoding `runs=20` in scripts without making it configurable.
**Why It’s Bad**: Different systems may require different thresholds (e.g., 50 runs for high-risk modules).
**Fix**: Make the run count a configurable parameter, as shown in the examples above.

## Performance Considerations

### CPU Overhead
The Determinism Gate adds CPU overhead by running the test suite 20 times. For a test suite that takes 1 second per run, the gate adds 19 seconds of CI time. This is negligible for most workflows but can be significant for large, slow test suites.

### Memory Allocation
The Python script uses minimal memory (a few KB for signatures). The Bash script is even lighter. No memory concerns.

### Network Latency
If the tests involve network calls, the gate will amplify latency. For example, a test that makes 10 HTTP requests per run will make 200 requests total. Consider mocking network calls in the gate.

### Scalability
The gate scales linearly with the number of runs. For 20 runs, it’s 20x the test time. For 100 runs, it’s 100x. Choose the run count based on risk tolerance: 20 for low-risk modules, 50+ for high-risk refactors.

## Frequently Asked Questions (FAQ)

**Q: Why 20 runs? Why not 10 or 50?**
A: 20 runs is a statistical sweet spot. It provides 95% confidence that the system is deterministic (assuming a binomial distribution of failures). Fewer runs risk missing intermittent failures; more runs increase CI time without meaningful gains. For high-risk modules, you can increase the count.

**Q: Can I use the Determinism Gate for unit tests?**
A: Yes, but it’s overkill. Unit tests are typically deterministic by design. The gate is most valuable for characterization tests, integration tests, and systems with legacy code or external dependencies.

**Q: How do I handle tests that are inherently non-deterministic (e.g., load testing)?**
A: Don’t use the gate for inherently non-deterministic tests. Instead, refactor the test to be deterministic (e.g., mock external dependencies, inject fixed seeds). If that’s not possible, exclude the test from the gate.

**Q: What if the gate fails due to a known flaky test?**
A: Fix the flaky test first. The gate is a safety net, not a crutch. If a test is flaky, it’s a bug in the test itself, not the system under test.
