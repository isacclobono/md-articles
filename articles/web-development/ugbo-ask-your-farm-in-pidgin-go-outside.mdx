# Ugbo: Ask Your Farm in Pidgin, Go Outside

## Introduction

Building software for underserved markets often means rethinking assumptions we've internalized in our daily work. I recently encountered a project called Ugbo—a conversational web app that lets farmers ask questions in Pidgin English and get reliable, actionable farm advice in return. The name "Ugbo" itself means "farm" in several Nigerian languages, and the core idea is deceptively simple: lower the language barrier so technology serves people where they are, not where we assume they should be.

From an engineering perspective, the challenge isn't just translating text. It's about building a pipeline that handles code-switching, preserves agricultural terminology, stays responsive under variable network conditions, and remains maintainable as the knowledge base grows. This article walks through the full architecture, code, and practical considerations of building a system like Ugbo, from the ground up.

## Why This Matters

Language localization in agri-tech isn't a nice-to-have; it's a production bottleneck. I've worked on projects where a well-trained model sat unused because the interface was only in English or French, and smallholder farmers couldn't articulate their problems in those languages. The real-world pain point is clear: if a farmer can't ask "Why are my leaves turning yellow?" in a language they think in, the most sophisticated AI backend is irrelevant.

From a systems perspective, this translates to several engineering challenges:
- **Low-latency translation** between Pidgin and English (or other local languages) without round-tripping to expensive cloud APIs every time.
- **Intent detection** that understands agricultural domain language, not just generic conversational phrasing.
- **Knowledge retrieval** that respects structured data (soil reports, weather alerts, planting calendars) while also being flexible enough to handle free-form questions.
- **Observability** that lets us debug misclassifications or translation drops in the field, where network connectivity may be spotty.

Building Ugbo means trading off raw model size for reliability, cost, and offline capability. It's a case study in how to ship AI-powered features that actually work in production, not just in a notebook.

## How It Works

Below is the end-to-end flow that Ugbo uses. Every request starts at the web UI, moves through a series of micro-services, and returns an answer in the farmer's language.

```mermaid
flowchart TD
    A[Farmer (Web UI)] --> B[React Frontend]
    B --> C[Express/GraphQL API]
    C --> D[Translate Service<br/>(Pidgin ↔ English)]
    D --> E[Intent Detector<br/>(LLM fine-tuned)]
    E --> F[Knowledge Retriever<br/>(Vector DB)]
    F --> G[Answer Generator<br/>(LLM)]
    G --> H[Translate Service<br/>(English → Pidgin)]
    H --> C
    C --> A
    D -.-> I[External NLP API<br/>(Hugging Face)]
    E -.-> J[Custom Intent Model<br/>(Python/Flask)]
    F -.-> K[PostgreSQL + pgvector]
    G -.-> L[OpenAI/GPT-4 or Local LLM]
    H -.-> I
```

**Step-by-step:**

1. **Input** – The farmer types a question in Pidgin (e.g., "My tomatoes get wet, wet. What I do?") into the React UI.
2. **Translate** – The frontend sends the raw text to the Translate Service, which converts Pidgin → English using a local Hugging Face `facebook/nllb-200` model wrapped in a Flask micro-service. Results are cached in Redis with a TTL of 24 hours to avoid repeat computation.
3. **Detect Intent** – The English query hits the Intent Detector. We use a fine-tuned LLaMA‑2‑7B model via Ollama for local inference, with an OpenAI GPT‑4 SDK fallback if the local model fails or the query falls outside the agricultural domain.
4. **Retrieve Knowledge** – The detected intent guides a vector search against PostgreSQL + pgvector. The knowledge base stores chunks of farm advice, each tagged with metadata: crop type, growth stage, region, and source (extension service, research paper, farmer trial). Similarity is computed via cosine distance on sentence‑transformers embeddings.
5. **Generate Answer** – The retriever returns the top‑k most relevant chunks. These, plus the original query, are fed to the Answer Generator (LLM) to produce a concise, actionable response in English.
6. **Translate Back** – The English answer passes through the Translate Service again, this time English → Pidgin. The translated output is sent back through the GraphQL API to the frontend.
7. **Deliver** – The farmer sees the answer instantly, in their own language, with a confidence score and source tags.

This flow is deliberately stateless across services, with Redis and PostgreSQL providing the only persistent state. Each micro-service can be scaled independently, and the whole stack runs in Docker containers orchestrated by Kubernetes (or Docker‑Compose for local development).

## Core Concepts

### Translation Micro‑service
The heart of Ugbo's language bridge is a custom Hugging Face transformer. We chose `facebook/nllb-200` because it supports 200 languages, including Nigerian Pidgin (`pcm`), and offers a good trade-off between translation quality and inference speed. The service is built with Flask, exposes a single `/translate` endpoint, and uses ONNX runtime for accelerated CPU inference. Caching aggressively reduces latency for repeated queries.

### Intent Detection
Rather than relying on a pure LLM prompt that might drift, we fine-tune a smaller model on a labeled dataset of agricultural questions. The training set includes Pidgin‑English pairs annotated with intents like "nutrient deficiency", "pest identification", "weather alert", "planting schedule". The model outputs a probability distribution over intents, which then gates the knowledge retrieval step. If the confidence is below a threshold, the system falls back to a general‑purpose LLM prompt.

### Knowledge Graph & Vector Search
The knowledge base is PostgreSQL with the `pgvector` extension. Each advice entry is stored as a row with columns: `id`, `crop`, `stage`, `region`, `content`, `embedding` (vector(1536)). We use `pgvector`'s `inner_product` operator for similarity search, which is fast enough for our current scale (≈ 50 k entries) and integrates directly with our existing relational queries (e.g., filtering by region or crop type before vector search).

### Answer Generation
We run two LLM back‑ends: a local LLaMA‑2‑7B via Ollama for cost‑controlled production, and OpenAI's GPT‑4 as a safety net. The prompt template is strict: it includes the user query, the top‑k retrieved chunks (with source citations), and a "language guard" that forces the output to be concise and actionable. If the local model returns a confidence score below 0.6, the request is rerouted to GPT‑4.

### Caching & Observability
Redis stores two things: translation pairs (Pidgin↔English) with a 24‑hour TTL, and recent intent‑to‑response mappings. Prometheus scrapes latency and error rates from each micro-service; Grafana dashboards show translation miss rates, vector search latency, and LLM token usage. Jaeger traces a single request across all services, which has been invaluable when debugging a sudden spike in "translation timeout" errors last month.

### 1. GraphQL Resolver (Node.js + Express + Apollo Server)

This resolver ties the whole pipeline together. It receives the farmer's Pidgin question, runs translation, intent detection, knowledge retrieval, answer generation, and translates back.

```typescript
// src/graphql/resolvers.ts
import { gql, ApolloServer } from '@apollo/server';
import { expressMiddleware } from '@apollo/server/express4';
import express from 'express';
import translate from '../services/translate';
import detectIntent from '../services/intent';
import retrieveKnowledge from '../services/knowledge';
import generateAnswer from '../services/answer';
import Redis from 'ioredis';

const TYPEDEFS = gql`
  enum Language { EN, PIDGIN }
  type AnswerResult {
    answer: String!
    confidence: Float!
    sources: [String]
  }
  type Query {
    askQuestion(text: String!, language: Language = EN): AnswerResult
  }
`;

const RedisClient = new Redis(process.env.REDIS_URL || 'redis://localhost:6379');

async function translateText(text: string, from: string, to: string): Promise<string> {
  const cacheKey = `translate:${from}:${to}:${text}`;
  const cached = await RedisClient.get(cacheKey);
  if (cached) return cached;

  const result = await translate(text, from, to); // calls Flask micro-service
  RedisClient.setex(cacheKey, 86400, result); // 24h TTL
  return result;
}

async function askQuestion(_, { text, language }: { text: string; language: Language }) {
  let english = text;
  let pidgin = text;

  // 1. Translate to English if starting from Pidgin
  if (language === 'PIDGIN') {
    english = await translateText(text, 'pcm', 'en');
  }

  // 2. Detect intent
  const intent = await detectIntent(english); // LLaMA‑2‑7B local, fallback to GPT‑4 SDK

  // 3. Retrieve knowledge
  const { chunks, metadata } = await retrieveKnowledge(english, intent);

  // 4. Generate answer in English
  const { answer, confidence } = await generateAnswer(english, chunks, intent);

  // 5. Translate back to Pidgin if needed
  if (language === 'PIDGIN') {
    pidgin = await translateText(answer, 'en', 'pcm');
    return { answer: pidgin, confidence, sources: metadata.map((m: any) => m.source) };
  }

  return { answer, confidence, sources: metadata.map((m: any) => m.source) };
}

const server = new ApolloServer({
  typeDefs: TYPEDEFS,
  resolvers: {
    Query: { askQuestion },
  },
});

const app = express();
server.start().then(() => app.use('/graphql', expressMiddleware(server)));

app.listen(4000, () => {
  console.log('🌱 Ugbo API ready at http://localhost:4000/graphql');
});
```
