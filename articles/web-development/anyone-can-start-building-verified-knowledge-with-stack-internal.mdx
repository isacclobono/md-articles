# Anyone can start building verified knowledge with Stack Internal

## Introduction  
I was troubleshooting a tricky React hydration issue when I realized the answer I needed lived across three separate blogs, a GitHub wiki, and a Stack Overflow post. I spent an hour copying code snippets, reconciling version differences, and verifying each claim. The friction was obvious: fragmented tutorials, no unified verification, and a lack of a single source of truth for developers. Stack Internal was built to solve exactly this problem. It turns the collective wisdom of the Stack Exchange ecosystem into a living, versioned knowledge base that anyone can author, verify, and maintain with the same rigor the community applies to code.

## Why This Matters  
For engineering organizations, unreliable documentation translates directly into slower onboarding, increased bug rates, and wasted developer hours. In our production cluster we once measured 12 % of support tickets stemmed from outdated API examples. A centralized, verified knowledge platform reduces those tickets by providing a single, up‑to‑date source for every concept. It also democratizes contribution: newcomers can publish after a transparent verification pipeline, rather than waiting for a lone maintainer to update a static site. The result is a self‑sustaining feedback loop where code and its documentation evolve together.

## How It Works  
The core flow moves a contribution from author to published article through a series of tightly coupled services. Below is a high‑level flowchart that captures the journey:

```mermaid
flowchart TD
    A[Author drafts article] --> B[Client App (React editor)]
    B --> C[API Gateway]
    C --> D[Auth Service]
    D --> E[Knowledge Service]
    E --> F[PostgreSQL (metadata)]
    E --> G[Object Storage (markdown)]
    E --> H[Redis Queue]
    H --> I[Verification Worker]
    I --> J[CI/Validation (GitHub Actions)]
    J --> K[Static Site Generator]
    K --> L[CDN]
    I --> M[Moderator UI]
    M --> N[Approval/Rejection]
    N --> E
```

1. **Author drafts** – The author composes markdown in the client app, attaches tags, and selects a visibility level.  
2. **API Gateway** – An Express‑based gateway routes requests, enforces rate limits, and aggregates metrics.  
3. **Auth Service** – JWT tokens are validated against a Stack Exchange OAuth2 provider; the user’s Stack ID becomes the canonical author.  
4. **Knowledge Service** – Handles CRUD, versioning, and status transitions (`draft` → `pending_verification` → `verified` → `published`).  
5. **Storage** – Metadata lives in PostgreSQL; raw markdown is stored in S3/MinIO for cheap scaling.  
6. **Queue** – A Redis‑backed job queue (`verification`) serializes linting and validation work.  
7. **Verification Worker** – Runs `markdownlint`, schema validation, and a lightweight fact‑check against the Stack Exchange API. If any rule fails, the entry is moved back to `draft` with a reason attached.  
8. **CI/Validation** – Every push to the `main` branch triggers GitHub Actions that run unit tests, integration tests, and a security scan (e.g., `npm audit`).  
9. **Static Site Generator** – Eleventy pulls verified entries from the Knowledge Service, applies a shared layout, and writes to a CDN.  

The pipeline ensures that only content that passes automated checks and community review reaches end users, while the author receives immediate feedback on any issues.

## Core Concepts  
- **Verification Layer** – Three‑tier validation: (1) client‑side markdown linting, (2) server‑side schema and semantic checks, (3) manual moderator approval. Each step logs to an audit table in PostgreSQL, preserving a full trail.  
- **Versioning** – Each knowledge entry is immutable once published. New updates create a new row with a `version` number; the previous version is retained for roll‑back.  
- **Slug Generation** – A deterministic slug is derived from the title using a custom algorithm that lower‑cases, replaces non‑alphanumerics, and ensures uniqueness against existing slugs.  
- **Role‑Based Access** – Permissions are stored in a `roles` table (`author`, `moderator`, `admin`). The Knowledge Service checks these before performing state transitions.  
- **Indexing Strategy** – `idx_knowledge_status_created_at` accelerates queries for pending items; `idx_knowledge_slug` guarantees fast reads; full‑text search indexes on `title` and `content` enable rapid discovery.

export enum KnowledgeStatus {

### 3. Controller – Creating an Entry  

```ts
// src/controllers/knowledge.controller.ts
import { Controller, Post, Body, UseGuards, Req, Res } from '@nestjs/common';
import { Request, Response } from 'express';
import { JwtAuthGuard } from '../guards/jwt-auth.guard';
import { CreateKnowledgeDto } from '../dto/create-knowledge.dto';
import { KnowledgeService } from '../services/knowledge.service';
import { generateSlug } from '../utils/slug.utils';

@Controller('knowledge')
@UseGuards(JwtAuthGuard)
export class KnowledgeController {
  constructor(private readonly svc: KnowledgeService) {}

  @Post()
  async create(@Req() req: Request, @Res() res: Response, @Body() dto: CreateKnowledgeDto) {
    try {
      const author = (req as any).user.userId;
      const slug = generateSlug(dto.title);

      const payload: CreateKnowledgeDto & { authorId: string; slug: string; status: string } = {
        ...dto,
        authorId: author,
        slug,
        status: 'pending_verification',
      };

      const entry = await this.svc.create(payload);
      // Notify verification worker via Redis queue
      await this.enqueueVerification(entry.id);

      return res.status(201).json({ id: entry.id, slug, status: entry.status });
    } catch (err) {
      // Defensive: log internal error, return generic message
      console.error('Failed to create knowledge entry', err);
      return res.status(500).json({ message: 'Internal server error' });
    }
  }

  private async enqueueVerification(entryId: string): Promise<void> {
    const redis = this.svc.getRedisClient();
    await redis.lpush('verification_queue', JSON.stringify({ entryId, timestamp: Date.now() }));
  }
}
```

### 4. Service – Business Logic & Versioning  

```ts
// src/services/knowledge.service.ts
import { Injectable } from '@nestjs/common';
import { InjectRepository } from '@nestjs/typeorm';
import { Repository } from 'typeorm';
import { KnowledgeEntity, KnowledgeStatus } from '../models/knowledge.entity';
import { CreateKnowledgeDto } from '../dto/create-knowledge.dto';

@Injectable()
export class KnowledgeService {
  constructor(
    @InjectRepository(KnowledgeEntity)
    private readonly repo: Repository<KnowledgeEntity>,
  ) {}

  async create(payload: CreateKnowledgeDto & { authorId: string; slug: string; status: string }) {
    const entity = this.repo.create({
      id: payload.id,
      authorId: payload.authorId,
      slug: payload.slug,
      title: payload.title,
      content: payload.content,
      tags: payload.tags,
      status: payload.status as KnowledgeStatus,
      createdAt: new Date(),
      updatedAt: new Date(),
    });

    return this.repo.save(entity);
  }

  async findPending(limit = 20) {
    return this.repo.find({
      where: { status: KnowledgeStatus.PENDING_VERIFICATION },
      order: { createdAt: 'ASC' },
      take: limit,
    });
  }

  async approve(entryId: string, moderatorId: string) {
    const entry = await this.repo.findOneBy({ id: entryId });
    if (!entry) {
      throw new Error('Entry not found');
    }
    entry.status = KnowledgeStatus.VERIFIED;
    entry.updatedAt = new Date();
    return this.repo.save(entry);
  }

  async publish(entryId: string) {
    const entry = await this.repo.findOneBy({ id: entryId });
    if (!entry || entry.status !== KnowledgeStatus.VERIFIED) {
      throw new Error('Cannot publish unapproved entry');
    }
    entry.status = KnowledgeStatus.PUBLISHED;
    entry.updatedAt = new Date();
    return this.repo.save(entry);
  }

  getRedisClient() {
    // Injected via module provider; simplified here
    return global.redis;
  }
}
```

### 5. Verification Worker  

```ts
// src/workers/verification.worker.ts
import * as Redis from 'ioredis';
import { KnowledgeService } from '../services/knowledge.service';
import { KnowledgeStatus } from '../models/knowledge.entity';
import markdownlint from 'markdownlint';

const redis = new Redis(process.env.REDIS_URL);
const svc = new KnowledgeService();

async function run() {
  while (true) {
    const [raw] = await redis.brpop('verification_queue', 5);
    if (!raw) continue;

    const job = JSON.parse(raw);
    const entry = await svc.findOne(job.entryId);
    if (!entry) {
      console.warn(`Verification job references missing entry ${job.entryId}`);
      continue;
    }

    // 1️⃣ Lint markdown
    const lintResult = await markdownlint.promises.markdownlint(entry.content, {
      defaultStyle: false,
    });

    // 2️⃣ Schema validation (title length, tag format, etc.)
    const validationErrors = await svc.validate(entry);
    if (Object.keys(lintResult).length || validationErrors.length) {
      entry.status = KnowledgeStatus.DRAFT;
      entry.rejectedReason = `Lint: ${JSON.stringify(lintResult)}; Validation: ${validationErrors.join(', ')}`;
      await svc.save(entry);
      // Notify author
      await svc.notifyAuthor(entry.authorId, entry.rejectedReason);
      continue;
    }

    // 3️⃣ Fact‑check against Stack Exchange API (simplified)
    const factCheck = await svc.factCheck(entry.content);
    if (!factCheck.passed) {
      entry.status = KnowledgeStatus.DRAFT;
      entry.rejectedReason = `Fact‑check failed: ${factCheck.reason}`;
      await svc.save(entry);
      await svc.notifyAuthor(entry.authorId, entry.rejectedReason);
      continue;
    }

    // All checks passed – move to verified
    entry.status = KnowledgeStatus.VERIFIED;
    await svc.save(entry);
    // Push to moderator UI (via websocket or polling)
    await svc.notifyModerator(entry.id);
  }
}

run().catch(err => console.error('Verification worker crashed', err));
```

## Best Practices  
- **Never trust client‑provided metadata** – always recompute slugs and normalize tags server‑side.  
- **Use read‑replicas for article reads** – keep write operations on the primary to avoid race conditions during status transitions.  
- **Paginate verification queues** – if the queue grows beyond a few thousand items, split into multiple Redis lists (`verification_queue_1`, `verification_queue_2`).  
- **Cache markdown rendering** – store rendered HTML in Redis with a TTL equal to the article’s freshness window; invalidate on status change.  
- **Audit logs are immutable** – store them in a write‑once storage (e.g., Amazon S3) with object lock enabled.  

## Common Mistakes & Anti-Patterns  

| Mistake | Why It Hurts | Fix |
|---------|--------------|-----|
| **Skipping manual review** | Automated linting can’t catch contextual accuracy; misinformation slips through. | Require at least one moderator approval before publishing. |
| **Storing markdown in DB** | Relational databases are not optimized for large blobs; performance degrades. | Move raw markdown to object storage; keep only metadata in PostgreSQL. |
| **Flat permission model** | Newbies can edit published articles, causing drift. | Implement role‑based access; only authors and moderators can edit; published articles are immutable. |
| **Blocking verification on UI thread** | Long‑running linting hangs API responses. | Offload verification to a background worker; return immediate “queued” response. |
| **Hard‑coded API keys** | Secrets leak into version control. | Use environment variables and secret managers; rotate keys regularly. |

## Performance Considerations  
- **Database queries** – Use eager loading sparingly. For the verification list, fetch only `id`, `title`, `status`, and `createdAt`.  
- **Redis memory** – Each verification job occupies ~200 B; a queue of 10 k jobs uses ~2 MB, well within typical limits.
