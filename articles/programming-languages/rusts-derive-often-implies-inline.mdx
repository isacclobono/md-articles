# Rust's derive often implies inline

## Introduction
A recent release in our production service spiked the binary size by 40 KB after swapping a plain `#[derive(Debug)]` for a `#[derive(Instrument)]` on a generic enum. The build log showed no new dependencies, yet `cargo bloat --release` highlighted a surge in duplicated symbols. The root cause was not the trait’s implementation but the cascade of monomorphization and LLVM’s auto‑inlining heuristics that turned a single derive into megabytes of inline code across the crate’s generic usage sites.

## Why This Matters
Derive macros are a convenience, but they are not magic. They expand to concrete `impl` blocks that the compiler treats identically to hand‑written code. When those blocks sit inside generic types, each instantiation spawns its own copy of the generated functions. LLVM’s inliner then decides which of those copies are “hot” and forces them inline, often causing code bloat that is invisible to the eye but visible in binary size and compile‑time. Understanding this chain lets engineers keep performance predictable and avoid surprise size jumps in CI pipelines.

## How It Works
Derive expansion is a textual transformation performed at the macro level. The compiler receives the generated `impl` blocks as if they were written manually. If the surrounding type is generic, each concrete type that appears in the code triggers a monomorphization step, producing a fresh copy of those impl methods. LLVM then runs its inlining pass, which by default inlines functions marked `#[inline]` or those that appear “small and hot”. The derived impls often satisfy both conditions, so they get inlined aggressively, inflating the final binary.

## Core Concepts
- **Derive macro expansion**: A procedural macro that emits `impl SomeTrait for MyType { … }` at the token level. No runtime magic.
- **Monomorphization**: The compiler’s process of creating a unique version of generic code for each distinct set of type parameters.
- **Inlining heuristics**: LLVM’s default rule set that marks functions as `inline` based on size, call frequency, and attributes.
- **Code bloat**: The increase in binary size caused by duplicated inline functions across many monomorphized instances.

## Examples & Code Walkthrough
Below is a realistic domain model that demonstrates the problem. The example uses `#[derive(Instrument)]` from the `tracing` crate’s `instrument` macro, but the same pattern appears with `Clone`, `Debug`, `PartialEq`, etc.

```rust
// src/lib.rs
use tracing::Instrument;
use tracing::Span;

/// A request that can be traced and cloned for retries.
#[derive(Instrument, Clone, Debug, PartialEq)]
pub struct HttpRequest {
    /// The HTTP method.
    method: String,
    /// The request path.
    path: String,
    /// Optional query parameters.
    query: Option<std::collections::HashMap<String, String>>,
}

/// Manual implementation for comparison.
impl HttpRequest {
    #[inline(always)]
    fn new(method: &str, path: &str) -> Self {
        Self {
            method: method.to_string(),
            path: path.to_string(),
            query: None,
        }
    }
}

/* Generated by #[derive(Instrument)] (conceptually):
impl HttpRequest {
    fn span(&self) -> Span {
        Span::current().entered_child("http.request")
    }
}
impl<'a> Instrument for HttpRequest {
    type Output = ();
    fn wrap(self, inner: impl Future<Output = ()> + Send) -> impl Future<Output = ()> + Send {
        let span = self.span();
        async move {
            span.in_scope(|| inner.await)
        }.instrument(span)
    }
}
*/

/// A generic service that processes requests.
pub struct Service<T> {
    handler: fn(&T) -> Result<(), Box<dyn std::error::Error>>,
}

impl<T> Service<T> {
    pub fn new(handler: fn(&T) -> Result<(), Box<dyn std::error::Error>>) -> Self {
        Self { handler }
    }
}

/// Process a request, spawning a span for each call.
pub async fn process_request<R>(req: R) -> Result<(), Box<dyn std::error::Error>>
where
    R: Instrument, // Instrument is a trait bound that the derive supplies
{
    // The derive inserts a span around this block.
    let span = Span::current().entered_child("process");
    async move {
        (req.handler)(&req).instrument(span).await
    }.await
}
```

**Observations**

- The `#[derive(Instrument)]` creates an `impl Instrument for HttpRequest` that wraps futures with a span. The generated `wrap` method is tiny and marked `#[inline]` by default.
- Because `Service<T>` is generic, each concrete type `HttpRequest` that satisfies `Instrument` will monomorphize `process_request`. The inlined `wrap` appears in every instance, duplicating the same few bytes of code.
- The `#[inline(always)]` on `HttpRequest::new` is a separate concern, but it illustrates how developers can inadvertently compound the problem.

## Best Practices
1. **Inspect generated code** with `cargo expand` or `rustc -Zunpretty=expanded` to confirm the impl signatures.
2. **Guard hot derives** with `#[inline(never)]` on the generated wrapper if the proc‑macro supports it. Many custom derives expose an attribute to suppress inlining.
3. **Feature‑gate heavy derives** (e.g., `#[derive(Clone)]` on structs with many fields) for `debug` or `test` builds only.
4. **Break monomorphization chains** by wrapping types in newtypes that are not generic, or by using `#[derive]` on non‑generic structs.
5. **Leverage `#[optimize(size)]`** (nightly) on generic functions that rely on derived traits to keep the optimizer focused on size rather than speed.

## Common Mistakes & Anti-Patterns
| Mistake | Why it hurts | Fix |
|---------|--------------|-----|
| Deriving `Clone` on a 16‑field struct used in a hot generic loop. | Each monomorphized clone impl is inlined, inflating the binary and increasing instruction cache pressure. | Implement `Clone` manually and place `#[inline(never)]` on the generated methods, or split the struct into smaller components. |
| Assuming `#[derive(Debug)]` is free. | The generated `fmt::Debug` impl often contains match arms that are duplicated per monomorphized type, leading to extra code. | Use `#[derive(Debug)]` only when necessary; otherwise, implement `Display` or `Debug` selectively. |
| Relying on `#[derive]` for `Copy` on a large enum. | `Copy` generates a `Clone`-like impl that is inlined, causing large copies to be duplicated at compile time. | Derive `Clone` only and use `#[inline(never)]` on the clone impl, or restructure the enum to be `Copy` only when small. |
| Ignoring LTO interactions. | Even with `#[inline(never)]` the compiler may still inline across translation units when Link‑Time Optimization is enabled. | Run `cargo build --release --features lto` to see the impact, or disable LTO for debug builds. |

## Performance Considerations
- **Binary size**: Each inlined derived method adds roughly the size of its machine code. For a generic enum with 4 variants and 40 bytes per impl, 100 monomorphizations can add ~160 KB.
- **Compile time**: Inlining derived code forces the compiler to process larger functions in each translation unit, increasing LLVM’s optimization time.
- **Cache behavior**: Duplicated inline code pollutes instruction caches, especially on CPUs with limited I‑cache per core. Profiling with `perf` or `llvm‑prof` often reveals spikes in cache‑miss rates after a heavy derive is introduced.

## Frequently Asked Questions (FAQ)
**Q: Does `#[derive]` always cause inlining?**  
A: Not always. If the derived impl contains large functions, or if the compiler decides they are not hot, they may stay out‑of‑line. However, the default behavior is to treat them like any other `impl` method, making inlining likely.

**Q: Can I disable inlining for a specific derive?**  
A: You can add `#[inline(never)]` to the generated wrapper if the proc‑macro supports it. Otherwise, consider implementing the trait manually and annotating the methods with `#[inline(never)]`.

**Q: What about `#[derive(Copy)]`?**  
A: `Copy` generates a trivial `Clone`-like implementation that is often inlined. Use it sparingly on large types; prefer `Clone` with `#[inline(never)]` for larger payloads.

**Q: Does this affect debug builds?**  
A: Debug builds have less aggressive inlining, but the monomorphization cost remains. Use `#[inline(never)]` or feature‑gate derives in debug builds to keep compile times manageable.

**Q: How do I measure the impact?**  
A: Run `cargo bloat --release` to see size contributions, and `cargo build --profile dev` to compare compile times. The `objdump -t` output can reveal duplicated symbols for derived traits.

## Conclusion
Derive macros are a powerful shorthand, but they are not invisible. The token‑level expansion they perform feeds directly into the compiler’s monomorphization and inlining pipelines, often causing binary bloat that developers do not anticipate. By recognizing the chain—derive → impl → monomorphization → inlining—engineers can apply targeted mitigations such as `#[inline(never)]`, feature‑gated derives, or manual trait implementations. The result is a more predictable performance profile, smaller binaries, and faster compilation cycles, all of which are essential for production‑grade Rust codebases.
