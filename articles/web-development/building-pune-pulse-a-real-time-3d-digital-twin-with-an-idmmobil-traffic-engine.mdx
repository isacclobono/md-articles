   *## Introduction*
   City traffic simulation usually falls into two camps: abstract cellular automata that run fast but ignore physics, or heavy macroscopic models that choke on real-time constraints. When we started Pune Pulse, we needed a middle ground. We wanted a browser-based 3D digital twin that could ingest live GPS telemetry, simulate microscopic vehicle dynamics, and render tens of thousands of entities at 60fps without melting client GPUs. The answer wasn't a custom physics engine from scratch. It was adapting the Intelligent Driver Model (IDM) and MOBIL lane-changing algorithm for the web, paired with a deterministic state-sync layer. This article breaks down exactly how we architected the stack, calibrated the simulation for Indian road conditions, and bridged heavy numerical computation with lightweight WebGL rendering.

   *## Why This Matters*
   Urban mobility platforms are moving from static dashboards to interactive digital twins. The engineering friction lies in the simulation-to-rendering handoff. Most teams try to run the simulation on the client, which breaks determinism and drains mobile batteries. Others push everything to a backend, creating a bottleneck that collapses under WebSocket backpressure. Pune Pulse solves this by decoupling the physics step from the render loop, using a fixed-timestep simulation worker and a client-side interpolation layer. If you are building real-time spatial applications, fleet tracking systems, or traffic visualization tools, understanding this separation of concerns prevents the latency spikes and frame drops that kill user trust.

   *## How It Works*
   The architecture operates on a strict producer-consumer pipeline. Raw vehicle telemetry streams into an ingestion service that filters noise and maps coordinates to an H3 spatial grid. The grid feeds a pool of simulation workers running the IDM/MOBIL logic at a fixed 10Hz tick rate. Instead of broadcasting full state snapshots, a delta compressor calculates position and velocity changes, packing them into a binary WebSocket protocol. The browser client receives these ticks, runs a deterministic integrator to smooth movement between frames, and hands the final transforms to Three.js instanced meshes.


   The flow is intentionally linear to preserve causality. Telemetry arrives asynchronously, but the simulation worker enforces a strict clock. When network jitter drops packets, the client interpolator fills the gap using recorded velocity vectors. The H3 index prevents O(N²) neighbor lookups during lane-change calculations. Every component is stateless except the simulation worker, which holds the authoritative vehicle registry. This design keeps the backend horizontally scalable while guaranteeing the frontend receives a consistent, physics-compliant world state.

   *## Core Concepts*
   Three principles govern the system:
   1. **Fixed-Timestep Simulation:** Physics calculations run at a constant Δt regardless of network latency or render frame rate. This eliminates drift and ensures identical simulations across different hardware.
   2. **Spatial Partitioning for O(1) Neighbor Queries:** IDM requires knowing the distance and relative speed to the leading vehicle. MOBIL requires checking adjacent lanes. We use Uber's H3 hexagonal indexing to bucket vehicles by geographic cell, reducing neighbor discovery from a full graph scan to a localized cell query.
   3. **Delta Compression & Binary Framing:** JSON is too heavy for 10Hz updates across thousands of entities. We serialize state changes into fixed-size byte buffers using `DataView`, transmitting only delta position, delta heading, and velocity magnitude. This cuts bandwidth by ~70% compared to payload-heavy JSON formats.

   *## Examples & Code Walkthrough*
   The IDM acceleration function dictates how a vehicle reacts to the car ahead. In production, we had to adjust the standard parameters to account for tighter following distances and higher speed variance typical in Pune.

   ```typescript
   // IDM Acceleration Model (Calibrated for Urban Indian Traffic)
   export function calculateIdmAcceleration(
     egoSpeed: number,
     distToLeader: number,
     relativeSpeed: number,
     vehicleLength: number,
     simParams: {
       desiredSpeed: number;
       comfortableAccel: number;
       maxDecel: number;
       minGap: number;
       timeHeadway: number;
       accelerationExponent: number;
       decelerationExponent: number;
     }
   ): number {
     const {
       desiredSpeed,
       comfortableAccel,
       maxDecel,
       minGap,
       timeHeadway,
       accelerationExponent,
       decelerationExponent
     } = simParams;

     // Prevent division by zero when no leader exists
     if (distToLeader === Infinity || distToLeader < vehicleLength + minGap) {
       return -maxDecel;
     }

     const effectiveGap = distToLeader - vehicleLength;
     const headwayTerm = timeHeadway * relativeSpeed;
     const gapTerm = (minGap * minGap) / (effectiveGap - minGap);

     // Standard IDM formula with calibrated exponents
     const acceleration = comfortableAccel * (
       1 - Math.pow(egoSpeed / desiredSpeed, accelerationExponent) -
       Math.pow(headwayTerm + gapTerm, decelerationExponent)
     );

     // Clamp to physical limits to prevent simulation instability
     return Math.max(-maxDecel, Math.min(comfortableAccel, acceleration));
   }
   ```

   The function runs inside a `WebWorker` to avoid blocking the main thread. We pass `timeHeadway` values slightly lower than European defaults (0.8s vs 1.5s) to match local driving behavior. The clamping step is critical; without it, floating-point drift occasionally pushes acceleration beyond physical limits, causing vehicles to tunnel through each other during high-density gridlock.

   For lane changes, MOBIL evaluates incentive, safety, and politeness. We compute a propensity score per adjacent lane:

   ```typescript
   // MOBIL Lane Change Propensity Calculator
   export function evaluateMobilLaneChange(
     egoSpeed: number,
     leaderSpeed: number,
     followerSpeed: number,
     jerkTolerance: number,
     politenessFactor: number
   ): number {
     // Incentive: acceleration gain for ego and follower
     const egoIncentive = calculateIdmAcceleration(egoSpeed, Infinity, 0, 4.5, defaultParams);
     const followerIncentive = calculateIdmAcceleration(followerSpeed, Infinity, 0, 4.5, defaultParams);
     const currentFollowerIncentive = calculateIdmAcceleration(followerSpeed, 20, egoSpeed - followerSpeed, 4.5, defaultParams);

     const incentiveMetric = (1 + politenessFactor) * followerIncentive + egoIncentive - currentFollowerIncentive;

     // Safety check: follower must not brake harder than jerk tolerance
     const isSafe = currentFollowerIncentive > -jerkTolerance;

     return isSafe ? incentiveMetric : -Infinity;
   }
   ```

   We set `politenessFactor` to 0.2 instead of the academic 0.1. Real-world data showed that overly aggressive lane changes destabilize the simulation, causing phantom traffic waves. The safety threshold prevents the model from allowing cuts-in that force the follower into emergency braking.

   *## Best Practices*
   - **Run simulation in a WebWorker or dedicated backend process.** Never couple physics steps to `requestAnimationFrame`. Frame rate drops will corrupt time deltas and break determinism.
   - **Serialize state with `ArrayBuffer` and `DataView`.** Avoid JSON for high-frequency telemetry. Binary packing reduces GC pressure and network serialization overhead.
   - **Implement client-side dead reckoning.** When WebSocket packets drop, extrapolate position using the last known velocity and heading. Fade the entity opacity to signal interpolation to the user.
   - **Cache route graphs in memory.** Loading road topology from disk on every tick kills performance. Use a flat key-value store or in-memory adjacency list for lane connectivity.

   *## Common Mistakes & Anti-Patterns*
   1. **Variable Timestep Physics:** Using `performance.now()` delta between frames as the simulation step causes speedups on high-refresh monitors and slowdowns on low-end devices. Fix: Decouple simulation time from render time. Run physics at a fixed 10Hz, accumulate leftover time, and interpolate visuals.
   2. **O(N²) Neighbor Lookups:** Iterating through all vehicles to find the car ahead scales terribly. Fix: Use a spatial grid (H3 or uniform voxel grid) to limit queries to immediate neighbors.
   3. **Blocking the Main Thread with Geometry Updates:** Updating thousands of Three.js meshes per frame triggers layout thrashing and GC pauses. Fix: Use `InstancedMesh` with a pre-allocated buffer geometry. Update the instance matrix array directly instead of modifying individual scene graphs.
   4. **Ignoring Network Backpressure:** Broadcasting full state snapshots to every connected client floods the WebSocket gateway. Fix: Implement a publish-subscribe spatial filter. Only send updates to clients viewing a specific geographic region, and throttle updates based on client viewport relevance.

   *## Performance Considerations*
   The simulation worker processes ~15,000 vehicles at 10Hz on a modern CPU core. The bottleneck is not the IDM formula itself, but the neighbor discovery and matrix math. We mitigated this by precomputing lane connectivity matrices and using typed arrays (`Float32Array`) for position storage. Memory allocation drops to near zero after initialization because we reuse buffers instead of creating new objects per tick.

   Network bandwidth scales linearly with connected clients, but spatial filtering reduces the effective payload by ~60%. A typical 10Hz update for a 10km² zone transmits roughly 450KB/s per client. The client interpolator runs at 60Hz, lerping between 10Hz ticks. This requires only two vector operations per entity per frame, keeping CPU overhead under 3ms on mid-range laptops.

   Garbage collection is the silent killer. We avoid closures inside the tick loop, use object pooling for temporary calculation vectors, and serialize binary data without intermediate string conversions. Profiling with Chrome DevTools shows heap usage stabilizing after 15 minutes of continuous operation.

   *## Frequently Asked Questions (FAQ)*
   **Q: Can this run on mobile devices?**
   A: Yes, but you must reduce the simulation tick rate to 5Hz and aggressively cull entities outside the frustum. Use `InstancedMesh` with a lower polygon count and disable shadow casting. The interpolation layer handles the lower tick rate smoothly.

   **Q: How do you handle WebSocket disconnections?**
   A: The client caches the last 30 ticks of state. On reconnection, it requests a full state snapshot, syncs the authoritative clock, and resumes interpolation. The server maintains a sliding window cache to serve catch-up packets without recomputing history.

   **Q: Why not use a cellular automata model like Nagel-Schreckenberg?**
   A: Cellular models are faster but lack continuous velocity and smooth acceleration curves. For a 3D digital twin requiring realistic braking distances and lane-change physics, IDM/MOBIL provides the necessary granularity without sacrificing performance.

   **Q: How do you calibrate parameters for different cities?**
   A: We collect anonymized GPS traces, compute average following distances, speed variance, and lane-change frequency. These metrics feed into a calibration script that adjusts `timeHeadway`, `politenessFactor`, and `maxDecel` until the simulated flow matches observed traffic density.
