# Docker Cloud Sandboxes Provide a Consistent Sandbox Abstraction Across Laptop and Cloud

## Introduction
Development teams that target the cloud often find that local environments drift from production. A Python script that runs locally may fail when the same code is deployed to a Kubernetes cluster because of subtle differences in library versions, system libraries, or resource limits. For AI‑centric workloads—where training, inference, and experimentation are tightly coupled to hardware—this inconsistency becomes a costly blocker. The solution is a **sandbox abstraction** that lets a developer describe *what* they need (resources, networking, security) and automatically receive an isolated execution context that behaves identically on a laptop and in the cloud.

## Why This Matters
When a model training job runs on a developer’s machine, it can consume up to 100 % of the CPU and 32 GB of RAM. The same job, when moved to a cloud environment, may be throttled by a default quota or placed on a node with a different kernel version. The result is “it works on my machine” but fails in CI, or worse, a production inference service that returns stale results because the container ran on a different base image.

A unified sandbox model eliminates these failures by:

* **Deterministic resource guarantees** – CPU, memory, and GPU limits are expressed once and enforced everywhere.  
* **Portable security posture** – capabilities, sysctls, and filesystem mounts are defined in a manifest and applied uniformly.  
* **Zero‑trust lifecycle management** – sandboxes are created, inspected, and destroyed through a single API, simplifying audit trails.  
* **AI‑aware provisioning** – the same AI model that predicts optimal training resources can drive sandbox scaling both locally and on‑prem.

## How It Works
The flow from a developer’s editor to a running sandbox is orchestrated by a set of cooperating services. The diagram below visualizes the core interaction pattern.

1. **Manifest authoring** – The developer creates a `sandbox.yaml` (or `docker‑compose.yml`‑style) that defines image, resource limits, mounts, networking, and security options.  
2. **Local validation** – The `docker` CLI reads the manifest, validates it against a JSON schema, and can launch a sandbox instantly using the host’s Docker daemon. This gives rapid feedback at zero cost.  
3. **Cloud request** – The same manifest is uploaded to the Cloud Sandbox API (a thin wrapper around gRPC/REST). The API authenticates the request, stores the spec in a control‑plane database, and triggers the orchestrator.  
4. **AI‑assist prediction** – Before the orchestrator creates the sandbox, it calls the AI‑Assist service with workload metadata (e.g., model size, batch size). The service returns a resource profile (CPU cores, memory, GPU count) that is merged into the final sandbox spec.  
5. **Provisioning** – The orchestrator expands the spec into a Docker container definition, selects a node pool, and submits the job to the cloud’s container runtime (Docker on Linux VMs, gVisor, or Kata Containers). It also registers the sandbox ID in the observability stack.  
6. **Lifecycle & monitoring** – The orchestrator watches for events (start, health check failure, termination). Metrics flow to Loki/Elastic, traces to OpenTelemetry, and the AI layer can react to anomalies (e.g., CPU spikes) by scaling the sandbox up or down.  
7. **Feedback loop** – Developers receive real‑time logs and can attach to the sandbox via SSH or a web shell. The AI layer records outcomes (training time, accuracy) to improve future predictions.

## Core Concepts
A **sandbox** is an isolated execution context that guarantees a set of resources and security controls. The abstraction is built around three pillars:

* **Specification** – A JSON/YAML schema (`sandbox.yaml`) that captures image, entrypoint, resource limits, bind mounts, network aliases, capabilities, and security options.  
* **Runtime** – Docker’s native isolation (namespaces, cgroups, rootless mode) on the laptop; a managed Docker runtime (Docker Engine on VMs, gVisor, or Kata) in the cloud.  
* **Control Plane** – A Kubernetes‑based controller that reconciles the spec, communicates with the AI‑Assist service, and enforces policies via OPA.

The **Sandbox Manager** (Go service) implements the reconciliation loop:

```go
// sandbox_manager.go
package main

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"time"

	"github.com/yourorg/sandbox-api/proto/sandboxpb"
	"google.golang.org/grpc"
	"google.golang.org/grpc/credentials/insecure"
)

// SandboxSpec mirrors the YAML/JSON schema used by developers.
type SandboxSpec struct {
	Image          string            `json:"image"`
	CPU            int               `json:"cpu"`
	MemoryGB       int               `json:"memory_gb"`
	Mounts         []MountSpec       `json:"mounts"`
	Network        NetworkSpec        `json:"network"`
	Security       SecuritySpec       `json:"security"`
	GPUs           int               `json:"gpus,omitempty"`
	Entrypoint     []string          `json:"entrypoint,omitempty"`
	Env            map[string]string `json:"env,omitempty"`
}

// MountSpec describes a host‑to‑container bind mount.
type MountSpec struct {
	HostPath string `json:"host_path"`
	MountPath string `json:"mount_path"`
	ReadOnly bool   `json:"read_only,omitempty"`
}

// NetworkSpec defines networking constraints.
type NetworkSpec struct {
	Alias string `json:"alias,omitempty"`
	Port  int    `json:"port,omitempty"`
}

// SecuritySpec captures capability and sysctl settings.
type SecuritySpec struct {
	Capabilities []string `json:"capabilities,omitempty"`
	Sysctls      map[string]string `json:"sysctls,omitempty"`
}

// SandboxManager watches the control‑plane for new specs and creates containers.
type SandboxManager struct {
	client sandboxpb.SandboxServiceClient
}

// CreateSandbox receives a spec, enriches it with AI predictions, and hands it to the cloud runtime.
func (sm *SandboxManager) CreateSandbox(ctx context.Context, spec *SandboxSpec) (*sandboxpb.SandboxResponse, error) {
	// 1. Call AI‑Assist for resource tuning.
	pred, err := sm.queryAIAssist(ctx, spec)
	if err != nil {
		return nil, fmt.Errorf("AI assist query failed: %w", err)
	}
	// Merge predictions (simple example: override CPU/Memory if AI suggests higher values).
	if pred.CPU > spec.CPU {
		spec.CPU = pred.CPU
	}
	if pred.MemoryGB > spec.MemoryGB {
		spec.MemoryGB = pred.MemoryGB
	}

	// 2. Serialize spec to protobuf.
	pbSpec, err := toProto(spec)
	if err != nil {
		return nil, fmt.Errorf("spec serialization failed: %w", err)
	}

	// 3. Forward to the cloud runtime via gRPC.
	resp, err := sm.client.Create(ctx, &sandboxpb.CreateRequest{Spec: pbSpec})
	if err != nil {
		return nil, fmt.Errorf("cloud runtime Create failed: %w", err)
	}
	log.Printf("Sandbox created: ID=%s, Node=%s", resp.Id, resp.Node)
	return resp, nil
}

func main() {
	conn, err := grpc.Dial("sandbox-control-plane:50051", grpc.WithTransportCredentials(insecure.NewCredentials()))
	if err != nil {
		log.Fatalf("failed to dial control plane: %v", err)
	}
	client := sandboxpb.NewSandboxServiceClient(conn)
	manager := &SandboxManager{client: client}

	// Example: load a spec from a file and create a sandbox.
	spec := &SandboxSpec{
		Image:    "python:3.11-slim",
		CPU:      2,
		MemoryGB: 4,
		Mounts: []MountSpec{
			{HostPath: "/home/dev/project", MountPath: "/workspace", ReadOnly: true},

	ctx, cancel := context.WithTimeout(context.Background(), 30*time.Second)
```

## Examples & Code Walkthrough
### 1. Local Sandbox Creation (Python)
The snippet below shows a production‑grade helper that builds a Docker container with strict resource limits and read‑only mounts. It includes error handling, validation of the host path, and explicit capability management.

```python
# sandbox_local.py
import docker
import logging
from pathlib import Path
from docker.errors import DockerException, APIError

logging.basicConfig(level=logging.INFO)
logger = logging.getLogger("sandbox_local")

def validate_host_path(path: Path) -> None:
    """Ensure the host path exists and is a directory."""
    if not path.exists():
        raise ValueError(f"Host path does not exist: {path}")
    if not path.is_dir():
        raise ValueError(f"Host path is not a directory: {path}")

def create_sandbox(project_path: Path, cpu: int = 2, mem_gb: int = 4) -> docker.models.containers.Container:
    """
    Spawn a Docker sandbox on the local machine with the given resource limits.
    Returns the container object for further inspection or attachment.
    """
    validate_host_path(project_path)

    try:
        client = docker.from_env()
    except DockerException as e:
        logger.error("Failed to connect to Docker daemon: %s", e)
        raise

    # Convert GB to bytes; Docker SDK expects MemoryBytes.
    mem_bytes = mem_gb * 1024 * 1024 * 1024
    nano_cpus = cpu * 1_000_000_000

    # Build a minimal security profile.
    container_config = {
        "Image": "python:3.11-slim",
        "Command": "sleep infinity",
        "Name": f"sandbox-{project_path.name}",
        "CpuShares": 0,  # No fairness weighting, pure limit.
        "NanoCpus": nano_cpus,
        "Memory": mem_bytes,
        "MemorySwap": 0,  # Disable swap for deterministic behavior.
        "ReadOnly": False,  # Container FS is read‑write; host mounts can be read‑only.
        "SecurityOpt": ["no-new-privileges:true"],
        "CapAdd": ["SETPCAP"],  # Minimal needed capability.
        "CapDrop": ["ALL"],
        "Volumes": {str(project_path): {"bind": "/workspace", "mode": "ro"}},
        "Detach": True,
        "Tty": False,
    }

    try:
        container = client.containers.run(**container_config)
        logger.info("🟢 Local sandbox started: %s", container.id)
        return container
    except APIError as e:
        logger.error("Docker API error while creating sandbox: %s", e)
        raise

if __name__ == "__main__":
    # Example invocation from the project root.
    project = Path.cwd() / "my-ai-project"
    try:
        create_sandbox(project, cpu=4, mem_gb=8)
    except Exception as e:
        logger.critical("Sandbox creation aborted: %s", e)
        exit(1)
```

Key points:

* **Defensive validation** – the host path is checked before Docker interaction.
* **Explicit resource limits** – `NanoCpus` and `Memory` guarantee the sandbox cannot exceed the requested quota.
* **Least‑privilege capabilities** – only `SETPCAP` is added; everything else is dropped.
* **Read‑only mount** – the project directory is exposed read‑only to prevent accidental writes.
