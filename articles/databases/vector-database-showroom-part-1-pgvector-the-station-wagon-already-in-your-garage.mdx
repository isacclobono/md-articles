# Vector database showroom. Part 1 pgvector — The Station Wagon Already in Your Garage.

## Introduction  
Similarity search has become a cornerstone of modern AI‑powered products. From semantic search across product catalogs to recommendation engines that surface relevant articles based on intent, the ability to compare vectors quickly is more valuable than ever. PostgreSQL ships with the `vector` extension, exposing a familiar RDBMS interface while delivering sub‑millisecond approximate nearest‑neighbor lookups. For teams already running a robust relational database layer, adding a purpose‑built vector engine may seem unnecessary at first glance. Yet treating a well‑tuned `pgvector` instance as a lightweight vector store often reduces operational overhead and leverages existing tooling. Think of it as the reliable station wagon sitting in the garage—capable, familiar, and ready for the road without demanding a brand‑new fleet.

## Why This Matters  
Embedding generation is cheap compared with high‑resolution image retrieval, yet efficient ranking remains hard enough on its own. By keeping everything within one database system, we eliminate cross‑service data shuffling, simplify backup pipelines, and benefit from native query tracing. For organizations that still rely heavily on PostgreSQL for transactions and reporting, moving just the vector workload onto that platform yields immediate productivity gains while preserving consistency guarantees that many teams fear when adopting separate vector databases.

## How It Works  

Below is a compact illustration of the end‑to‑end flow: a CSV file supplies raw documents, a Python service encodes each entry with a transformer model, then batches the results for insertion. After insertion, the same table benefits from dedicated indexes that accelerate both exact and approximate searches. The diagram captures the critical steps from input to query execution.

```mermaid
    H --> J[Top‑k results returned]
```

### Step‑by‑step break down  

1. **Loading** – The CSV contains pairs such as `doc123, "Project briefing"`. Each row receives a unique `source_id`.  
2. **Encoding** – We instantiate a pretrained model (`all-MiniLM-L6-v2` by default) and call `.encode()` which returns a normalized float32 vector. Normalization ensures cosine similarity equals Euclidean distance after the `_nnref` operation.  
3. **Batching** – To keep round‑trip latency low, batches of up to five hundred rows are assembled. The helper `_upsert_batch` sends a single `INSERT … ON CONFLICT` statement per batch, committing after every batch.  
4. **Conflict resolution** – When a `source_id` already exists, the update clause refreshes the raw text and timestamp while preserving previously stored coordinates.  
5. **Indexing** – Two complementary index types make the table work for both near‑exact matches and fuzzy recalls. The `ivfflat` method groups vectors into coarse buckets and runs a flat tree inside each bucket for fast distance computation. The `hnsw` index builds a graph structure optimized for high recall under moderate memory footprints.  

## Core Concepts  

* **`vector` data type** – Stores a fixed‑dimensional array of floats with a defined size. Unlimited precision is available because PostgreSQL manages the binary representation behind the scenes.  
* **Storage layout** – The column `embedding` holds the whole vector; the `created_at` timestamp supports time‑based pruning policies. Because the column is non‑nullable, each record always carries a comparable metric.  
* **Index mechanics** –  
  * **IVFFlat** partitions space into clusters, allowing quick elimination of far‑away candidates before deeper traversals.  
  * **HNSW** constructs multi‑layered proximity graphs; search walks upward, jumping between layers to locate the target neighbourhood efficiently.  
* **Granularity control** – Selecting `vector(384)` works well for distilled models like MiniLM, reducing storage while retaining sufficient expressiveness for short passages. Longer contexts typically demand larger dims (e.g., 768 for BERT‑base).  

## Examples & Code Walkthrough  

### Database schema  

```sql
CREATE TABLE document_embeddings (
    id              BIGSERIAL PRIMARY KEY,
    source_id       TEXT NOT NULL,          -- external logical identifier
    content         TEXT,                  -- optional raw text for audit or re‑encoding
    embedding        VECTOR(384) NOT NULL,  -- the vector itself
    created_at      TIMESTAMPTZ DEFAULT now()
);

-- Exact‑search index (optional, useful for small corpora)
CREATE INDEX idx_doc_source ON document_embeddings (source_id);

-- Approximate index using IVFFlat (good balance of memory and speed)
CREATE INDEX idx_doc_ivfflat
    USING ivfflat (embedding vector_l2_ops)
    WITH (lists = 100);

-- Approximate index using HNSW (requires PG ≥ 15)
CREATE INDEX idx_doc_hnsw
    USING hnsw (embedding vector_l2_ops)
    WITH (m = 16, ef_construction = 64);
```

### Python loader implementation  

```python
import csv
import os
from pathlib import Path
from typing import List, Tuple

import psycopg2
from psycopg2.extras import execute_values
from sentence_transformers import SentenceTransformer

# Configuration ---------------------------------------------------------
MODEL_NAME = "all-MiniLM-L6-v2"          # lightweight, fast inference
BATCH_SIZE = 500                         # tune based on memory pressure
CSV_PATH   = "documents.csv"             # expected columns: source_id, content


def create_indexes(conn: psycopg2.connection) -> None:
    """Create the two approximate indexes once."""
    with conn.cursor() as cur:
        cur.execute("""
            CREATE INDEX IF NOT EXISTS idx_doc_ivfflat
                USING ivfflat (embedding vector_l2_ops)
                WITH (lists = 100);
        """)
        cur.execute("""
            CREATE INDEX IF NOT EXISTS idx_doc_hnsw
                USING hnsw (embedding vector_l2_ops)
                WITH (m = 16, ef_construction = 64);
        """)


def load_embeddings(csv_path: str, dsn: str) -> None:
    """
    Encode CSV rows and upsert into document_embeddings.
    Handles transient failures gracefully by retrying individual rows.
    """
    model = SentenceTransformer(MODEL_NAME)   # lazy init avoids warm‑up delay
    try:
        with psycopg2.connect(dsn) as conn:
            create_indexes(conn)

            with open(csv_path, newline="", encoding="utf-8") as f:
                reader = csv.DictReader(f)
                batch: List[Tuple[str, str, List[float]]] = []

                for row in reader:
                    source_id = row["source_id"].strip()
                    text = row["content"].strip()

                    if not source_id or not text:
                        continue  # skip malformed entries

                    # Compute normalized embedding
                    try:
                        vec = model.encode(text, normalize_embeddings=True).tolist()
                    except Exception as e:
                        # Log error and move on; do not abort whole job
                        print(f"Failed to encode {source_id}: {e}")
                        continue

                    batch.append((source_id, text, vec))
                    if len(batch) >= BATCH_SIZE:
                        _upsert_batch(conn, batch)
                        conn.commit()
                        batch.clear()

                # Flush remaining rows
                if batch:
                    _upsert_batch(conn, batch)
                    conn.commit()

    except Exception as exc:
        # Propagate unexpected errors, but never swallow silently
        raise RuntimeError(f"Database pipeline failed: {exc}") from exc


def _upsert_batch(conn: psycopg2.connection, rows: List[Tuple]) -> None:
    """
    Insert a batch of rows, updating on duplicate source_id.
    Uses a bulk statement via execute_values for optimal throughput.
    """
    # Build parameter list: (source_id, content, embedding)
    params = [
        (src, txt, vec)
        for src, txt, vec in rows
    ]

    sql = """
        INSERT INTO document_embeddings (source_id, content, embedding)
        VALUES %s
        ON CONFLICT (source_id) DO UPDATE
        SET content = EXCLUDED.content,
            embedding = EXCLUDED.embedding,
            created_at = now();
    """

    try:
        execute_values(
            conn,
            sql,
            params,
            template="(%s, %s, %s)",
        )
    except psycopg2.Error as db_err:
        # If something went wrong during the bulk upsert, rollback the batch
        conn.rollback()
        raise RuntimeError(f"Upsert failed: {db_err}") from db_err
```

### Key design decisions highlighted  

* **Batch sizing** – Larger batches improve CPU utilization but increase memory consumption during transformation. In practice we start with 500 rows; adjust based on GPU or CPU headroom.  
* **`ON CONFLICT DO UPDATE`** – Guarantees eventual consistency without reading the table repeatedly. The `now()` timestamp keeps the collection fresh for time‑based expiry strategies.  
* **Normalized vectors** – Applying L2 normalization beforehand lets us treat Euclidean distance as cosine similarity, simplifying downstream ranking logic.  

## Best Practices  

- **Version alignment** – Keep the `pgvector` version synchronized with the PostgreSQL release you run; minor updates add support for higher‑dimensional types but most features remain stable.  
- **Dimensional selection** – Start with 128–256 dimensions for short documents; switch to 384 or 768 when context windows exceed 200 tokens. Profile memory usage (`SELECT pg_size_pretty(pg_total_virtual_file_size);`) before scaling.  
- **Index maintenance** – Rebuild `ivfflat` indexes periodically (e.g., nightly) and monitor `hits` and `seeks` metrics in `pg_stat_user_indexes`.  
- **Security** – Grant read/write privileges on the table rather than on the whole database. Use parameterized queries to prevent injection through the CSV payload.  
- **Monitoring** – Export query latency via `pg_stat_statements` and watch for spikes caused by concurrent heavy vector loads.  

## Common Mistakes & Anti‑Patterns  

1. **Treating the table as immutable** – Updating `created_at` on every conflict forces the entire row replacement, which can cause unnecessary disk writes. Instead, only touch `created_at` when business rules dictate a new timestamp.  
2. **Ignoring memory fragmentation** – Very large corpora can exhaust RAM when storing full‑precision floats. Consider storing lower‑precision `BYTEA` representations (e.g., 8‑bit quantization) and decoding only when necessary.  
3. **Assuming uniform vector quality** – Different sources exhibit varying semantic density. A single model may overfit to some domains, degrading relevance elsewhere. Run a validation split and benchmark multiple models before committing.  
4. **Skipping conflict detection logic** – Without `ON CONFLICT`, repeated runs would either duplicate records or silently overwrite outdated versions, leading to stale metadata.  

## Performance Considerations  

* **CPU cost** – Encoding dominates runtime; choose a lighter model for low‑traffic services. Batch processing amortizes the model initialization overhead.  
* **Network latency** – All operations stay within a single node, so round‑trip delays are minimal compared to distributed vector stores.  
* **Scalability ceiling** – With PG 15+, HNSW supports tens of millions of vectors comfortably. Beyond that, consider sharding by `source_id` hash and replicating hot partitions across nodes.  
* **Complexity class** – Exact search is bounded by O(N·D) in the worst case, whereas HNSW achieves O(log N) average lookup. For interactive UIs, the logarithmic guarantee translates to sub‑second response times even at scale.

## Frequently Asked Questions (FAQ)  

**Q: Does pgvector replace Elasticsearch?**  
A: No. It complements traditional search engines by providing ACID semantics and easy integration with existing relational schemas. Where pure inverted‑index capabilities are needed, you may still consult Elastic or another specialized engine.  

**Q: Can I use pgvector for very long documents?**  
A: Yes, but you must choose a higher dimensional space (e.g., 1024) to preserve discriminative power. Otherwise, lossy compression techniques like PCA can reduce dimension without catastrophic information loss.
