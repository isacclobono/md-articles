# Every AI-agent enforcement story this week is really about missing evidence

## Introduction
Last week three separate enforcement actions made headlines: a financial‑advising agent was fined for undisclosed risk disclosures, a hiring‑assistant bot was ordered to halt after biased screening logs could not be produced, and a healthcare triage agent faced a regulator’s demand for proof that its escalation paths followed clinical guidelines. In each case the core issue was not that the model gave a wrong answer—it was that nobody could reconstruct *what* the agent did, *when* it did it, and *why* it chose that path. The missing piece is verifiable evidence of the agent’s execution history.

## Why This Matters
Software teams have long treated logging as a diagnostic aid. With autonomous agents, regulators now treat that log as legal evidence. If you cannot produce a tamper‑proof, causally linked record of each decision, you expose the organization to fines, forced shutdowns, and reputational damage. Conversely, a solid evidence pipeline turns compliance from a reactive scramble into a provable property of the system, letting you ship agents faster because auditors can verify behavior on demand.

## How It Works
We propose an **Evidence Service** that sits between the agent runtime and any external system. Every meaningful action—policy check, tool call, state update—is turned into a signed, timestamped event that includes:

* A globally unique causal ID linking it to its predecessor.
* The agent instance ID and version.
* A hash of the input payload and the output payload.
* A reference to the policy rule that authorized the action.
* A cryptographic signature generated by a short‑lived key held in a hardware security module (HSM).

Events are appended to an immutable log (e.g., AWS QLDB, Azure Confidential Ledger, or an append‑only S3 bucket with Object Lock). A verifier can later replay the log, validate signatures, and reconstruct the exact decision tree for any time window.

**Step‑by‑step**

1. **Instrumentation** – A thin wrapper around the agent’s core loop captures entry/exit points of each policy‑guarded action.
2. **Event Builder** – Creates a JSON‑like structure with the fields above, computes a SHA‑256 hash of the concatenated input+output, and fetches the current causal ID from a monotonic counter stored per‑instance.
3. **Signing** – The builder hands the serialized event to an HSM client; the HSM returns an ECDSA‑P256 signature. The private key never leaves the HSM.
4. **Append** – The signed event is sent via a producer (Kafka, Kinesis, or gRPC) to the immutable log service. The log guarantees order and prevents rewrites.
5. **Verification** – An auditor runs a verifier that reads the log, checks each signature against the public key rotated daily, validates the causal chain, and optionally reproduces the agent’s deterministic policy engine to confirm that the recorded action matches the rule.

## Core Concepts

| Concept | Description |
|---------|-------------|
| **Causal ID** | A UUIDv5 derived from the parent event’s ID and a monotonically increasing sequence number. Guarantees a directed acyclic graph of events. |
| **Policy Reference** | A stable identifier (e.g., UUID) pointing to a version‑controlled policy document stored in a Git‑backed repo. Allows auditors to check the exact rule that was in force. |
| **Input/Output Hash** | SHA‑256 of the canonical JSON representation of the data the agent received and emitted for that step. Detects any tampering or replay. |
| **HSM‑Backed Signing** | Guarantees non‑repudiation: only the agent’s trusted signing key could have produced the signature. |
| **Immutable Log** | Append‑only storage with cryptographic chaining (like a blockchain) or cloud object lock, providing tamper‑evidence and easy replay. |
| **Verifier** | A stateless service that replays the log, validates signatures, and can generate a human‑readable audit trail or machine‑readable compliance evidence. |

## Examples & Code Walkthrough
Below is a simplified but production‑ready implementation in Go. It assumes an HSM client (`hsm.Signer`) that implements `Sign(msg []byte) (signature []byte, err error)` and a Kafka producer (`prod.Producer`) for the immutable log.

```go
package evidence

import (
	"context"
	"crypto/sha256"
	"encoding/hex"
	"encoding/json"
	"fmt"
	"time"

	"github.com/segmentio/kafka-go"
	"example.com/hsm" // placeholder for your HSM SDK
)

// Event represents a single auditable action.
type Event struct {
	CausalID      string    `json:"causal_id"`
	InstanceID    string    `json:"instance_id"`
	Timestamp     time.Time `json:"timestamp"`
	PolicyRef     string    `json:"policy_ref"`
	InputHash     string    `json:"input_hash"`
	OutputHash    string    `json:"output_hash"`
	Signature     string    `json:"signature"`
	SignatureAlg  string    `json:"signature_alg"` // e.g., "ECDSA-P256"
}

// NewEvent builds an Event from raw payloads.
func NewEvent(ctx context.Context, instanceID, policyRef string, in, out []byte, signer *hsm.Signer, prod *kafka.Writer) (*Event, error) {
	// 1. Compute hashes.
	inHash := sha256.Sum256(in)
	outHash := sha256.Sum256(out)

	// 2. Fetch or generate causal ID.
	// In a real system you would store a per‑instance counter in Redis or similar.
	causalID, err := getOrCreateCausalID(ctx, instanceID)
	if err != nil {
		return nil, fmt.Errorf("causal ID: %w", err)
	}

	// 3. Assemble unsigned event.
	unsigned := Event{
		CausalID:   causalID,
		InstanceID: instanceID,
		Timestamp:  time.Now().UTC(),
		PolicyRef:  policyRef,
		InputHash:  hex.EncodeToString(inHash[:]),
		OutputHash: hex.EncodeToString(outHash[:]),
		SignatureAlg: "ECDSA-P256",
	}

	// 4. Serialize for signing (deterministic order).
	b, err := json.Marshal(unsigned)
	if err != nil {
		return nil, fmt.Errorf("marshal: %w", err)
	}

	// 5. Sign via HSM.
	sig, err := signer.Sign(b)
	if err != nil {
		return nil, fmt.Errorf("sign: %w", err)
	}
	unsigned.Signature = hex.EncodeToString(sig)

	// 6. Persist to immutable log.
	if err = prod.WriteMessages(ctx, kafka.Message{
		Value: b,
	}); err != nil {
		return nil, fmt.Errorf("kafka write: %w", err)
	}

	return &unsigned, nil
}

// getOrCreateCausalID is a stub; replace with your store.
func getOrCreateCausalID(ctx context.Context, instanceID string) (string, error) {
	// Example: use a Redis INCR keyed by instanceID.
	// For brevity we return a random UUID.
	return fmt.Sprintf("%s-%d", instanceID, time.Now().UnixNano()), nil
}
```

## Best Practices
1. **Instrument early, instrument everywhere** – Wrap every external call, model inference, and policy decision. Missing a single point creates a blind spot that auditors will exploit.
2. **Keep the signing key short‑lived** – Rotate HSM‑backed keys daily or per‑instance and store the public key in a trusted key‑management service. This limits the damage if a key is compromised.
3. **Make the immutable log the source of truth** – Never rely on mutable databases for audit trails. If you need to query, create a read‑only replica that ingests from the log via change‑data‑capture.
4. **Validate on ingest** – Have the log service reject events that fail signature verification or that reuse a causal ID. This prevents malformed data from entering the chain.
5. **Provide a verification API** – Auditors should be able to submit a time window and receive a signed proof (Merkle root + inclusion proof) that the log segment has not been altered.
6. **Document the schema** – Version the Event JSON schema using something like JSON Schema or Protobuf. Include the schema ID in each event so future verifiers know how to parse older records.

## Common Mistakes & Anti‑Patterns
| Mistake | Why it’s risky | Fix |
|---------|----------------|-----|
| **Logging only the final output** | Loses the intermediate policy checks and tool calls; you cannot prove *how* the answer was derived. | Instrument each policy gate and external call as shown in the code. |
| **Using application‑level signatures** | If the private key lives in the same process as the agent, malware could extract it and forge events. | Delegate signing to an HSM or cloud KMS where the private key never leaves the secure boundary. |
| **Relying on mutable storage (e.g., Postgres) for audit** | Updates or deletions can erase evidence, violating non‑repudiation. | Use an append‑only store with object lock or a ledger database; treat the log as write‑once. |
| **Skipping causal linking** | Without a chain, you cannot reconstruct branching decisions or detect replay attacks. | Include a parent‑event ID or monotonic counter; verify the chain during validation. |
| **Ignoring schema evolution** | Older events become unreadable, breaking verification pipelines. | Encode a schema version in each event and maintain backward‑compatible readers/writers. |

## Performance Considerations
* **CPU overhead** – Signing with an HSM adds ~0.5‑2 ms per event on modern hardware; hashing is negligible (<0.1 ms). For high‑frequency agents (e.g., >10k events/sec) batch signatures or use a hardware accelerator.
* **Network latency** – The log append is a single RPC; with Kafka or Kinesis you typically see <5 ms 99th‑percentile latency in the same region. Cross‑region adds ~30‑50 ms.
* **Storage growth** – Each event is roughly 200‑400 bytes (JSON + signature). At 1k events/sec you generate ~30‑70 GB/day. Retention policies can be tiered: hot storage for 30 days, cold/archive for longer periods.
* **Scalability** – The pattern is horizontally scalable: multiple agent instances share the same log topic; the log service partitions by key (instanceID) to preserve order per instance while allowing parallel writes.
* **Back‑pressure** – If the log falls behind, the instrumentation middleware should apply a bounded queue and drop or buffer events according to your risk tolerance (e.g., drop non‑critical telemetry, retain policy‑check events).

## Real‑World Usage
- **Netflix** uses an event‑sourcing pipeline with Kafka and immutable S3 archives to audit recommendation‑model decisions for regulatory compliance in the EU.
- **Uber**’s Michelangelo platform signs each feature‑store lookup and model inference request with a Cloud HSM, storing the chain in an append‑only Cassandra cluster to satisfy audit requests from financial regulators.
- **Cloudflare**’s Workers AI service logs every invocation to a tamper‑proof log built on Flintrock (their internal ledger) enabling rapid response to data‑subject‑access‑requests and AI‑specific legislation.
- **Stripe Radar** records each fraud‑decision event with a cryptographic hash of the input features and the model version, allowing regulators to reconstruct the exact rule set that fired on a given transaction.

These organizations treat the evidence log as a first‑class system component, not an afterthought, and consequently can produce compliance artifacts on demand without scrambling for logs.
