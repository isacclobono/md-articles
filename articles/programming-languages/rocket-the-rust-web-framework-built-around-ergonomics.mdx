# Rocket: The Rust Web Framework Built Around Ergonomics

## Introduction
When we started building HTTP services in Rust, the language’s safety guarantees were a huge win, but the amount of boilerplate needed to wire routes, extract request data, and manage state felt heavy. Rocket tackles that friction by leaning into Rust’s type system and macro ecosystem so you can write handlers that look almost like plain functions while still getting zero‑cost abstractions and compile‑time guarantees.

## Why This Matters
In production, a web framework must deliver three things: correctness, performance, and developer velocity. Rust already gives you the first two; Rocket adds the third by reducing the ceremony around request validation, dependency injection, and error handling. Teams that adopt Rocket often see faster iteration on API contracts because the compiler catches mismatched inputs early, and the runtime overhead stays comparable to hand‑written async code.

## How It Works
Rocket’s core is a pipeline that transforms an incoming TCP connection into a typed request, runs user‑defined guards, invokes a handler, and then runs any configured fairings before sending the response. The framework uses a combination of compile‑time routing (via macros) and runtime type checking (via the `FromRequest` trait) to guarantee that a handler only receives data that satisfies its declared constraints.

```mermaid
flowchart TD
    A[TCP Connection] --> B[Request Init]
    B --> C{Routing}
    C -->|Match| D[Request Guards]
    D -->|Pass| E[Handler]
    D -->|Fail| F[Error Handler / Catcher]
    E --> G[Response Generation]
    G --> H{Fairings (Attach/Respond)}
    H --> I[Write to Socket]
    F --> H
```

**Step‑by‑step**

1. **Request Init** – Rocket reads raw bytes, builds a `Request` struct that holds headers, query string, and body.
2. **Routing** – The `#[get]`, `#[post]`, etc., macros generate a compile‑time map; the router looks up the handler based on method and path.
3. **Request Guards** – Each guard implements `FromRequest`. Rocket runs them in order; if any guard returns a failure, the request is short‑circuited to an error handler or a default catcher.
4. **Handler** – The user function receives only the successfully extracted values (typed, validated, and ready to use).
5. **Response Generation** – The handler returns a type that implements `Responder`; Rocket turns it into an HTTP response.
6. **Fairings** – Attach fairings run before the request is processed; Respond fairings run after the response is built, enabling logging, metrics, or header injection without cluttering handlers.

Because each stage is generic over lifetimes and types, the compiler can inline most of the logic, leaving virtually no runtime indirection beyond the actual work your handler does.

## Core Concepts
- **Routing Macros** – `#[get("/path")]`, `#[post("/path", data = "<body>")]`, etc., generate static route tables at compile time.
- **Request Guards** – Traits like `FromRequest` allow you to extract authenticated users, validate JSON payloads, or pull state from the application context. Guards can fail forward or return custom error types.
- **State** – Application‑wide data (e.g., a database connection pool) is stored in a `State<T>` type and injected via guards.
- **Fairings** – Hooks for cross‑cutting concerns. `Attach` fairings run at launch (good for DB pool initialization); `Respond` fairings run after a response is built (good for logging latency).
- **Catchers** – Centralized error handling for specific status codes or error types, keeping handlers focused on the happy path.

## Examples & Code Walkthrough
Below is a minimal but realistic API for a blogging platform. It shows how to guard routes with JWT authentication, extract typed JSON, and share a database connection pool via `State`. Error handling uses Rocket’s built‑in `Result` propagation.

```rust
#![feature(proc_macro_hygiene, decl_macro)]

#[macro_use] extern crate rocket;

use rocket::serde::{Deserialize, Serialize};
use rocket::State;
use rocket::http::Status;
use rocket::request::{self, FromRequest, Outcome};
use rocket::data::{self, FromData};
use rocket::serde::json::Json;
use sqlx::{PgPool, Postgres, Transaction};
use std::convert::Infallible;
use std::ops::Deref;

/// Application state shared across all requests.
struct AppState {
    db: PgPool,
}
impl Deref for AppState {
    type Target = PgPool;
    fn deref(&self) -> &Self::Target {
        &self.db
    }
}

/// Simple JWT claims struct (in real code you would use a proper lib).
#[derive(Debug, Deserialize, Serialize)]
struct Claims {
    sub: i64, // user id
    exp: usize,
}

/// Guard that extracts a verified JWT from the `Authorization` header.
#[rocket::async_trait]
impl<'r> FromRequest<'r> for Claims {
    type Error = Infallible;

    async fn from_request(req: &'r rocket::Request<'_>) -> Outcome<Self, Self::Error> {
        let header = req.headers().get_one("Authorization")
            .and_then(|h| h.strip_prefix("Bearer "))
            .ok_or_else(|| (Status::Unauthorized, "missing token"))?;
        // In practice, verify signature and expiration with a library like `jsonwebtoken`.
        // Here we just decode the payload (base64) for demo purposes.
        let claims: Claims = match base64::decode_config(header, base64::URL_SAFE) {
            Ok(bytes) => serde_json::from_slice(&bytes).unwrap_or_else(|_| {
                return Outcome::Failure((Status::BadRequest, "malformed token"));
            }),
            Err(_) => return Outcome::Failure((Status::Unauthorized, "invalid encoding")),
        };
        Outcome::Success(claims)
    }
}

/// Payload for creating a new post.
#[derive(Deserialize)]
struct NewPost {
    title: String,
    body: String,
}

/// Representation returned to the client.
#[derive(Serialize)]
struct PostResponse {
    id: i64,
    title: String,
    body: String,
    author_id: i64,
}

/// Handler: create a new post, requires authenticated user.
#[post("/posts", format = "json", data = "<new_post>")]
async fn create_post(
    _claims: Claims, // guard ensures we have a valid user
    state: &State<AppState>,
    Json(new_post): Json<NewPost>,
) -> Result<Json<PostResponse>, Status> {
    let mut tx: Transaction<Postgres> = state.begin()
        .await
        .map_err(|_| Status::InternalServerError)?;

    let record = sqlx::query!(
        r#"
        INSERT INTO posts (title, body, author_id)
        VALUES ($1, $2, $3)
        RETURNING id, title, body, author_id
        "#,
        new_post.title,
        new_post.body,
        _claims.sub
    )
    .fetch_one(&mut tx)
    .await
    .map_err(|_| Status::InternalServerError)?;

    tx.commit()
        .await
        .map_err(|_| Status::InternalServerError)?;

    Ok(Json(PostResponse {
        id: record.id,
        title: record.title,
        body: record.body,
        author_id: record.author_id,
    }))
}

/// Handler: list posts, public endpoint.
#[get("/posts")]
async fn list_posts(state: &State<AppState>) -> Result<Json<Vec<PostResponse>>, Status> {
    let rows = sqlx::query!(
        r#"
        SELECT id, title, body, author_id FROM posts ORDER BY id DESC
        "#
    )
    .fetch_all(&*state)
    .await
    .map_err(|_| Status::InternalServerError)?;

    let posts = rows.into_iter()
        .map(|r| PostResponse {
            id: r.id,
            title: r.title,
            body: r.body,
            author_id: r.author_id,
        })
        .collect();

    Ok(Json(posts))
}

/// Global error catcher for 404.
#[catch(404)]
fn not_found() -> &'static str {
    "Resource not found"
}

#[launch]
fn rocket() -> _ {
    // In a real app you would load the DB URL from env.
    let pool = PgPool::connect("postgres://localhost/blog")
        .await
        .expect("DB connection failed");

    rocket::build()
        .manage(AppState { db: pool })
        .mount("/", routes![create_post, list_posts])
        .register("/", catchers![not_found])
}
```

**What the code shows**

- **Guards**: `Claims` validates a JWT and makes the user ID available to handlers without extra boilerplate.
- **State**: The `AppState` struct wraps a `sqlx::PgPool`; Rocket injects it via `&State<AppState>`.
- **Error Handling**: Handlers return `Result<_, Status>`. Rocket automatically maps `Err(Status)` to the proper HTTP response. A dedicated catcher handles 404s.
- **Async**: All DB calls use `sqlx`’s async API; Rocket’s runtime is Tokio‑based, so no thread‑blocking occurs inside routes.

## Best Practices
1. **Keep guards cheap** – Run only validation or lightweight lookups inside `FromRequest`. Expensive work (e.g., DB queries) should live in handlers or be pre‑loaded into State.
2. **Prefer `State` for shared resources** – Connection pools, configuration, or caches belong here; avoid globals.
3. **Leverage fairings for observability** – Attach a fairing that records request start time; a Respond fairing logs latency and status. This keeps handlers clean.
4. **Use typed responses** – Define custom `Responder` types for reusable payloads (e.g., paginated lists) rather than scattering `Json` calls everywhere.
5. **Validate early, fail fast** – If a guard can reject a request, do it before touching expensive resources. This reduces wasted CPU and DB load under malformed traffic.
6. **Test guards in isolation** – Rocket’s `local::Client` lets you simulate requests and assert guard outcomes without spinning up a real server.

## Common Mistakes & Anti-Patterns
| Mistake | Why it’s a problem | Fix |
|---|---|---|
| **Blocking CPU work in an async route** (e.g., heavy image processing) | Blocks the Tokio thread pool, hurting concurrency. | Offload to a thread pool via `tokio::task::spawn_blocking` or move work to a background worker system. |
| **Overusing `State` for request‑scoped data** | Shared mutable state across requests can cause race conditions or accidental data leakage. | Use request guards or the `request::local_state!` macro for per‑request data; reserve `State` for truly global resources. |
| **Ignoring catchers and letting panics bubble up** | Uncaught panics produce 500 responses with no context, making debugging harder. | Register catchers for common error types (`catch(400)`, `catch(500)`) and consider a fairing that captures panic info and logs it. |
| **Using `.unwrap()` on `Result` from DB queries** | Turns recoverable errors into crashes. | Propagate the error with `?` and map to an appropriate `Status`, or define a custom error type that implements `Responder`. |
| **Neglecting payload size limits** | Large JSON bodies can exhaust memory. | Apply `#[post("/data", limit = "2MiB")]` or configure a global `limiter` fairing to cap request size. |

## Performance Considerations
- **Zero‑cost abstractions**: Rocket’s routing and guard resolution are resolved at compile time; the generated code is essentially a series of `match` statements and inline function calls, comparable to hand‑written `hyper` servers
