# Unreal C++ Course Chapter 107

## Introduction
The rise of GPU‑as‑a‑service has changed how we think about rendering workloads in Unreal Engine. Instead of maintaining a fixed render farm, teams can now pull compute from the cloud on demand, stream assets from object storage, and offload matchmaking or procedural logic to managed services. This chapter walks through a practical, end‑to‑end pipeline that ties these pieces together directly in C++.

## Why This Matters
When a game targets low‑end hardware but still wants film‑quality shading, the only viable path is to render frames remotely and stream the video back. Large open‑world titles often exceed the storage capacity of a typical console or PC, making on‑demand asset fetching essential. Matchmaking that runs on dedicated servers can become a bottleneck during peak hours, while a managed service scales automatically. Finally, running per‑request logic such as procedural terrain generation on servers avoids fragmenting the client binary and lets you update rules without a patch.

## How It Works
The pipeline consists of five loosely coupled modules that communicate through well‑defined interfaces. At startup the Auth module obtains a short‑lived token from AWS Cognito. The Asset Streamer uses that token to sign S3 GET requests and streams chunks into a local cache. The Remote Rendering Client opens a WebSocket to a GPU instance, sends input state, and receives encoded frames which are decoded and presented. The Matchmaking module talks to AWS GameLift to find a session and returns connection details. The Serverless Invoker calls an API Gateway endpoint that triggers a Lambda function for tasks such as procedural level generation.

```mermaid
flowchart TD
    A[Unreal Game] --> B[Auth Module]
    B -->|Cognito Token| C[Asset Streamer]
    C -->|Signed S3 URL| D[Remote Rendering Client]
    D -->|Input State| E[GPU Instance (NVidia Cloud)]
    E -->|Encoded Frames| D
    D -->|Decoded Frame| A
    B -->|Token| F[Matchmaking Client]
    F -->|GameLift Session| G[Game Server]
    B -->|Token| H[Serverless Invoker]
    H -->|API Gateway| I[Lambda Function]
```

Each module is implemented as a standalone Unreal object that can be instantiated from any gameplay class. Errors are propagated through delegate callbacks so the UI can react without blocking the game thread.

## Core Concepts
**Authentication token** – A short‑lived JWT issued by Cognito, stored in `FCloudAuthToken`. It contains the access key, secret key, and session token needed for signing AWS requests.

**Asset request** – Describes a single chunk (`FAssetChunkRequest`) with fields: bucket name, object key, byte range, expected SHA‑256 hash, and a delegate for completion.

**Render frame buffer** – Holds an encoded video packet (`FEncodedFrame`) and metadata (timestamp, sequence number). After decoding we produce an `FTexture2DRef` that can be fed to the UI.

**Matchmaking request** – Contains player attributes, desired session properties, and a callback that receives a `FGameLiftSessionInfo` with IP, port, and credentials.

**Serverless payload** – A JSON blob (`FLambdaPayload`) that the Lambda consumes; typical fields include a seed for procedural generation and a correlation ID for tracing.

All modules share a common interface `ICloudService` with methods `Initialize()`, `Execute()`, and `Shutdown()`. This makes it easy to swap implementations (e.g., using Azure instead of AWS) without touching gameplay code.
