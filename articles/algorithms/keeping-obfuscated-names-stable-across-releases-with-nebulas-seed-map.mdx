# Keeping obfuscated names stable across releases with Nebula''s seed map

## Introduction
Symbol stability across builds is a persistent challenge in large codebases. When obfuscation uses random salts or per‑build seeds, downstream tools—debuggers, profilers, static analyzers—receive different name mappings each time. Stack traces become unmappable, licensing checks fail, and instrumentation data loses coherence. In our team’s CI pipelines, we observed that a single release cycle could generate over two hundred distinct name collisions in symbol tables, forcing manual reconciliation before any cross‑release analysis could occur. Nebula’s seed‑map approach addresses this by coupling deterministic name generation to a persistent, version‑aware key‑value store. The result: obfuscated names remain identical across releases when the same seed is supplied, while still providing strong entropy against casual inspection.

## Why This Matters
In production environments that ship frequent updates, the ability to map an obfuscated binary back to its original source symbol is not a luxury—it’s a requirement. Debug sessions that span multiple releases rely on consistent naming; otherwise, developers spend cycles manually grepping through mangled identifiers. Instrumentation systems such as tracing collectors and coverage reporters also depend on stable symbol tables to aggregate metrics accurately. From a compliance standpoint, license verification scripts often hash symbol names to detect unauthorized modifications; random obfuscation breaks these checks outright. By anchoring obfuscation to a project‑wide seed that is recorded alongside each artifact, we eliminate the churn while preserving the protective goals of obfuscation.

## How It Works
The core mechanism revolves around a deterministic mapping function that takes an original symbol name and a master seed, then outputs a fixed-length obfuscated string. A persistent seed‑map stores the first‑seen mapping per symbol. Subsequent builds load the existing map, reuse entries, and only add new symbols when they appear for the first time. This append‑only strategy ensures idempotency: rebuilding the same codebase with the same seed produces byte‑identical obfuscated outputs, without re‑processing symbols that already have a mapping.

## Core Concepts
- **Master seed**: A 256‑bit value derived from a combination of repository identifier and build timestamp. It acts as the root of all name derivations.
- **Name mapping function**: A keyed cryptographic construction (HMAC‑SHA256) that takes the master seed, the original symbol, and an optional per‑symbol counter. The output is a fixed‑length hex string used as the obfuscated identifier.
- **Version counter**: Incremented only when a symbol is encountered for the first time in a given build. Re‑using existing entries keeps the map compact and names stable across incremental builds.
- **Persistence layer**: An append‑only log or immutable key‑value store that survives across CI runs. Common choices include BoltDB for pure‑Go stacks or SQLite for heterogeneous environments. Garbage‑collection policies can prune entries for symbols that have been removed from the codebase, but only after a configurable retention window.
- **Seed versioning**: Each seed map file is named with a hash of its master seed and a monotonically increasing edition number. Consumers read the accompanying manifest to locate the correct map for a given artifact.
