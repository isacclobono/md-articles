# Raspberry Pi locks down Pi 5 RAM upgrades in firmware

## Introduction
The Raspberry Pi 5 launched with a lot of fanfare, promising a faster Cortex‑A76 core and a new VideoCore VII GPU. Enthusiasts immediately began asking whether larger LPDDR4X modules could be used, hoping for 16 GB or more. A recent thread on Lobste.rs highlighted that the board’s firmware refuses to accept anything beyond the 8 GB JEDEC‑specified limit. The restriction is not a hardware limitation; it is enforced in the GPU‑side boot firmware that runs before the ARM cores ever see the memory.

## Why This Matters
Engineers building production‑grade edge devices need predictable memory sizing. When a platform silently caps RAM, it can cause out‑of‑memory crashes, wasted silicon, and additional power draw. Knowing where the limit originates lets us design work‑arounds, plan capacity upgrades, and avoid costly field failures.

## How It Works
The boot process on the Pi 5 proceeds through several stages before any DRAM training occurs. The firmware extracts the module’s SPD data, computes the total capacity, and then enforces a hard‑coded ceiling.

```mermaid
flowchart TD
    A[Power‑on] --> B[PMIC & reset logic]
    B --> C[ROM‑based bootloader (SoC)]
    C --> D[bootcode.bin (GPU firmware)]
    D --> E[start.elf (GPU firmware)]
    E --> F[Read SPD via I²C]
    F --> G[Compute total RAM size]
    G --> H{RAM size > 8192 MiB?}
    H -- Yes --> I[Force size to 8192 MiB]
    H -- No --> J[Continue DRAM training]
    J --> K[Pass control to ARM via arm_control]
    K --> L[kernel8.img boots]
```

### Memory detection logic (original firmware)
```c
/* SPD read – simplified, runs in GPU firmware context */
uint32_t read_spd_density(void) {
    uint8_t buf[2];
    i2c_read(SPD_ADDR, 0x0A, buf, 2);   // Byte 0x0A = Module Density (Mbit per chip)
    return ((buf[0] << 8) | buf[1]);    // Result in Mbit
}

/* Compute total RAM (original firmware logic) */
uint32_t compute_ram_size(void) {
    uint32_t density = read_spd_density();          // Mbit per chip
    uint8_t  chip_width   = i2c_read_byte(SPD_ADDR, 0x0C); // Data width (bits)
    uint8_t  ranks        = i2c_read_byte(SPD_ADDR, 0x0E); // Number of ranks
    uint8_t  devices      = i2c_read_byte(SPD_ADDR, 0x0B); // Devices per rank

    // Total Mbit = density * devices * ranks * (chip_width / 8)
    uint32_t total_mbit = density * devices * ranks * (chip_width / 8);
    return total_mbit / 8;   // Convert to MiB
}

/* Enforce ceiling */
void enforce_ram_limit(uint32_t *size_out) {
    uint32_t size = compute_ram_size();   // MiB
    if (size > 8192) {                    // 8 GB limit
        *size_out = 8192;                 // clamp to 8 GB
    } else {
        *size_out = size;
    }
}
```

The `enforce_ram_limit` routine is called from `start.elf` during the `mem_init` phase. If the computed size exceeds 8192 MiB, the value is forced down to the ceiling, effectively truncating any larger module to 8 GB.

### Lock‑down location and rationale
The check lives in `start.elf`, specifically inside the `mem_init` function. Disassembly excerpt (annotated) shows the constant:

```asm
    ; r0 = computed RAM size in MiB
    cmp     r0, #8192        ; 8 GB limit
    ble     .Lcontinue
    mov     r0, #8192        ; force to 8 GB if larger
.Lcontinue:
    ; … proceed with DRAM training using r0 …
```

The constant originates from licensing agreements and silicon validation data. Power‑delivery designs on the board guarantee stable operation up to 8 GB; exceeding that could stress the VRM and cause instability.

## Core Concepts
- **SPD (Serial Presence Detect)**: an I²C‑based lookup table stored on the DIMM that describes density, rank count, and bus width.
- **GPU‑side boot firmware**: runs in a privileged mode before the ARM cores are initialized; it owns the SDRAM controller.
- **Memory ceiling constant**: a hard‑coded 8192 MiB value that cannot be overridden by `config.txt` because the check occurs before the configuration file is parsed.
- **DRAM training**: the GPU firmware programs timing registers based on the clamped size; any larger module would produce mismatched timing, leading to data corruption.

## Best Practices
1. **Validate SPD data early** – treat the I²C read as a potential failure point; retry with timeout handling.
2. **Clamp before DRAM training** – the size must be set prior to programming timing registers; any later change is ineffective.
3. **Document the ceiling** – make the 8 GB limit explicit in hardware design notes to avoid confusion during board revisions.
4. **Test with multiple densities** – verify that the firmware correctly rejects sizes above the limit while accepting the maximum allowed.

## Common Mistakes & Anti-Patterns
| Mistake | Why it fails | Fix |
|---------|--------------|-----|
| Assuming `config.txt` can override the limit | The check occurs before `config.txt` is parsed; the constant is baked into `start.elf`. | Accept the limit or redesign the board to use a different SoC. |
| Ignoring SPD read errors | A failed I²C transaction yields a default density, leading to incorrect size calculation. | Implement retry logic and fallback defaults, and log errors for diagnostics. |
| Hard‑coding the 8 GB value in user code | Makes the code brittle if the limit changes in future revisions. | Pull the ceiling from a shared header or configuration file within the firmware. |
| Over‑provisioning power delivery without checking VRM headroom | Even though the firmware caps RAM, a larger module may draw more current during initialization, stressing the regulator. | Verify VRM margins in silicon validation reports before selecting higher‑density modules. |

## Performance Considerations
The RAM‑size clamp adds a single comparison and conditional move in the `mem_init` path – a negligible runtime cost (sub‑microsecond). However, the DRAM training routine itself scales with the number of ranks and devices; larger modules would increase training time, potentially extending boot latency. Since the firmware caps at 8 GB, training time remains bounded, which is beneficial for predictable edge‑device uptime.

## Frequently Asked Questions (FAQ)

**Q1: Can I modify the firmware to lift the 8 GB cap?**  
A: The limit is enforced in read‑only firmware code. Recompiling the bootloader would require source access, which is not publicly available. The practical approach is to work within the 8 GB envelope.

**Q2: Does the Pi 5’s SoC support more than 8 GB physically?**  
A: The BCM2712 silicon is capable of addressing larger memory spaces, but the JEDEC‑specified LPDDR4X interface and power‑delivery design are validated only up to 8 GB.

**Q3: Will using a 4 GB module affect performance compared to 8 GB?**  
A: No. The firmware trains the SDRAM controller based on the detected size; a 4 GB module simply results in a smaller training window, which can be marginally faster.

**Q4: Are there any hidden registers that expose the true capacity?**  
A: No public registers expose the unclamped size. All size information is derived from SPD data before the clamp is applied.

**Q5: How does the lock‑down affect custom kernel modules that request more memory?**  
A: The kernel sees the size reported by the firmware (capped at 8 GB). Any request beyond that will be rejected by the memory allocator, leading to allocation failures.

## Conclusion
The Raspberry Pi 5’s firmware deliberately caps RAM at 8 GB by reading SPD data, computing the total capacity, and clamping the result before DRAM training. This design choice stems from licensing, silicon validation, and power‑delivery constraints rather than a hardware limitation. Understanding the boot flow, the detection routine, and the enforcement point enables engineers to build reliable systems, avoid surprise failures, and make informed capacity decisions when deploying Pi 5 devices at scale.
