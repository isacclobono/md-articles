# Docker is weird

## Introduction
Containers promise isolation, reproducibility, and fast startup, yet the tooling around them feels like a patchwork of legacy concepts bolted onto modern kernels. When we first shipped our micro‑service platform, the build pipeline would sometimes fail with cryptic errors about missing layers, and the runtime would occasionally OOM despite modest memory requests. Understanding why Docker behaves oddly required peeling back its internal architecture rather than accepting “it’s just Docker”.

## Why This Matters
Engineers need reliable builds and predictable performance. A broken container image can cascade into deployment failures, hidden latency spikes, and costly rollbacks. Knowing the mechanics lets teams diagnose issues faster, avoid hidden footguns, and design services that survive the quirks of the underlying runtime.

## How It Works
Docker’s core is a thin wrapper around Linux kernel features combined with a content‑addressable image store. The daemon manages image layers, mounts, and the lifecycle of containers. Below is a simplified flow of a container start‑up:

```mermaid
flowchart TD
    A[User runs `docker run`] --> B[Docker CLI]
    B --> C[Docker daemon]
    C --> D[containerd]
    D --> E[OCI runtime (runc)]
    E --> F[Kernel namespaces & cgroups]
    F --> G[Container process]
```

1. **CLI → Daemon** – The `docker` command sends a gRPC request to the daemon, which validates the request and prepares the image.
2. **Image handling** – Docker pulls layers from the local content‑addressable store or a registry, verifies checksums, and assembles them into a temporary filesystem using `overlayfs` or `aufs`.
3. **Runtime creation** – `containerd` launches `runc`, which sets up namespaces (`pid`, `net`, `mnt`, `ipc`, `uts`, `user`) and cgroups to isolate the process.
4. **Execution** – The container’s main process runs inside the isolated environment, seeing only the mounted layers.

## Core Concepts
- **Image** – A read‑only collection of layers identified by a SHA‑256 digest. Each layer is a tarball of filesystem changes.
- **Layer** – Immutable delta stored in the local storage driver (`overlay2` is the default). Layers are layered on top of each other to form the container’s writable rootfs.
- **Storage driver** – Handles copy‑on‑write semantics. `overlay2` merges lower and upper layers into a single inode tree, avoiding the performance pitfalls of older drivers like `devicemapper`.
- **Namespaces & cgroups** – Provide isolation for processes, network, mounts, and resource limits. Docker delegates these to the kernel, but misconfigurations (e.g., sharing the host network) can leak resources.
- **OCI spec** – Docker implements the Open Container Initiative specification, ensuring compatibility with other runtimes like `containerd` and `CRI‑O`.

## Examples & Code Walkthrough
Below is a minimal Go program that mimics Docker’s image inspection using the `docker/cli` library. It demonstrates how to retrieve an image’s layers, verify checksums, and mount them read‑only.

```go
package main

import (
	"context"
	"fmt"
	"log"

	"github.com/docker/docker/client"
	"github.com/docker/docker/pkg/units"
)

func main() {
	ctx := context.Background()
	cli, err := client.NewClientWithOpts(client.WithHost("unix:///var/run/docker.sock"))
	if err != nil {
		log.Fatalf("cannot connect to Docker daemon: %v", err)
	}
	defer cli.Close()

	// Inspect the image by its digest
	imageRef := "sha256:abc123def456..." // replace with real digest
	img, _, err := cli.ImageInspectWithRef(ctx, imageRef, docker.HostConfig{})
	if err != nil {
		log.Fatalf("image inspection failed: %v", err)
	}

	// Print layer digests
	fmt.Println("Image layers:")
	for _, layer := range img.GraphLayerIDs {
		fmt.Printf("- %s\n", layer)
	}

	// Example: calculate total size in human‑readable units
	totalSize := units.HumanReadableBytes(img.Size)
	fmt.Printf("Total image size: %s\n", totalSize)
}
```

Key points:
- The `ImageInspectWithRef` call fetches the image metadata, including the list of layer digests.
- `img.Size` reflects the cumulative size of all layers.
- No privileged operations are performed; the program runs as an ordinary user with Docker socket access.

## Best Practices
1. **Pin digests, not tags** – Tags can move; digests are immutable and guarantee reproducibility.
2. **Prefer `overlay2`** – It offers the best performance and space efficiency for most workloads. Avoid `vfs` or `devicemapper` unless required by legacy infrastructure.
3. **Limit container resources** – Set `--memory`, `--cpus`, and `--pids-limit` to prevent runaway processes from exhausting host resources.
4. **Use explicit `--network`** – Default `bridge` networking can cause IP conflicts; prefer `host` or user‑defined networks with subnet isolation.
5. **Validate image signatures** – Enable `docker trust` or an external scanner to ensure only signed images are run in production.

## Common Mistakes & Anti-Patterns
| Mistake | Why it hurts | Fix |
|---------|--------------|-----|
| **Relying on `latest` tag** | Images can change unexpectedly, breaking deployments. | Use immutable digests; automate digest verification in CI. |
| **Mounting host directories directly** | Bypasses isolation, can leak host files into containers. | Use named volumes or bind‑mount with read‑only flags; avoid `--privileged`. |
| **Disabling seccomp/AppArmor** | Opens a path for privilege escalation inside the container. | Keep default profiles; customize only when absolutely required. |
| **Neglecting layer caching** | Rebuilding images on every change inflates build time and storage. | Structure Dockerfiles to reorder instructions so frequently changing layers are near the end. |

## Performance Considerations
- **CPU overhead** – Namespace setup is O(1) per container, but context switches between host and container can add ~5‑10 µs per syscall. For high‑frequency workloads, consider using `gVisor` or `kata-containers` if stronger isolation is needed.
- **Memory usage** – `overlay2` stores each layer as separate files; duplicate data across layers leads to wasted space. Periodic `docker system prune` removes unused layers, but in long‑running services image reuse is essential.
- **I/O latency** – The copy‑on‑write mechanism can cause additional disk seeks when many layers are accessed simultaneously. Using SSDs and enabling `noatime` on the storage mount reduces this impact.
- **Scalability limits** – The daemon is a single process; on hosts with thousands of containers it becomes a bottleneck. Horizontal scaling with a swarm or Kubernetes mitigates this by distributing container lifecycles across multiple daemon instances.

## Real-World Usage
- **Netflix** runs its micro‑services on Docker Swarm, leveraging `overlay2` for efficient layer sharing across thousands of nodes. They enforce image signing and automated roll‑backs to keep latency under 100 ms for video transcoding pipelines.
- **Uber** uses Docker as the building block for its data‑processing jobs. By pinning digests and employing custom storage drivers tuned for SSD-backed filesystems, they achieve sub‑second job start times even with multi‑gigabyte images.
- **Cloudflare** runs edge workers in lightweight containers built from minimal `scratch` images. They rely on `runc` directly (bypassing the daemon) to reduce attack surface and improve start‑up latency to under 5 ms.

## Frequently Asked Questions (FAQ)

**Q1: Why does `docker build` sometimes fail with “layer fetch failed”?**  
A: The error indicates the registry could not deliver a layer due to network timeout or rate limiting. Retry with exponential backoff or use a local registry mirror to improve reliability.

**Q2: Can I run Docker without the daemon?**  
A: Yes. Tools like `containerd` or `podman` implement the OCI runtime directly, eliminating the single‑process bottleneck of the Docker daemon.

**Q3: Is it safe to share a host’s network namespace with a container?**  
A: It removes isolation, allowing containers to see each other’s ports and potentially interfere with each other’s traffic. Prefer user‑defined bridge networks unless you have a specific need for host networking.

**Q4: How do I limit CPU usage without cgroups?**  
A: Docker’s `--cpus` flag translates to cgroup CPU quotas. Setting a limit here is the recommended approach; manual cgroup manipulation is error‑prone.

**Q5: What’s the difference between `docker run` and `docker exec`?**  
A: `docker run` creates a new container instance, while `docker exec` runs a command inside an already‑running container. Use `exec` for ad‑hoc commands; `run` for full container lifecycles.

## Conclusion
Docker’s odd behavior stems from its blend of legacy Linux isolation primitives, a content‑addressable image model, and a daemon‑centric architecture. By understanding the underlying layers, storage drivers, and isolation mechanisms, engineers can avoid common pitfalls, optimize performance, and integrate containers reliably into production pipelines. Pinning digests, choosing the right storage driver, and respecting resource limits are practical steps that turn Docker’s quirks into predictable, scalable assets.
