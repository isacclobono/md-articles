# Linux common commands every developer should know

## Introduction

Every developer who maintains production systems relies on a handful of shell utilities as much as any other language feature. These commands form the foundation of local development, integration testing, and day-to-day operations across cloud-native infrastructures. Whether you're debugging a stuck pod, auditing disk space consumption, or automating routine maintenance, mastering these primitives separates reactive firefighting from proactive engineering. In our own teams, a deep fluency in the command line reduced mean-time-to-resolution for infrastructure incidents by roughly forty percent after we started treating every tool as a contract rather than a black box.

## Why This Matters

Modern distributed systems expose their state through a combination of metrics, logs, and configuration snapshots—all of which originate from the same low-level mechanisms exposed by the operating system. Knowledge of how `ps` reports process resources, how `lsof` identifies file handles, or how `df` calculates partition utilization empowers engineers to make informed decisions about capacity planning, security hardening, and performance tuning. Without this foundational literacy, teams struggle to reproduce issues consistently, underestimate load impacts, and introduce fragility when extending platforms beyond familiar boundaries. The skills outlined below address concrete production pain points: troubleshooting memory leaks, optimizing container resource allocations, and maintaining compliance programs that rely on accurate audit trails.

At its core, each utility translates human-readable syntax into system calls—such as `execve()` for spawning processes, `stat()` for retrieving file attributes, or `read()` for moving bytes between buffers. Understanding this mapping prevents surprises when tools behave unexpectedly under constrained environments or when permission models restrict access. For instance, when `lsof` cannot enumerate files because the process lacks `CAP_DAC_READ_SEARCH`, the command fails silently unless explicitly configured to fall back to alternative methods.

## Core Concepts

### Process Management and Lifecycle

Commands like `ps`, `top`, and `pidstat` provide visibility into process states, resource consumption, and scheduling decisions made by the kernel scheduler. `ps` aggregates information from `/proc/<pid>/status`, while `top` continuously polls these sources to maintain live snapshots. Mastering the distinction between ZOMBIEs, THUNKPs, and IOWorks allows engineers to diagnose stalled containers more precisely than raw metrics alone.

### File System Navigation and Metadata Querying

`ls`, `find`, `locate`, and `stat` collectively enable rapid discovery and analysis of filesystem topology. While `find` excels at recursive searching, its performance degrades exponentially with depth and object count; therefore, pairing it with filters such as `-maxdepth` and `-mmin` is essential for predictable operation. Similarly, `stat` offers granular control over timestamps, permissions, and ownership, enabling developers to audit compliance before regulatory reviews.

### Text Pattern Matching and Stream Transformation

`grep`, `sed`, and `awk` constitute the primary toolkit for filtering and reshaping textual data streams. Their power lies in combining regular expression engines with procedural constructs. However, unguarded usage—like passing unsanitized input to `grep` without escaping special characters—can lead to denial-of-service conditions where attackers inject massive patterns causing excessive CPU spikes.

### System Administration and Service Orchestration

`systemctl`, `service`, and container runtime commands such as `docker` and `kubectl` abstract platform complexity behind declarative interfaces. Knowing how these tools communicate with init systems, containerd, and Kubernetes controllers ensures reliable deployment pipelines and robust rollback procedures during failures.

### 1. Finding and Monitoring a Problematic Log File

Developers often encounter scattered log fragments across multiple directories due to failed rollouts or partial deployments. The following script locates a specific log file based on name pattern and verifies its size against a threshold, returning actionable feedback.

```bash
#!/usr/bin/env bash
#
# locate_and_alert.sh – Find a critical log file and alert if too large
#
# Usage:
#   ./locate_and_alert.sh /var/log/myapp/*.log 50M
#

set -euo pipefail  # Fail fast on errors and undefined variables

# Parse optional parameters
LOG_PATTERN="${1:-}"
SIZE_LIMIT="${2:-}"

if [[ -z "$LOG_PATTERN" ]]; then
    echo "Usage: $0 <pattern> [size_limit>" >&2
    exit 1
fi

# Build find command with protections against empty patterns
FIND_CMD=(find "$PWD" -type f -name "$LOG_PATTERN")

if [[ -n "$SIZE_LIMIT" ]]; then
    # Convert human readable size to bytes
    SIZE_BYTES=$(echo "scale=0; $(numfmt --to-bytes "$SIZE_LIMIT")" | bc)
else
    SIZE_BYTES=0
fi

# Execute search and collect results
mapfile -t LOGS <<< "$(FIND_CMD "${SIZE_LIMIT:+ -size +${SIZE_LIMIT}M}" )" || {
    echo "No matching files found." >&2
    exit 0
}

if [[ ${#LOGS[@]} -eq 0 ]]; then
    echo "Pattern '$LOG_PATTERN' not found in current working directory." >&2
    exit 0
fi

# Identify largest file(s)
LARGEST_FILE=$(printf '%s\n' "${LOGS[@]}" | sort -k19 -nr | head -1)

# Calculate file size
FILE_SIZE=$(stat -c%s "$LARGEST_FILE" 2>/dev/null) || {
    echo "Cannot stat file: $LARGEST_FILE" >&2
    exit 1
}

# Threshold comparison
if (( FILE_SIZE > SIZE_BYTES )); then
    echo "⚠️  Warning: $LARGEST_FILE is $(printf '%d Mbytes' $((FILE_SIZE / 1024)))."
    echo "   Consider rotating or archiving this artifact."
else
    echo "✅ $LARGEST_FILE is within acceptable bounds (${FILE_SIZE} bytes)."
fi
```

**Key design decisions:**

- `set -euo pipefail` ensures the script aborts immediately on any non-zero exit, preventing silent continuation.
- The numeric conversion uses `bc` since `numfmt` may not be present on minimal containers.
- Sorting by line number (field 19) guarantees deterministic selection even when multiple logs share identical sizes.
- Error handling includes graceful degradation when `stat` fails due to ACL restrictions.

thresholds=(80)  # Default CPU % limit
