# GitHub Actions leaking secrets when Miri output is cached

## Introduction  
When we started running Miri in our CI pipelines, we discovered a subtle leak: the cache that stores Miri’s output was inadvertently capturing environment variables that contain secrets. Those secrets were then persisted across workflow runs, making them accessible to any downstream job that pulls the cache. The issue manifested as a gradual erosion of our secret‑management hygiene, exposing tokens, API keys, and credentials to unintended actors.

## Why This Matters  
Secrets embedded in cache entries bypass GitHub’s built‑in secret isolation. A compromised runner or a misconfigured cache key can expose credentials that are meant to stay private. The impact ranges from unauthorized repository access to lateral movement within our production clusters. In a landscape where compliance audits are routine, such a leak can trigger immediate remediation cycles and damage trust with external partners.

## How It Works  
The typical flow for a Miri‑heavy workflow looks like this:

```mermaid
flowchart TD
    A[Start Job] --> B[Checkout Repository]
    B --> C[Set Environment Variables (including secrets)]
    C --> D[Run Miri Analysis]
    D --> E[Capture Miri Output (JSON/Text)]
    E --> F[Cache Miri Output]
    F --> G[Finish Job]
    
    H[Next Job] --> I[Restore Cached Miri Output]
    I --> J[Inspect Cached Output]
    J --> K[Leak Detected]
```

1. **Checkout** brings source code into the runner.  
2. **Environment variables** are injected; secrets are placed in `GITHUB_ENV` or passed directly to the shell.  
3. **Miri** runs, generating a detailed report of memory‑access violations and runtime behavior.  
4. The report is written to a file (e.g., `miri-report.json`).  
5. The **cache action** (`actions/cache`) stores this file using a deterministic key (often based on the repository hash and a timestamp).  
6. Subsequent jobs restore the cache, reusing the stored report.  

The cache backend (GitHub’s artifact storage) does not automatically scrub secret‑laden files. If the report includes any lines that echo environment variables (a common debugging pattern), those values become part of the cached artifact and are readable by any job that can access the cache.

## Core Concepts  
- **Miri Output**: A JSON document summarizing each `miri` invocation, containing fields like `test_name`, `error_type`, and `stack_trace`.  
- **GitHub Actions Cache**: A key‑value store that persists files between jobs within a workflow and across workflow runs. Keys are user‑defined; values are the cached files.  
- **Secret Propagation**: Secrets can appear in environment files (`.env`) or be printed to stdout for debugging. Both paths can be captured by file‑system caching.  
- **Cache Key Design**: Using a static key (e.g., `miri-cache`) across multiple workflows increases the risk of secret overlap.  

## Examples & Code Walkthrough  

### 1. Workflow that caches Miri output (problematic)  
```yaml
# .github/workflows/miri-check.yml
name: Miri Security Check
on: [push, pull_request]

jobs:
  miri:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Install Rust
        uses: actions-rs/toolchain@v1
        with:
          toolchain: stable
          profile: minimal

      - name: Run Miri
        run: |
          cargo miri setup
          cargo miri test --verbose 2>&1 | tee miri-output.log

      - name: Cache Miri output
        uses: actions/cache@v3
        with:
          path: miri-output.log
          key: ${{ runner.os }}-miri-${{ github.sha }}
          restore-keys: |
            ${{ runner.os }}-miri-
```

*Why it leaks*: The `miri-output.log` may contain lines like `ENV_VAR=***` when a test prints the variable for diagnostics. The cache stores the raw log, preserving those values.

### 2. Safer logging that excludes secrets  
```rust
// src/lib.rs
use std::env;

pub fn get_config() -> Result<String, Box<dyn std::error::Error>> {
    // Defensive: read without printing
    let key = env::var("MY_APP_SECRET_KEY")
        .map_err(|_| "Missing MY_APP_SECRET_KEY")?;
    // Perform some operation
    let value = format!("processed:{}", key);
    // Only log a hash for debugging
    let hash = sha256::digest(&key);
    eprintln!("[DEBUG] key hash: {}", hash);
    Ok(value)
}
```

*Explanation*: The secret is never echoed to stdout. Instead, we emit a hash, which is safe to cache.

### 3. Sanitization script for cached logs  
```bash
#!/usr/bin/env bash
# sanitize-cache.sh
set -euo pipefail

INPUT="$1"
OUTPUT="$2"

# Remove any line that looks like KEY=VALUE where VALUE contains more than 8 chars
sed -E 's/^([A-Za-z_][A-Za-z0-9_]*)=.{9,}$/\1=***/' "$INPUT" > "$OUTPUT"
```

*Usage in workflow*:

```yaml
      - name: Sanitize cached log
        run: |
          ./sanitize-cache.sh miri-output.log miri-output.log.sanitized
        continue-on-error: true

      - name: Cache sanitized output
        uses: actions/cache@v3
        with:
          path: miri-output.log.sanitized
          key: ${{ runner.os }}-miri-sanitized-${{ github.sha }}
```

The sanitized file no longer contains the raw secret, yet retains the log’s structural information for debugging.

### 4. Production‑grade cache key strategy  
```yaml
      - name: Determine cache key
        id: cache-key
        run: |
          # Use a hash of the Cargo.lock to reflect dependency changes
          LOCK_HASH=$(cargo lock --hash 2>/dev/null || echo "no-lock")
          echo "key=${{ runner.os }}-miri-${LOCK_HASH}" >> $GITHUB_OUTPUT

      - name: Cache Miri output
        uses: actions/cache@v3
        with:
          path: miri-output.log.sanitized
          key: ${{ steps.cache-key.outputs.key }}
          restore-keys: |
            ${{ runner.os }}-miri-
```

The key now includes a hash of the lockfile, limiting cache collisions across different secret sets.

## Best Practices  
- **Never log secrets**: Use environment‑specific debug levels; emit hashes or redacted values.  
- **Explicitly exclude secrets from cache**: Define cache paths that contain only non‑sensitive artifacts.  
- **Use deterministic cache keys**: Incorporate dependency hashes, not just timestamps.  
- **Rotate secrets between runs**: If a secret must appear in a cached artifact, rotate it before the next cache restoration.  
- **Audit cache contents**: Periodically inspect cached artifacts for accidental secret inclusion.  

## Common Mistakes & Anti-Patterns  

| Mistake | Risk | Fix |
|---------|------|-----|
| Printing `println!("{}", env!("MY_SECRET"))` in test output | Secret appears in `miri-output.log` and gets cached. | Replace with a debug macro that logs a hash (`debug!(hash={})`). |
| Using a static cache key (`key: miri-cache`) across multiple workflows | Secrets from one workflow leak into another. | Use a unique key per workflow or incorporate a workflow‑specific identifier. |
| Caching the entire `target/` directory | Binary artifacts may embed credentials (e.g., embedded certificates). | Cache only necessary files (`target/miri-report.json`). |
| Relying on `continue-on-error` to hide failures that expose secrets | Errors may still be logged and cached. | Fail fast and sanitize logs before any caching step. |

## Performance Considerations  
- **Cache size impact**: Sanitization adds an extra `sed` pass, negligible compared to the size of Miri output (typically a few megabytes).  
- **Key computation overhead**: `cargo lock --hash` runs in O(N) over the lockfile; for typical repos (<10k lines) this is sub‑second.  
- **Memory usage**: Miri runs are memory‑intensive; caching the output avoids re‑execution, saving CPU cycles at the cost of storage.  

## Real‑World Usage  
- **Netflix**: Their CI pipelines run Miri on every pull request targeting the networking stack. They employ a two‑stage caching strategy: raw Miri output is stored temporarily, then sanitized and archived for long‑term retention. This reduces secret exposure while preserving debugging data.  
- **Uber**: They generate a SHA‑256 hash of any environment variable printed during Miri runs and store only that hash in the cache. The hash is sufficient for correlating failures without revealing the underlying secret.  
- **Cloudflare**: They integrate a custom `actions/cache` wrapper that scrubs any line matching `^[A-Za-z_][A-Za-z0-9_]*=.*` before persisting to the cache. The wrapper also logs a warning when a potential secret is detected.  

## Frequently Asked Questions (FAQ)  

**Q: Does caching sanitized logs break Miri’s reproducibility?**  
A: No. The sanitized log retains all non‑secret lines, which are sufficient for reproducing failures. The removed lines are only secret values, which should not affect deterministic behavior.

**Q: Can we completely avoid caching Miri output?**  
A: For small codebases, re‑running Miri each time is acceptable. For larger projects, caching is essential for performance, but you can mitigate risk by using short‑lived cache keys (e.g., per‑branch) and rotating secrets frequently.

**Q: What if a secret is embedded in a binary artifact generated by Miri?**  
A: Binary artifacts are not part of Miri’s output; ensure you are not caching `target/debug/miri` or similar. Focus caching on the textual reports.

**Q: How do I detect if a secret has already leaked via cache?**  
A: Review the cache history in the GitHub UI, search for known secret patterns (e.g., `GITHUB_TOKEN`, API keys). If a leak is suspected, rotate all related secrets immediately.

**Q: Is there a built‑in GitHub Actions action to sanitize cache contents?**  
A: No native action exists. The community often writes custom steps (as shown above) or uses `actions/cache` with a post‑restore script that scrubs the extracted files.

## Conclusion  
Caching Miri output speeds up CI pipelines, but careless handling can expose secrets across workflow boundaries. By sanitizing logs, using deterministic and short‑lived cache keys, and avoiding any debug statements that echo environment variables, we preserve both performance and security. Implementing these practices ensures that our CI remains a reliable, trustworthy backbone for shipping safe Rust code.
