# ADTs & Enums in Scala 3: Making Illegal States a Compile Error

## Introduction

In our production systems, the most costly bugs rarely stem from syntax errors or missing imports. They come from invalid state transitions. We've all seen the incident reports: an order marked as `SHIPPED` with a null tracking ID, a user account `DEACTIVATED` while still holding an active session token, or a payment gateway callback processing a transaction that's already `REFUNDED`. These are illegal states leaking into the runtime, often triggered by edge cases that slip past unit tests and live until a customer hits the wall.

Scala 3 gives us a robust mechanism to eliminate this class of defects before the code ever reaches production. By leveraging Algebraic Data Types (ADTs) and the new `enum` syntax, we can encode business invariants directly into the type system. The compiler becomes the gatekeeper, rejecting code that attempts to construct or transition into impossible states. This isn't just about cleaner code; it's about raising the floor of reliability in complex web applications where state management drives business logic.

## Why This Matters

Web applications are state machines masquerading as CRUD interfaces. Every HTTP request represents an attempt to transition the domain model from one state to another. When we model these states loosely—using `String` status codes or `Boolean` flags—we push validation to runtime. We end up writing defensive checks like `if (order.status == "PAID" && order.trackingId != null)` scattered across controllers, services, and repositories. This approach is brittle. It relies on developers remembering to check invariants everywhere, and it breaks the moment a new state is added without updating every guard clause.

By making illegal states unrepresentable, we shift the burden from runtime validation to compile-time verification. This approach delivers three tangible benefits for engineering teams:

1.  **Elimination of Null Pointer Exceptions:** Data required for a state is bundled with the state itself. You cannot have a `Shipped` order without a `trackingId` because the type doesn't exist without it.
2.  **Exhaustiveness Checking:** Scala's `match` expressions guarantee that every possible state is handled. If you add a new state like `REFUNDED`, the compiler fails on every `match` block that doesn't account for it, forcing immediate updates across the codebase.
3.  **Self-Documenting Domain Models:** The type signature serves as the specification. Reading `CheckoutState` immediately reveals the lifecycle of a checkout flow, including the data available at each stage.

## How It Works

The core mechanism relies on the distinction between Sum Types and Product Types, combined with Scala 3's structural enforcement.

A Sum Type (represented by `enum` or `sealed trait`) declares that a value can be one of a fixed set of alternatives. A Product Type (like a `case class`) declares that a value consists of a specific combination of fields. Scala 3 `enum` allows us to define sum types where each case can carry its own product data.

When we define a state machine using an enum, we enforce two constraints:
1.  **Existence Constraint:** You cannot instantiate a case without providing the required data. The compiler verifies arguments at construction time.
2.  **Transition Constraint:** Methods that perform state transitions can be typed to accept only specific source states and return specific target states. Attempting to call a transition method on an incompatible state results in a type error or a pattern match mismatch that the compiler highlights.

This creates a compile-time state machine. The code simply won't compile if you try to perform an invalid transition or construct an incomplete state.

If a developer attempts to create `OrderState.Shipped()` without arguments, the build fails immediately. The `Illegal States` path is blocked by the type system, ensuring only valid states propagate through the application.

## Core Concepts

To apply this effectively in web development, we need to understand three foundational concepts in Scala 3.

**1. Algebraic Data Types (ADTs):**
ADTs combine Sum and Product types. In Scala 3, `enum` is the idiomatic way to define Sum types. Each case in the enum represents a distinct state. Cases can be unitary (no data) or carry data (product types). This allows us to model states that require different information. For example, a `PaymentFailed` state might carry an error code, while a `PaymentPending` state carries an authorization ID.

**2. Exhaustiveness Checking:**
Scala's pattern matching is exhaustive. When you `match` on an enum, the compiler verifies that all cases are handled. If you add a new case to the enum, the compiler flags
