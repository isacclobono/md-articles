# Docker for Developers: Containers, Images, and Compose Explained

## Introduction

I was debugging a Node project at 2 AM when the CI pipeline reported “Failed to install native module `bcrypt`.” The host had Node 18, but the container ran Node 16. The error trace listed a missing OpenSSL version, a mismatched glibc, and a Postgres auth failure—all in one stack trace. The senior dev on call said, “`docker compose up -d --build`.” One command, and the environment was magically consistent across my laptop, the CI runner, and the staging server.  

That moment taught me that Docker is not a “black box” or a “magic button.” It is a concrete OS‑level abstraction that lets developers ship the same exact runtime from development to production. By the end of this article you will know *why* that one command works at the kernel level, how images are built as layered filesystems, and how Docker Compose orchestrates those containers without needing Kubernetes.

We assume a Linux or macOS host with Docker Engine 24+ and basic CLI literacy. No Swarm, no K8s. This is the solo‑developer and small‑team story.

## Why This Matters

In modern software delivery, the “it works on my machine” problem is a classic reliability risk. Engineers lose hours to environment drift: language versions, system libraries, network configurations, or disk layouts. Docker solves this by packaging an application and its dependencies into a portable unit that runs identically anywhere Docker is installed.

Production teams care because:

* **Consistency** – The same image runs in CI, staging, and production. No more “works on my machine” tickets.
* **Isolation** – A misbehaving service cannot corrupt the host OS, thanks to kernel namespaces and cgroups.
* **Velocity** – New environments spin up in seconds, enabling rapid testing and feature flagging.
* **Resource efficiency** – Containers share the host kernel, so you get VM‑like isolation with a fraction of the overhead.

If you have ever spent a morning chasing a bug that only appears in staging, Docker is the technology that can eliminate that friction.

## How It Works

Docker builds a container from an **image**—a layered filesystem stored as read‑only layers in the image’s `manifest.json`. When a container starts, the runtime creates a **writable layer** on top of those read‑only layers, then applies kernel namespaces and cgroups to isolate the process.

Below is a visual flow of the Docker lifecycle for a typical microservice. The diagram shows how source code, build steps, image storage, and Compose orchestration interact.

```mermaid
flowchart TD
    A[Source Code] --> B[Dockerfile]
    B --> C[Build Context]
    C --> D[Docker Build]
    D --> E[Layer 1: Base Image]
    E --> F[Layer 2: Dependencies]
    F --> G[Layer 3: Application Code]
    G --> H[Image (Registry)]
    H --> I[Docker Compose File]
    I --> J[docker compose up -d]
    J --> K[Pull Image (if not local)]
    K --> L[Create Container (Writable Layer)]
    L --> M[Apply Namespaces & Cgroups]
    M --> N[Start Process]
    N --> O[Network & Volumes]
    O --> P[Service A]
    O --> Q[Service B]
    P --> R[Health Checks]
    Q --> R
    R --> S[Restart / Scale]
```

**Step‑by‑step breakdown:**

1. **Source Code** – The application code lives in a directory (`ledger-api`).  
2. **Dockerfile** – A declarative script that defines how to transform that code into a runnable artifact.  
3. **Build Context** – The set of files sent to the daemon (`docker build - < context/`). Only files referenced with `ADD` or `COPY` are actually transferred.  
4. **Docker Build** – The engine reads the Dockerfile line‑by‑line, executing each instruction as a separate step. Each step creates a new **layer** that is cached based on the instruction hash.  
5. **Layers** – Layer 1 is the base OS image (`alpine:3.19`). Layer 2 adds runtime packages (`ca-certificates`). Layer 3 copies the compiled binary, and Layer 4 sets up non‑root user.  
6. **Image (Registry)** – The final image is stored as a tarball in a registry (Docker Hub, GCR, etc.). The registry provides a content‑addressable store: pulling an image downloads only missing layers.  
7. **Docker Compose File** – A YAML file that defines services, networks, and volumes for a multi‑container application. It is a lightweight orchestrator that starts, stops, and restarts containers as a unit.  
8. **`docker compose up -d`** – The CLI talks to the Docker daemon, which creates containers. If the image is not present locally, the daemon pulls it from the registry.  
9. **Create Container** – A new writable layer is added on top of the image’s read‑only layers. This layer holds any changes made at runtime (e.g., log files, temporary data).  
10. **Namespaces & Cgroups** – The kernel isolates the container’s view of the filesystem (`MNT`), network stack (`NET`), process table (`PID`), and other system resources. Cgroups enforce CPU, memory, and I/O limits, which tools like `docker stats` read from `/sys/fs/cgroup`.  
11. **Network & Volumes** – Compose creates an internal bridge network so services can resolve each other by name. Persistent data is mounted as a named volume, keeping host state separate from container state.  
12. **Health Checks** – Each container can expose a health endpoint (`/healthz`). Docker monitors this endpoint and uses it for restart policies (`docker compose restart` on failure).  
13. **Restart / Scale** – When a container exits, Docker respects the `restart: unless‑stopped` policy, bringing the service back online automatically.

## Core Concepts

| Concept | What It Is | Developer Impact |
|---------|------------|------------------|
| **Image** | Read‑only filesystem layers plus metadata (`Dockerfile`, `config.v2.json`). | Immutable artifact you can version, scan, and share. |
| **Container** | Runtime instance of an image with a writable layer and kernel isolation. | Portable process that can be started, stopped, or killed. |
| **Namespaces** | Kernel subsystems that partition system resources (`PID`, `NET`, `MNT`, `UTS`, `IPC`). | Prevents a container from seeing host processes, network interfaces, or files outside its root. |
| **cgroups** | Controls resource allocation (CPU, memory, blkio). | Guarantees that a runaway process cannot starve the host. |
| **Dockerfile** | Declarative script with instructions (`FROM`, `RUN`, `COPY`, `EXPOSE`). | Defines reproducible build steps; each line is a cacheable layer. |
| **Docker Compose** | YAML file (`version: '3.8'`) that defines multi‑container apps. | One‑click start/stop of dependent services, internal DNS, and shared networks. |
| **Volumes** | Persistent storage mounted into containers. | Keeps data alive across container restarts and host upgrades. |
| **Networks** | Isolated Ethernet‑like constructs with DNS resolution. | Services communicate via hostname (`ledger-api_db`) without exposing ports. |

Understanding these pieces lets you reason about why `docker compose up` can solve a tangled dependency problem in seconds.

## Examples & Code Walkthrough

Below is a complete, production‑grade example of a microservice called `ledger-api`. The code is deliberately realistic: it includes proper error handling, health checking, and layer caching strategies.

### 1. Dockerfile (multi‑stage, production‑lean)

```dockerfile
# Dockerfile for ledger-api (multi-stage, production-lean)

# ── Stage 1: Build ──────────────────────────────────────────────
FROM golang:1.22-alpine AS builder
WORKDIR /src

# Cache go.mod/go.sum first – changes here invalidate the whole stage
COPY go.mod go.sum ./
RUN go mod download

# Copy the rest of the source; changes to *.go affect only this layer
COPY . .
# Build a static binary to avoid glibc dependency
RUN CGO_ENABLED=0 GOOS=linux go build \
    -trimpath \
    -ldflags="-s -w" \
    -o /out/ledger-api ./cmd/ledger

# ── Stage 2: Runtime ────────────────────────────────────────────
FROM alpine:3.19
# Add only runtime dependencies: certs, timezone, and a non‑root user
RUN apk add --no-cache ca-certificates tzdata && \
    addgroup -S app && adduser -S app -G app

# Copy the compiled binary from the builder stage
COPY --from=builder /out/ledger-api /usr/local/bin/ledger-api
# Ensure the binary is executable
USER app

# Expose health endpoint and application port
EXPOSE 8443

# Docker‑managed healthcheck – used by Compose and Docker Swarm
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
    CMD wget -qO- http://127.0.0.1:8443/healthz || exit 1

# Default command; can be overridden via docker run
ENTRYPOINT ["ledger-api", "--config", "/etc/ledger/config.yaml"]
```

**Why each instruction matters**

* `CGO_ENABLED=0` → static binary, no libc linking, smaller attack surface.  
* `go mod download` before `COPY . .` → if `go.mod` changes, only the download layer is rebuilt, not the whole app.  
* `trimpath` and `-ldflags="-s -w"` → strip debug info and symbols, reducing binary size.  
* `addgroup`/`adduser` → non‑root runtime user, following the principle of least privilege.  
* `HEALTHCHECK` → Docker will automatically restart containers that fail this endpoint, preventing zombie processes.

### 2. docker-compose.yml (ledger‑api with Postgres and Redis)

```yaml
# docker-compose.yml – version 3.8
version: '3.8'

services:
  ledger:
    build:
      context: .
      dockerfile: Dockerfile
      target: runtime   # Use the 'runtime' stage (the one after AS runtime)
    ports:
      - "8443:8443"
    environment:
      # Pass host‑level configuration into the container
      - LEDGER_DB_HOST=postgres
      - LEDGER_REDIS_HOST=redis
      - LEDGER_LOG_LEVEL=info
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_started
    restart: unless-stopped
    healthcheck:
      test: ["CMD", "wget", "-qO-", "http://127.0.0.1:8443/healthz"]
      interval: 10s
      timeout: 5s
      retries: 3
      start_period: 30s

  postgres:
    image: postgres:15-alpine
    environment:
      POSTGRES_DB: ledger
      POSTGRES_USER: ledger
      POSTGRES_PASSWORD: ${LEDGER_PG_PASS:?need PG pass}
    volumes:
      - pg_data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ledger -d ledger"]
      interval: 5s
      retries: 5
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: ["redis-server", "--appendonly", "yes"]
    volumes:
      - redis_data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 5
    restart: unless-stopped

volumes:
  pg_data:
  redis_data:
```

**Key points**

* `depends_on` alone is not enough for health; we use `condition: service_healthy` for Postgres and `service_started` for Redis.  
* Environment variables are injected securely; the Postgres password is taken from the host `.env` file (not shown) to avoid committing secrets.  
* Each service defines its own `healthcheck` so Docker can report service status accurately.  
* Volumes keep data persistent across container restarts.

### 3. Debug script (find a stuck container)

```bash
#!/usr/bin/env bash
# debug_container.sh – attach to a running ledger container and dump state

set -euo pipefail

CONTAINER="${1:-ledger}"   # default to the ledger service name
DOCKER="docker"

# 1. Show container info and resource usage
echo "=== Container $CONTAINER Info ==="
$DOCKER inspect --format='{{- .Name }}: {{ .State.Status }} ({{ .State.Running }})' "$CONTAINER"
$DOCKER stats --no-stream "$CONTAINER"

# 2. Capture cgroup limits for debugging
echo "=== Cgroup Limits ==="
$DOCKER top "$CONTAINER"

# 3. Check logs (last 50 lines) and health endpoint
echo "=== Recent Logs ==="
$DOCKER logs --tail=50 "$CONTAINER"

echo "=== Health Endpoint ==="
curl -s -o /dev/null -w "%{http_code}" http://localhost:8443/healthz || echo "curl failed"

# 4. If container is not healthy, restart it
if ! $DOCKER inspect --format='{{ .State.Health.Status }}' "$CONTAINER" | grep -q healthy; then
    echo "Container is unhealthy – attempting restart"
    $DOCKER restart "$CONTAINER"
fi
```

**Usage**

```bash
./debug_container.sh ledger
```

The script pulls multiple signals: process list, cgroup limits, logs, and the health endpoint. It also automatically restarts an unhealthy container, which mirrors what a production monitoring system would do.

## Best Practices

* **Cache layers aggressively** – Keep `COPY go.mod go.sum .` early in the Dockerfile; changes to source code should invalidate only the final layer.  
* **Run as non‑root** – Use an unprivileged user inside the container; set `USER app` after copying binaries.  
* **Use healthchecks** – Docker can restart containers that fail health probes, preventing zombie processes from consuming resources.  
* **Pin base images** – Prefer `alpine:3.19` over `alpine:latest` to avoid unexpected updates.  
* **Scan images** – Integrate `trivy` or `grype` into CI to catch vulnerabilities before they reach production.  
* **Limit resource usage** – Set `deploy.resources` in Compose (or `docker run --memory=512m`) to protect the host from runaway processes.  
* **Separate build and runtime stages** – Smaller runtime images reduce attack surface and improve startup time.

## Common Mistakes & Anti-Patterns

| Mistake | Why It Hurts | Fix |
|---------|--------------|-----|
| **Bloating the image with `apt-get install`** | Each `RUN` creates a new layer; `apt-get` adds megabytes of unused packages and potential vulnerabilities. | Use the smallest base image (`alpine`, `distroless`). Install only required packages with `--no-cache`. |
| **Overprivileged containers** | Running as `root` lets a compromised app read host files and escalate privileges. | Create a dedicated non‑root user (`adduser -S app`) and drop capabilities (`DROP ALL`). |
| **Misusing `depends_on`** | `depends_on` only expresses container start order, not actual readiness. | Use `condition: service_healthy` or explicit health checks. |
| **Healthcheck that never fails** | If the health endpoint always returns 200, Docker cannot detect a dead service. | Make the healthcheck call a critical internal dependency (e.g., `/healthz` that checks DB connectivity). |
| **Mounting host directories with `docker run -v` in production** | Host directory permissions can leak into the container, exposing secrets. | Use named volumes (`docker compose volumes create`) and keep secrets out of the filesystem. |
