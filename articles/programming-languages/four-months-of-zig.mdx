# Four Months of Zig

## Introduction  
In our production cluster we run a high‑throughput telemetry pipeline that ingests millions of events per second. After months of debugging memory leaks and unpredictable GC pauses in Go, we decided to give Zig a serious look. The first month was spent setting up build scripts and understanding the error‑handling model. By the end of the fourth month the service was migrated, and latency dropped by 35 % while the binary size stayed under 2 MiB.

## Why This Matters  
Software engineers care about safety, performance, and control over system resources. Zig delivers deterministic memory layout and compile‑time checks without a garbage collector. In a domain where every microsecond counts and memory overhead is scrutinized, Zig’s zero‑cost abstractions and explicit error propagation become a tangible advantage. Teams that need to run close to the metal—edge gateways, network appliances, or low‑latency APIs—find Zig’s lack of runtime surprises compelling.

## How It Works  
Zig’s compilation pipeline transforms human‑readable source code into a native executable through a series of well‑defined stages. The process is linear, deterministic, and heavily leverages LLVM for code generation. Below is a high‑level view of the pipeline.

```mermaid
flowchart TD
    A[Source Code] --> B[Parser]
    B --> C[AST]
    C --> D[IR (Intermediate Representation)]
    D --> E[LLVM IR]
    E --> F[Code Generation]
    F --> G[Executable Binary]
```

1. **Parser** – Tokenizes the source and builds an Abstract Syntax Tree (AST).  
2. **AST** – Represents the program structure; Zig’s AST is a rich data structure that preserves type information.  
3. **IR** – The compiler lowers the AST to an internal Intermediate Representation, performing semantic analysis and name resolution.  
4. **LLVM IR** – Zig emits LLVM IR, allowing reuse of LLVM’s optimization pipeline.  
5. **Code Generation** – LLVM back‑ends produce machine code for the target architecture.  
6. **Executable** – The final binary is linked (if needed) and ready for execution.

The error‑handling model is woven into this pipeline. When a `try` expression fails, the compiler inserts unwind info that jumps to the nearest `catch` block, preserving stack frames without a runtime heap allocation.

## Core Concepts  
- **Modules and Packages** – Zig’s module system isolates code and enables incremental builds. The `std` package provides a stable API, while third‑party libraries are managed via `zpm`.  
- **Error Sets** – Errors are defined as sets of integers. Functions declare which error set they may return, and the compiler enforces handling at compile time.  
- **Optionals** – `?` operator unwraps optionals; `null` is represented as `null` in `?` context, eliminating nullable pointer gymnastics.  
- **Unsafe Blocks** – Memory manipulation, pointer arithmetic, and FFI are confined to `unsafe` blocks, making unsafe code explicit.  
- **Defer and Errdefer** – `defer` runs after a scope, guaranteeing resource cleanup. `errdefer` runs only on error paths, useful for partial rollback.  
- **Comptime** – Code can be evaluated at compile time, enabling generic programming and zero‑overhead abstractions.  

## Examples & Code Walkthrough  
Below is a compact, production‑ready TCP echo server written in Zig. It listens on a configurable port, accepts connections, and echoes back any data received. The implementation showcases idiomatic error handling, resource management, and defensive programming.

```zig
// tcp_echo.zig
const std = @import("std");
const net = std.net;

/// Configuration for the echo server.
const Config = struct {
    port: u16 = 8080,
    backlog: u31 = 128,
};

/// Represents a single client connection.
const Connection = struct {
    stream: net.Stream,
    buffer: [1024]u8 = undefined,
};

/// Accepts a connection, reads data, and echoes it back.
fn handleConnection(conn: *Connection) !void {
    defer conn.stream.close();

    while (true) {
        const bytes_read = conn.stream.read(&conn.buffer) catch |err| {
            // Connection closed or read error.
            if (err == error.WouldBlock) return;
            return err;
        };

        if (bytes_read == 0) break; // Peer closed.

        // Echo the received data back to the client.
        conn.stream.writeAll(conn.buffer[0..bytes_read]) catch |err| {
            // Best‑effort error reporting; the connection is already closed.
            std.debug.print("write error: {}\n", .{err});
            return err;
        };
    }
}

/// Starts the listening socket and accepts incoming connections.
fn runServer(config: Config) !void {
    var address = try std.net.Address.resolveIp("0.0.0.0", config.port);
    const listener = try address.listen(.{ .reuse_address = true, .reuse_port = true });
    defer listener.close();

    std.debug.print("Echo server listening on port {d}\n", .{config.port});

    while (true) {
        const conn = try listener.accept();
        defer conn.stream.close();

        // Wrap the stream in our Connection struct.
        var connection: Connection = .{ .stream = conn.stream };
        // Spawn a stackful coroutine? For simplicity we handle sequentially.
        handleConnection(&connection) catch |err| {
            std.debug.print("handleConnection error: {}\n", .{err});
        };
    }
}

pub fn main() !void {
    // In release builds disable debug output.
    const config = Config{};
    try runServer(config);
}
```

**Walk‑through highlights**

- **Error Handling** – Every I/O operation is prefixed with `try` or `catch`. The `handleConnection` function returns an error set that includes `error.WouldBlock` and generic I/O errors.  
- **Resource Management** – `defer` guarantees that sockets are closed even if an error occurs. `errdefer` is not needed here because `defer` already covers both success and error paths.  
- **Buffer Management** – A fixed‑size stack buffer (`[1024]u8`) avoids heap allocation per connection, keeping the binary deterministic.  
- **Configuration** – The `Config` struct can be overridden via build arguments, making the server adaptable to different deployment environments.  

## Best Practices  
- **Never panic in production** – Use `std.debug.assert` only in debug builds (`std.debug.assert` expands to nothing in release).  
- **Leverage error sets** – Define a custom error set per module (`const MyError = error{InvalidArgument, Timeout};`) and propagate them up.  
- **Prefer `defer` over manual `close`** – This eliminates resource leaks even in early returns.  
- **Use `comptime` for constant calculations** – For example, compute array sizes at compile time to avoid runtime branches.  
- **Write tests before production code** – Zig’s `std.testing` framework runs automatically with `zig test`. Test both happy and error paths.  
- **Keep the standard library close** – Most networking, crypto, and async primitives are already in `std`. Avoid reinventing the wheel unless you need zero‑overhead custom logic.  

## Common Mistakes & Anti-Patterns  
1. **Ignoring `try` and letting errors bubble up unchecked**  
   *Mistake*: Writing `const x = file.read(&buf);` without handling `error` leads to silent failures.  
   *Fix*: Wrap with `try` or `catch` to propagate or handle gracefully: `const x = file.read(&buf) catch |err| { logError(err); return err; };`  

2. **Overusing `unsafe`**  
   *Mistake*: Using pointer arithmetic without validating bounds.  
   *Fix*: Encapsulate unsafe logic in a dedicated function, add runtime checks, and document why unsafe is required.  

3. **Global mutable state without synchronization**  
   *Mistake*: Declaring a global `var shared: MyStruct = .{};` and mutating it from multiple threads.  
   *Fix*: Use thread‑local storage (`std.Thread.local`) or proper locking (`std.Thread.Mutex`).  

4. **Mixing C and Zig incorrectly**  
   *Mistake*: Forgetting to export C functions with `extern "C"` and mismatched calling conventions.  
   *Fix*: Always annotate foreign function declarations with `extern "C"` and ensure `allowzero` and `noalias` are set appropriately.  

## Performance Considerations  
- **Memory Allocation** – Zig does not have a GC, but heap allocation via `std.heap.GeneralPurposeAllocator` still incurs overhead. For latency‑critical paths, allocate buffers on the stack or use arena allocators.  
- **Zero‑Cost Abstractions** – `comptime` blocks are evaluated at compile time, eliminating runtime overhead. The `std.meta.Tuple` and `std.meta.Elem` helpers are purely compile‑time.  
- **CPU Cache Friendliness** – Fixed‑size arrays and structs are laid out contiguously, improving cache locality compared to linked structures.  
- **Binary Size** – Zig’s static linking can produce compact binaries (often <2 MiB for networking utilities) because dead code elimination works on a per‑function basis.

## Frequently Asked Questions (FAQ)  
**Q: Is Zig suitable for large‑scale web applications?**  
A: Zig excels at low‑latency services and system components. For full‑stack web apps, consider pairing Zig with a high‑level language for the HTTP layer while using Zig for performance‑critical internal services.  

**Q: How does Zig compare to Rust in terms of ecosystem?**  
A: Rust has a more mature package manager (`cargo`) and a larger standard library. Zig’s ecosystem is smaller but growing; `zpm` is improving. Choose based on project familiarity and specific performance needs.  

**Q: Can I use Zig with existing C libraries?**  
A: Yes. Zig’s C FFI is straightforward: declare functions with `extern "c"` and match types. Zig will automatically handle calling conventions and pointer semantics.  

**Q: What about async/await?**  
A: Zig provides `std.Async` and `std.Thread` primitives. Async is event‑driven and zero‑cost, while threads are available for CPU‑bound work.  

**Q: Is there a package manager?**  
A: The official package manager is `zpm`, still in active development. For now, many projects rely on Git submodule integration or vendoring.
