# Keep calm and call clone with Rust

## Introduction

We hit the borrow checker error again last Tuesday. It was the classic `E0382: use of moved value`. The code was simple enough: a function accepted a `RequestContext` by reference, but a downstream handler needed to spawn a task that outlived the reference. The borrow checker blocked us. We could not reborrow. We could not move.

The instinct for many engineers coming from Go, Java, or Python is to reach for a reference-counted pointer or a lock immediately. In Rust, there is a third option that sits between the two. It is the `Clone` trait.

`Clone` lets you explicitly duplicate a value. It is not magic. It is a trait with a method signature you define. When you write `.clone()`, you are telling the compiler exactly how to build a second, independent copy of the data. This article is about when to trust that operation, how to implement it correctly, and where it costs you money in CPU cycles.

## Why This Matters

In a language with a strict ownership model, copying data is not free. Rust guarantees memory safety without a garbage collector. Because of this, the compiler needs to know when memory is being duplicated so it can schedule the corresponding deallocation.

The `Clone` trait is the mechanism that makes this safe duplication explicit. If you ignore it, you spend your time fighting move semantics. If you overuse it, you spend your production budget on unnecessary `memcpy` calls and heap allocations.

We recently audited a high-throughput ingestion service. We found a hot path where a struct holding a `HashMap` and a `Vec` was being cloned at the start of every request handler. That struct was 4KB. At 50,000 requests per second, we were allocating and freeing 200MB of heap memory every second just to pass configuration down the stack. We were not copying logic; we were copying metadata. Fixing that required understanding exactly what `Clone` did under the hood.

## How It Works

When you call `.clone()` on a value, the compiler looks up the implementation of the `Clone` trait for that specific type. It does not recursively walk the memory block. It calls the `clone` method defined on the type.

If the type is `#[derive(Clone)]`, the compiler generates a field-by-field copy. For primitives, this is a register move. For heap-allocated data like `String` or `Vec`, the generated code allocates new memory and copies the bytes. It does not share the heap pointer. This is a deep copy by default.

If you want to share the heap pointer instead, you wrap the data in `Arc<T>` (Atomic Reference Counted). Cloning an `Arc` does not copy the inner data. It increments a counter.

The decision tree the compiler effectively runs looks like this:

```mermaid
flowchart TD
    A[Need value in scope B] --> B{Is T Copy?}
    B -->|Yes| C[Move or Copy by register]
    B -->|No| D{Can I borrow?}
    D -->|Yes| E[Share &T reference]
    D -->|No| F{Is T Clone?}
    F -->|Yes| G[call .clone()]
    F -->|No| H[Move ownership or wrap in Arc]
    G --> I[Heap allocation if needed]
    H --> I
```

The critical distinction is between `Copy` and `Clone`. `Copy` is a marker trait. It implies bitwise copy. `Clone` is a method you must implement, allowing for complex logic, such as cloning a file handle or resolving a lazy reference.

## Core Concepts

**Copy vs Clone**
`Copy` types live entirely on the stack. `u32`, `bool`, and tuples of `Copy` types implement this automatically. When you pass a `Copy` type to a function, the original remains valid. `Clone` applies to types that own resources, typically heap memory.

**The Clone Trait**
The trait definition is tiny:

```rust
pub trait Clone {
    fn clone(&self) -> Self;
}
```

Because it takes `&self`, you can clone from an immutable reference. This makes it ergonomic. You do not need ownership to duplicate a value.

**Clone Bounds in Generics**
When writing generic code, you often need to duplicate the generic type. You must add `T: Clone` to your bounds. Without this, the compiler cannot guarantee the type supports duplication.

**Arc and Clone**
`Arc<T>` implements `Clone`. When you clone an `Arc`, the inner `T` is not touched. Only the reference count in the heap metadata changes. This is the standard pattern for sharing expensive state across threads in Rust.
