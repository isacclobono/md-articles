# Running Captum on Cloud TPUs with TorchTPU: a work log

## Introduction
We hit a wall trying to explain why our vision transformer made a critical medical diagnosis. Captum worked flawlessly on our V100s, but scaling inference volume meant moving to Cloud TPUs for cost efficiency. The catch? Captum is GPU-centric, and TPUs demand a completely different execution model. This log documents the bridge we built between PyTorch's autograd and Google's TPU runtime using TorchTPU.

## Why This Matters
Production model interpretability isn't optional anymore—it's a compliance requirement. When your inference costs drop 60% by switching to TPUs, but your explanation pipeline breaks, you've got a bottleneck. This workflow lets engineers maintain SHAP/LIME-style explanations without abandoning TPU economics. We're talking about real-time attribution for every prediction in a radiology workflow, not just offline analysis.

## How It Works
The core challenge is that TPUs execute lazily while Captum relies on immediate autograd hooks. TorchTPU acts as a translation layer, but it requires explicit step management. Here's the flow:

```mermaid
flowchart TD
    A[Start: TPU Setup] --> B[Install torch_xla & drivers]
    B --> C[Configure Captum Model]
    C --> D[Load Data with TPU Pipeline]
    D --> E[Move Model to TPU]
    E --> F[Run Captum Attribution]
    F --> G{Sync TPU Steps?}
    G -->|Yes| H[xm.mark_step_done()]
    G -->|No| I[Debug Sync Issues]
    H --> J[Retrieve Attributions]
    I --> J
    J --> K[End: Analyze Results]
```

The critical insight: every Captum operation must be wrapped in `torch_xla.step()`. This forces the TPU to materialize its lazy graph, allowing gradient flow to work correctly. Without this, you're debugging phantom tensors.

## Core Concepts
- **Lazy vs Eager Execution**: TPUs build execution graphs lazily. Captum's IntegratedGradients expects immediate tensor operations. The `xm.mark_step_done()` call is our synchronization point.
- **Device Placement**: TPU cores communicate via high-speed interconnects. Host-device transfers are expensive—batch your attribution requests.
- **Gradient Accumulation**: TPU's XLA compiler optimizes for large batch sizes. Small attribution batches cause compilation overhead spikes.

## Examples & Code Walkthrough
Here's our production wrapper that handles the TPU synchronization correctly:

```python
import torch
import torch_xla
import torch_xla.distributed as xdist
from torch_xla import xm
from captum.attr import IntegratedGradients
from typing import Callable, Optional

class TPUAttributionEngine:
    def __init__(self, model: torch.nn.Module, background_data: torch.Tensor):
        self.model = model.to(xm.xla_device())
        self.background = background_data.to(xm.xla_device())
        self.ig = IntegratedGradients(self.model)
        
    def explain_prediction(self, 
                         input_tensor: torch.Tensor, 
                         target: Optional[int] = None) -> torch.Tensor:
        """
        Runs Integrated Gradients on TPU with proper step management.
        Returns attribution tensor on host memory.
        """
        # Critical: wrap in step context for TPU graph materialization
        with torch_xla.step():
            # Move input to TPU if not already there
            if input_tensor.device.type != 'xla':
                input_tensor = input_tensor.to(xm.xla_device())
            
            # Compute attribution
            attributions = self.ig.attribute(
                inputs=input_tensor,
                target=target,
                baselines=self.background,
                n_steps=50,
                return_convergence_delta=False
            )
            
            # Force sync - this is where most bugs occur
            xm.mark_step_done()
            
        # Move back to host for analysis
        return attributions.cpu()
    
    def batch_explain(self, 
                     inputs: torch.Tensor, 
                     targets: torch.Tensor,
                     batch_size: int = 8) -> list:
        """Process attribution in batches to amortize TPU compilation."""
        results = []
        for i in range(0, len(inputs), batch_size):
            batch_inputs = inputs[i:i+batch_size]
            batch_targets = targets[i:i+batch_size]
            
            with torch_xla.step():
                batch_attributions = self.ig.attribute(
                    inputs=batch_inputs,
                    target=batch_targets,
                    baselines=self.background,
                    n_steps=50
                )
                xm.mark_step_done()
                
            results.append(batch_attributions.cpu())
            
        return torch.cat(results)

# Usage example with medical imaging
def initialize_medical_attribution_engine():
    # Load your pretrained model (assume ViT for chest X-rays)
    model = torch.hub.load('facebookresearch/deit', 'deit_base_patch16_224', pretrained=True)
    
    # Background data: typical X-ray image
    background = torch.randn(1, 3, 224, 224)
    
    engine = TPUAttributionEngine(model, background)
    return engine

# Initialize once at startup
engine = initialize_medical_attribution_engine()

# Process a batch of patient scans
patient_scans = torch.randn(4, 3, 224, 224)  # 4 new X-rays
predictions = torch.tensor([0, 1, 0, 1])       # Model predictions

attributions = engine.batch_explain(patient_scans, predictions)
```

## Best Practices
1. **Batch Aggressively**: TPU compilation overhead dominates small batches. Aim for 8+ samples per step.
2. **Pre-warm the TPU**: Run a dummy attribution before serving traffic to avoid first-request latency.
3. **Monitor XLA Logs**: Use `XLA_FLAGS="--xla_log_hlo_module_level=3"` during debugging to inspect compiled graphs.
4. **Memory Management**: Call `xm.optimize_memory_usage()` after large attribution runs to prevent OOM errors.

## Common Mistakes & Anti-Patterns
1. **Missing `mark_step_done()`**: Forgetting this call leaves tensors stranded on TPU. The fix:
   ```python
   # WRONG - hangs indefinitely
   attribution = ig.attribute(input_tensor)
   
   # CORRECT - explicit sync
   with torch_xla.step():
       attribution = ig.attribute(input_tensor)
       xm.mark_step_done()
   ```

2. **Host-Device Ping-Pong**: Moving tensors back and forth kills performance. Keep data on TPU until final results:
   ```python
   # ANTI-PATTERN
   for sample in dataset:
       host_tensor = sample.cpu()
       tpu_tensor = host_tensor.to(xm.xla_device())
       result = process(tpu_tensor).cpu()  # Unnecessary round-trip
   
   # FIX - process entire batch on TPU
   tpu_batch = batch.to(xm.xla_device())
   results = process(tpu_batch).cpu()  # Single transfer
   ```

3. **Unsupported Ops**: Captum uses some ops XLA doesn't support. Replace problematic functions:
   ```python
   # If you hit this error, swap padding methods
   # Replace F.pad with TPU-safe alternatives
   def tpu_safe_pad(x, pad):
       if x.device.type == 'xla':
           return torch.nn.functional.pad(x, pad, mode='replicate')
       return torch.nn.functional.pad(x, pad)
   ```

## Performance Considerations
- **Memory**: TPU v3 has 32GB HBM per chip. Our ViT attribution uses ~8GB per batch of 16. Scale linearly.
- **Compilation Time**: First attribution takes 3-5 minutes due to XLA compilation. Subsequent runs: <100ms.
- **Network**: TPU-VM communication adds ~2ms latency per transfer. Batch size of 32 amortizes this effectively.
- **Big-O**: Attribution complexity is O(n_steps × batch_size × model_params). TPU excels at the matrix multiplications but suffers with small batch sizes.

## Frequently Asked Questions
**Q: Why not just use GPU for interpretability?**
A: GPU costs 3x more per inference hour. For high-volume production, TPU economics win. We're talking $0.05 vs $0.15 per 1000 explanations.

**Q: Does this work with SHAP?**
A: Partially. SHAP's kernel explainer works, but tree-based SHAP doesn't. We're porting it now—expect a follow-up post.

**Q: How do I handle non-deterministic TPU results?**
A: Set `torch.manual_seed(42)` and use `xm.set_global_seed(42)`. TPU floating-point non-determinism is real but manageable.

**Q: Can I use this with custom models?**
A: Yes, but you'll need to audit your ops. XLA supports most PyTorch ops, but some custom CUDA kernels will fail. Test early.
