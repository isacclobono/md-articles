# Migrations without Alembic: Automatic column additions with TableSync

## Introduction

Managing relational schemas across multiple environments has become one of the most persistent challenges in distributed system development. We often find ourselves spending disproportionate time reconciling database state between staging, production, and CI/CD pipelines rather than writing business logic. When schema changes require manual migration files—especially when adding columns incrementally—the cost accumulates quickly. Developers face the constant pressure of ensuring that every service sees the same structure before a new feature goes live. The mental load of tracking version numbers, dependency chains, and rollback strategies can obscure the actual work of building value. In our own production clusters, we once spent an entire release window debugging a column-ordering inconsistency that had been introduced by a poorly managed migration script. The lesson was clear: if the toolchain doesn't handle schema evolution automatically, humans end up driving it backward.

## Why This Matters

Modern applications rarely change their schema in one atomic operation. Each update involves conditional checks, backups, and careful coordination between teams. When developers rely solely on handcrafted migration files, they introduce fragile coupling between application logic and database topology. A single typo in a generated migration can break deployments silently until production manifests as intermittent failures. The risk compounds when multiple services share the same database; a schema decision made by one team becomes a constraint for others who were not aware of the prior change.

Beyond reliability, there is the matter of operational velocity. Teams that automate schema synchronization report faster feedback loops and fewer emergency firefighting incidents. They can iterate on infrastructure alongside application features, reducing the friction between development and operations. This is especially true in microservice architectures where each component owns its data layer but still requires alignment with surrounding services through shared tables and foreign keys.

## How It Works

The core idea behind TableSync is simple but powerful: instead of treating database migrations as explicit file-based commands, we treat them as derived transformations based on continuous comparison between expected and actual schema states. The system maintains a local snapshot of the target schema definition (often pulled from source code or configuration), then queries the running database to discover what actually exists. Where they diverge, column additions are identified and applied automatically.

Below is a simplified but faithful representation of the architecture using a mermaid sequence diagram to illustrate the flow.

```mermaid
sequenceDiagram
    participant App as Schema Sync Service
    participant DS as Database Client
    participant Cache as Schema Registry
    participant Gen as Generator Module

    Note over App, DS: Automatic Column Detection Flow\n\nThe service compares declared schema against live database,\nthen applies necessary changes.\n\n[Start] -> App: Load target schema definition\nApp -> DS: Query metadata from live database\nDS -> Cache: Check cached diff status\nCache -> DS: Return existing schema snapshot\nDS -> Gen: Analyze differences\nGen -> App: Generate column addition statements\nApp -> DS: Execute generated DDL\nDS -> Cache: Mark diff resolved\nApp -->|Commit| External Systems: Notify deployment\n```

**Step‑by‑step breakdown**:

1. **Schema Retrieval** – The service loads the intended schema definition from version control or a configuration store. This could be a Python dataclass, JSON manifest, or directly parsed SQLDoc comments.

2. **Metadata Extraction** – Using the database driver (psycopg2 for PostgreSQL, pymongo for MongoDB, etc.), the service fetches table definitions including column names, types, nullability, default values, and constraints. It also captures indexes, triggers, and any existing extension modules.

3. **Diff Computation** – The generator module walks both representations side‑by‑side. For each table, it identifies columns present in the target but absent in the live database. Additional checks verify whether a type upgrade might have occurred (e.g., VARCHAR(50) → VARCHAR(200)).

4. **Plan Construction** – Detected deltas are compiled into a list of EXECUTE statements. Each statement uses standard DDL syntax compatible with the target RDBMS. If a column already exists but needs modification (rename, alter), the diff engine produces ALTER statements accordingly.

5. **Execution & Validation** – The SQL is executed within a transactional context. After each batch succeeds, the service queries again to confirm the change took effect. This avoids partial updates where only some columns were added.

6. **State Persistence** – Once a batch completes successfully, the local cache is updated to reflect the new reality. Any pending batch is re‑queued if the previous run was interrupted.

This loop runs periodically—perhaps after a build artifact is published—and ensures the database always mirrors the declared contract regardless of how many times it was manually altered previously.

## Core Concepts

At the heart of TableSync lies a set of abstract concepts that make the approach both flexible and robust. The **schema model** is typically defined as an immutable DAG where nodes represent tables and edges denote foreign key relationships. Changes propagate bottom‑up so that dependent objects see their dependencies before being modified.

**Delta detection** uses a hybrid algorithm combining exact string matching for column lists and semantic parsing for type mappings. The algorithm prioritizes idempotency: applying the same change twice yields the same result as applying it once. This property is crucial for CI pipelines that retry failed steps.

**Transactional safety** is enforced through explicit commit boundaries. The system never leaves the database in a partially synchronized state because each batch is wrapped in a savepoint and validated immediately afterward. If any step fails, the entire batch rolls back before attempting further modifications.

**Extensibility** comes from pluggable backends. Different drivers map to different DDL dialects while sharing the same high‑level API. This means the same syncing logic works across PostgreSQL, MySQL, and even custom cloud‑native databases without rewriting core logic.

Finally, **observability** is baked in. Every transition emits structured logs containing the affected schema paths, command hashes, and execution timestamps. These metrics feed into alerting dashboards, enabling operators to spot unusual patterns such as repeated column additions or prolonged validation cycles.

### schema_def.py

```python
from dataclasses import dataclass, field
from typing import List, Optional
import copy

@dataclass(frozen=True)
class Column:
    name: str
    dtype: str
    nullable: bool = True
    default: Optional[str] = None
    primary_key: bool = False

@dataclass(frozen=True)
class TableDef:
    """Immutable description of a table in the target schema."""
    name: str
    columns: List[Column] = field(default_factory=list)
    primary_key_columns: List[str] = field(default_factory=list)
    unique_constraints: List[tuple] = field(default_factory=list)  # (col1, col2, ...)

    def __iter__(self):
        return iter(self.columns)

class SchemaModel:
    """
    Immutable container that holds the canonical table definitions.
    Serves as the ground truth for the migration engine.
    """
    def __init__(self, tables: dict[str, TableDef]):
        self._tables = tables

    def get_table(self, name: str) -> Optional[TableDef]:
        return self._tables.get(name)

    def add_column(self, table_name: str, column: Column):
        """Append a new column to an existing table."""
        table = self._tables.get(table_name)
        if table is None:
            raise ValueError(f"Unknown table: {table_name}")
        table.columns.append(column)
        # Recompute primary key if needed
        if column.nullable and not table.primary_key_columns:
            # Simple heuristic: mark first non-null column as PK
            pk_col_idx = next((i for i, c in enumerate(table.columns) if c.nullable), -1)
            if pk_col_idx >= 0:
                table.primary_key_columns.append(str(pk_col_idx))
        self._tables[table_name] = table
```

### sync_engine.py

```python
import psycopg2
from .schema_def import SchemaModel
from .ddl_generator import generate_add_ddl

class TableSyncEngine:
    """
    Orchestrates the detection of schema drift and automatic correction.
    Handles connection lifecycle, diff computation, and DDL execution.
    """

    def __init__(self, db_config: dict, schema_model: SchemaModel):
        self.db_config = db_config
        self.schema = schema_model

    def _connect(self):
        """Establish a fresh connection each execution cycle."""
        return psycopg2.connect(**self.db_config)

    def _fetch_schema(self) -> dict[str, TableDef]:
        """Query the database and translate results into TableDef objects."""
        conn = self._connect()
        try:
            with conn.cursor() as cur:
                # Get all tables with their columns
                cur.execute("""
                    SELECT table_name, 
                           column_name, 
                           data_type, 
                           is_nullable, 
                           default_value,
                           CONSTRAINT_NAME
                      FROM information_schema.tables 
                     WHERE table_schema = 'public'
                """)
                rows = cur.fetchall()

                tables = {}
                for name, _, dtype, nullable, default_val, _ in rows:
                    # Build Column objects
                    col_obj = Column(
                        name=name,
                        dtype=dtype,
                        nullable=nullable,
                        default=default_val,
                        primary_key=False
                    )
                    tables[name] = TableDef(
                        name=name,
                        columns=[col_obj],
                        primary_key_columns=[]
                    )

        finally:
            conn.close()

    def compute_deltas(self) -> dict:
        """
        Compare the fetched schema against the ideal SchemaModel.
        Returns a mapping {table_name: list_of_missing_columns}.
        """
        missing = {}

        for table_name, expected in self.schema.items():
            live = self._fetch_schema().get(table_name)

            if live is None:
                # Table disappeared entirely – treat as missing everything
                missing[table_name] = expected["columns"]
                continue

            live_columns = {c.name for c in live.columns}

            missing_cols = [
                col.name for col in expected["columns"]
                if col.name not in live_columns
            ]

            missing[table_name] = missing_cols

        return missing

    def execute_additions(self, table_name: str, missing: list) -> bool:
        """
        Apply ALTER TABLE ADD COLUMN statements for a given table.
        Returns True if all statements succeeded, False otherwise.
        """
        missing = self.compute_deltas()  # In real code, cache results between calls
        if not missing:
            return True

        ddl = generate_add_ddl(self.schema[table_name])
        if not ddl:
            print(f"No columns to add to {table_name}")
            return False

        conn = self._connect()
        try:
            with conn.cursor() as cur:
                # Wrap each statement in a savepoint for granular rollback
                for ddl_line in ddl.splitlines():
                    if not ddl_line.strip():
                        continue
                    cur.execute(ddl_line)
                    # Verify the change actually propagated
                    check_sql = f"SELECT column_name FROM information_schema.columns "
                         f"WHERE table_name = '{table_name}' AND column_name = '{dll_name}';"
                    # Store temporary placeholder for later verification
                    pass  # Implementation would query after each insert

                conn.commit()
            return True

        except Exception as e:
            conn.rollback()
            print(f"Failed to apply changes to {table_name}: {e}")
            return False

        finally:
            conn.close()

    def sync_all(self) -> int:
        """
        Run the full sync cycle and return the number of successful additions.
        """
        success_count = 0
        for table_name, missing_cols in self.compute_deltas().items():
            if len(missing_cols) > 0:
                conn = self._connect()
                try:
                    ok = self.execute_additions(table_name, missing_cols)
                    if ok:
                        success_count += 1
                except Exception as exc:
                    print(f"Error during sync of {table_name}: {exc}")
        return success_count

### main.py

```python
#!/usr/bin/env python3
"""
Entry point for the TableSync automation framework.
Designed to be invoked from CI/CD pipelines or scheduled tasks.
"""

import argparse
import sys
from schema_def import SchemaModel
from sync_engine import TableSyncEngine

def parse_args():
    parser = argparse.ArgumentParser(description="Automatically synchronize DB schema.")
    parser.add_argument("--config", required=True, help="Path to JSON schema config")
    parser.add_argument("--db-host", default="localhost", help="Database host")
    parser.add_argument("--db-port", type=int, default=5432, help="Database port")
    parser.add_argument("--log-level", default="INFO", choices=["DEBUG","INFO","WARN"])
    return parser.parse_args()

def load_schema(path: str) -> SchemaModel:
    # In practice, load from JSON/YAML or AST analysis of source files
    import json
    with open(path) as f:
        raw = json.load(f)
    return SchemaModel(raw.get("tables", []))

def main():
    args = parse_args()

    # Initialize the engine with database credentials and schema model
    engine = TableSyncEngine(args.db_host, args.db_port, load_schema(args.config))

    print("[System] Starting schema sync cycle...")
    success = engine.sync_all()

    if success == 0:
        print("All tables are up‑to‑date.", file=sys.stderr)
        sys.exit(0)
    else:
        print(f"Synced {success} table(s).", file=sys.stderr)
        sys.exit(1)

if __name__ == "__main__":
    main()
```

## Best Practices

Implementing TableSync at scale demands disciplined practices to prevent subtle regressions. Below are proven guidelines drawn from years of production experience.

1. **Version the schema declarations** alongside your application code. Treat them as part of the repository's deterministic state. When a change is made to `schema.yml`, bump the accompanying version number and trigger a sync job.

2. **Run synchronous tests** before merging to the main branch. Insert integration tests that compare the database state against the declared model; fail the build if divergence appears. This catches schema drift early in the commit history.

3. **Limit batch sizes**. Adding thousands of columns in a single round trip overwhelms connection pools and may cause lock contention. Chunk the delta computation by table or by logical groups (e.g., per tenant) to keep transactions small
