# Custom fields on the WooCommerce Checkout block: why your old snippet does nothing

## Introduction
WooCommerce has been gradually migrating its core UI toward a block-based rendering architecture. The checkout page, traditionally a PHP-rendered form hooked into `woocommerce_checkout_fields`, now lives partially in the Block Editor ecosystem. This shift means that many developers who have been customizing WooCommerce for years find their trusted snippets silently disappearing from the front end. I've seen this exact pattern repeat across production clusters: a developer copies a PHP filter from a forum post, drops it into `functions.php`, and watches in the browser as the field never appears, or appears on the classic checkout but vanishes when the block-based layout loads. This article explains the architectural reasons behind that failure and provides a concrete, production-grade approach to adding custom fields that survive the block transition.

## Why This Matters
In recent client projects, we've encountered checkout customization failures that stalled deployments. A missing VAT number field, a broken discount code input, or a misaligned order note can directly impact conversion rates and compliance requirements. The block-based checkout was introduced to improve performance, enable richer editor experiences, and align WooCommerce with modern WordPress block patterns. However, it also introduced a secondary data pipeline that many developers aren't aware of. Understanding why old hooks stop working isn't just academic—it's a prerequisite for maintaining reliable checkout experiences in WooCommerce 8.x and later.

## How It Works
### Architecture Overview
The modern WooCommerce checkout block operates on two parallel data paths. On the server, a filtered array of field definitions is registered via `woocommerce_checkout_block_fields`. On the client, a JavaScript module reads those definitions and renders the corresponding HTML within the block's DOM. The classic `woocommerce_checkout_fields` filter runs on the legacy checkout template, but the block component completely bypasses that array. Instead, it consults its own registration mechanism, and any field added via the classic hook is simply ignored during the block render phase.

```mermaid
flowchart TD
    A[Request arrives] --> B[WooCommerce Block Checkout component]
    B --> C{Server: wc_blocks/checkout}
    C --> D[woocommerce_checkout_block_fields filter]
    D --> E[wc_checkout_block_get_field_html()]
    E --> F[Rendered field HTML]
    F --> G[Client: wp.blocks registry]
    G --> H[wc_checkout_block JS module]
    H --> I[Inject field markup into DOM]
    I --> J[User interacts]
    J --> K[Save/POST data via REST API]
    K --> L[Order metadata persisted]
```

The flowchart above illustrates the end-to-end path: from the initial HTTP request, through the server-side field filter, into the rendering helper, then into the client-side block registry and JavaScript module that actually injects the HTML into the checkout interface. Any custom field you add must pass through both the server filter and the client-side injection point.

## Core Concepts
- **Block registration**: WooCommerce registers the checkout as a block under the `wc_blocks` namespace. The component lives in `woocommerce/blocks/checkout` and uses `Edit` and `Save` components defined in JavaScript.
- **Server-side field API**: The filter `woocommerce_checkout_block_fields` returns an associative array keyed by field slug. Each entry can define label, type, placeholder, CSS class, and visibility conditions. The helper `wc_checkout_block_get_field_html()` accepts a field key and returns the complete HTML string, including appropriate wrapping and attributes.
- **Client-side rendering**: The `wc_checkout_block` JavaScript module, registered via `wp.blocks.registerBlockType`, maintains the field registry in memory. When the block mounts, it calls the server endpoint, receives the field HTML, and inserts it into the designated `checkout-fields` container. The `save` component persists any user input as post meta via the REST API.
- **Data flow**: Custom fields must be registered on the server, their HTML must be generated by the helper, and the client module must be aware of the new field key to avoid rendering it as undefined.

## Examples & Code Walkthrough
Below is a complete, production-ready approach to adding a custom "Tax ID" field to the WooCommerce checkout block. The solution consists of three parts: a server-side filter to register the field, a helper call to generate the HTML, and a tiny JavaScript snippet to ensure the field appears in the block editor preview.

### Server-side PHP
```php
<?php
/**
 * Plugin: Custom Checkout Block Fields
 * Adds a Tax ID field to the WooCommerce checkout block.
 */

/**
 * Register the custom field in the block checkout field array.
 *
 * @param array $fields Associative array of checkout block fields.
 * @return array Modified field array with Tax ID included.
 */
function wccb_register_tax_id_field( $fields ) {
    // Only modify the array if we're in the block checkout context.
    // The filter runs on every checkout request; we guard against
    // accidental double-registration on the classic template.
    if ( ! function_exists( 'wc_get_checkout_url' ) || ! is_wc_version( '8.0' ) ) {
        return $fields;
    }

    // Define the field with sensible defaults.
    $fields['tax_id'] = [
        'type'        => 'text',
        'label'       => __( 'Tax ID / VAT Number', 'woocommerce' ),
        'placeholder' => _x( 'e.g. 123456789', 'Tax ID placeholder', 'woocommerce' ),
        'css_class'   => [ 'form-row', 'tax-id-field' ],
        'priority'    => 30, // Positioned after company field typically.
        'required'    => false,
    ];

    return $fields;
}
add_filter( 'woocommerce_checkout_block_fields', 'wccb_register_tax_id_field' );

/**
 * Ensure the field HTML includes a data attribute for the client-side module.
 *
 * @param string $html HTML output from the field helper.
 * @return string Modified HTML with data attribute.
 */
function wccb_tax_id_field_html( $html ) {
    // The helper wraps the field in a div with class "form-row".
    // We inject a data attribute so the JS module can identify the field key.
    if ( str_contains( $html, 'name="tax_id"' ) ) {
        $html = preg_replace(
            '/<div class="form-row"(.*?)>/',
            '<div class="form-row"$1 data-wccb-field="tax_id">',
            $html
        );
    }
    return $html;
}
add_filter( 'wc_checkout_block_field_html', 'wccb_tax_id_field_html' );
```

### Client-side JavaScript
The following script should be enqueued on the checkout page. It hooks into the `wc_checkout_block` module after the field HTML has been injected, and ensures the input is wired up for validation and submission.

```javascript
/**
 * Custom field initialization for WooCommerce Checkout Block.
 * Ensures the Tax ID field is accessible and its value is included
 * in the order submission payload.
 */
(function ( wp ) {
    'use strict';

    const { useEffect } = wp.element;
    const { useSelect } = wp.data;

    wp.hooks.addFilter(
        'wc_checkout_block/fields/rendered',
        'wccb/tax-id',
        ( fields ) => {
            // Ensure our field key exists in the rendered set.
            if ( 'undefined' === typeof fields.tax_id ) {
                return fields;
            }
            // Mark the field as validated for the submit handler.
            fields.tax_id.validated = true;
            return fields;
        }
    );

    useEffect( () => {
        // Listen for the block to finish rendering fields.
        const unsubscribe = wp.data.subscribe( () => {
            const fields = wp.select( 'wc-blocks/checkout' ).getFields();
            if ( fields && fields.tax_id ) {
                // Attach a change handler to normalize the input value.
                const input = document.querySelector( 'input[name="tax_id"]' );
                if ( input ) {
                    input.addEventListener( 'change', () => {
                        wp.dispatch( 'wc-blocks/checkout' ).setFieldProps( {
                            key: 'tax_id',
                            value: input.value.trim(),
                        } );
                    } );
                }
                unsubscribe();
            }
        } );
    }, [] );
} )( window.wp );
```

### What this accomplishes
- The PHP filter injects the field definition into the block's server-side array.
- The second filter ensures the rendered HTML carries a `data-wccb-field="tax_id"` attribute, which the JavaScript module can use to locate and wire the input.
- The JavaScript snippet runs after the block mounts, selects the input by its name, and dispatches a field-props update that the block's save handler will include in the REST API payload.

## Best Practices
1. **Always filter `woocommerce_checkout_block_fields`, not `woocommerce_checkout_fields`.** The block component reads the former; the latter is ignored during block render.
2. **Use the helper `wc_checkout_block_get_field_html()`** for generating field HTML. It handles wrapping, attribute naming, and accessibility attributes out of the box.
3. **Add a `data-wccb-field` attribute** on the wrapper element if you need JavaScript to locate the field by key. This is more reliable than querying by `name` attribute, which can conflict with other form inputs.
4. **Sanitize and validate on the server.** Even though the field is rendered by a helper, always add a sanitization callback via `woocommerce_update_order_meta` and `wc_validate_tax_id` (or a custom callback) to prevent malformed data from reaching the order meta table.
5. **Test on both classic and block checkouts.** The filter `woocommerce_checkout_block_fields` runs on the block checkout; on the classic template, it's a no-op. Verify that your field appears only where expected, and that no PHP warnings are triggered on the legacy path.

## Common Mistakes & Anti-Patterns
1. **Hooking into `woocommerce_checkout_fields` and expecting it to affect the block checkout.** This is the #1 root cause of "field does not appear" bugs. The block component completely bypasses that array. Fix: switch to `woocommerce_checkout_block_fields`.
2. **Missing the `data-wccb-field` attribute.** Without it, the client-side JavaScript has no deterministic way to locate your custom field among the many form rows. Result: the field renders but is invisible to the submission pipeline. Fix: add the attribute in a `wc_checkout_block_field_html` filter, as shown above.
3. **Forgetting to sanitize the field value.** Custom fields added via the block API are not automatically sanitized. If you store raw user input as order meta, you risk DB corruption or security issues. Fix: hook into `woocommerce_checkout_create_order` and apply `sanitize_text_field()` (or a more specific validator) before updating meta.
4. **Using `echo` inside the field HTML filter.** The `wc_checkout_block_field_html` filter expects a return value, not an echo. Outputting directly will break the helper's wrapping logic and produce malformed HTML. Fix: always `return $html;` at the end of your filter function.

## Performance Considerations
Adding custom fields to the block checkout introduces negligible overhead when done correctly. The server-side filter runs once per checkout request and adds a single array entry—O(1) complexity. The helper `wc_checkout_block_get_field_html()` performs a string swap and returns pre-wrapped HTML; its cost is dominated by the number of fields present, not by the complexity of your custom field. On the client, the JavaScript module mounts after the initial HTML render and performs a single DOM query to wire the input. Memory impact is a single object entry in the block's field registry. In high-traffic scenarios (thousands of checkout requests per minute), the additional DB query for field registration is already cached by WooCommerce's internal object cache, so marginal impact is observed. If you anticipate dozens of custom fields, consider lazy-loading field HTML via the REST endpoint `GET /wc-blocks/checkout/fields` rather than embedding all fields on every request.
